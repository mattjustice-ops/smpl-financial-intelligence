The Universal Billing IMS Principle — Three Financial Distinctions
Three financial distinctions are restated in every connector in this library because they are the most consequential sources of Financial Intelligence errors across every Billing implementation:
Invoice ≠ Revenue Recognition. An invoice documents that a billing event occurred. It does not confirm that revenue has been recognized under ASC 606/IFRS 15. The ERP is the canonical owner of recognized revenue; Billing estimates deferred revenue from service-period fields but never confirms it.
Payment ≠ ARR. A successful payment confirms cash collection — not recurring revenue commitment. A one-time payment produces no ARR; an annual prepay creates ARR in the period of subscription, not in the period of payment. The Subscription object, not the Payment object, is the source of ARR.
Subscription ≠ Bookings. A Billing subscription confirms commercial execution — that a customer is actively being billed. It does not confirm what the sales team recorded as the deal. Bookings confirmation requires CRM cross-validation; the gap between CRM Closed Won and Billing subscription creation is a standard implementation finding, not an error.
The Subscription Normalization Gate
Every Billing connector in this library has a mandatory Subscription Normalization Gate — the Billing equivalent of the CRM Stage Normalization Gate. Unlike the ERP library's extraction BLOCKs (which prevent all extraction until resolved) and the CRM library's confidence degradation gates (which allow extraction while degrading pipeline confidence), the Subscription Normalization Gate operates differently:
Subscription data CAN be extracted before the gate is resolved.
ARR CANNOT be reliably computed before the gate is resolved — the computed ARR figure will be incorrect, not just lower-confidence.
The gate must be resolved before any ARR Movement canonical object is created. Creating ARR Movement from unresolved subscription data produces silently incorrect ARR figures.
The three questions the Subscription Normalization Gate resolves for every customer, across every Billing connector in this library:
Gate Question
Why It Matters
Consequence If Skipped
Trial treatment: are trialing subscriptions included in ARR?
Default SMPL treatment excludes trials from ARR. If the customer's internal reporting includes trials, their ARR will never match SMPL until this is resolved.
ARR is systematically understated or overstated vs. customer's own ARR reporting — a discrepancy that appears immediately after the first ARR report is delivered.
Usage-based ARR policy: which portion of metered/usage billing counts as ARR?
The committed-minimum portion of usage billing is reasonably ARR; uncommitted overages are not. The line between them is customer-defined, never a platform default.
ARR from usage-billed customers is computed inconsistently — same usage pattern produces different ARR for different customers until policy is recorded in CEP.
Past_due / unpaid status treatment: should delinquent subscriptions remain in ARR?
Subscriptions that have failed payment but are not yet cancelled remain technically active in most Billing platforms. Whether they count as ARR is a business policy decision.
Delinquent-subscription ARR inflates total ARR until the gate is resolved. For customers with meaningful involuntary churn rates, this gap can be material.

Cross-Billing Principles
SMPL is always read-only. No Billing IMS specifies write operations.
ARR is derived from Subscriptions, not Invoices or Payments. The implementation agent always computes ARR from the Subscription object's active price and quantity, not from invoice amounts or payment totals. One-time invoice amounts must be explicitly excluded from ARR calculations.
Native SaaS metrics from Billing platforms are reference-only, never canonical. Chargebee's mrr field, Maxio's native metrics, and Zuora's pre-computed ARR are all cross-validation inputs — SMPL computes its own metrics from canonical Subscription data. Never import pre-computed vendor metrics as canonical values.
Revenue Recognition module status is always confirmed explicitly. For Chargebee, Maxio, and Zuora, the Revenue Recognition module materially changes the Revenue Schedule confidence ceiling. The implementation agent never assumes the module is active based on platform tier or vendor positioning.
Billing is the validation layer between CRM and ERP. Every Billing implementation is an opportunity to confirm that CRM Closed Won Opportunities correspond to actual subscriptions and that Billing invoices correspond to ERP-recognized revenue. Document both cross-validations explicitly in Section 6 (Canonical Population) for every connector.
IMS-201 — Stripe Billing
Stripe Billing is the Production Ready reference implementation for the Billing IMS library — the most consistent API, the lowest schema variability, and the most validated ARR derivation formula of any connector in this library. The implementation agent should expect minimal surprises and fast canonical population for standard configurations, with usage-based billing and multi-item subscriptions as the primary complexity drivers when present.
✱ ARCHITECT NOTE: Key characteristic distinguishing Stripe from all other Billing connectors in this library: Stripe stores all financial activity in a single account's API surface regardless of product complexity. There is no multi-site configuration, no Controlling Area equivalent, no ledger selection. The primary pre-extraction gate is environment type (livemode=true) — the Stripe equivalent of ERP's sandbox detection. The primary Subscription Normalization Gate question is ARR formula correctness, specifically ensuring subscription.items[] is used rather than the deprecated subscription.plan field.

4.3 ARR Movement Derivation — The Core Billing Transformation
ARR Movement is not a native Stripe object — it is derived from subscription state changes over time. This derivation is the most important transformation in the Billing IMS library, equivalent in consequence to account type normalization in the ERP library.
ARR MOVEMENT DERIVATION ALGORITHM:
  PREREQUISITES:
    1. Subscription Normalization Gate resolved (Table IMS-201.1.3)
    2. Historical subscription event stream available (GET /v1/events?type=customer.subscription.*)
    3. CEP.arr_policy confirmed for trial, usage, and delinquent treatment
  FOR each Subscription:
    COMPUTE current ARR = SUM(item.price.unit_amount × item.quantity × 12/interval)
      across all items where item.price.recurring.usage_type = "licensed"
    APPLY usage ARR per CEP.arr_policy.usage_treatment
    APPLY delinquent/trial exclusion per CEP.arr_policy
  FOR each Subscription state change event (from /v1/events):
    event_type                    → ARR Movement Category
    customer.subscription.created → NEW_BUSINESS (if first subscription for this Customer)
                                    REACTIVATION (if Customer had prior cancelled subscription)
    customer.subscription.updated → Compute ARR delta:
      delta > 0 → EXPANSION
      delta < 0 → CONTRACTION
      delta = 0 → metadata change only; no ARR Movement created
    customer.subscription.deleted → CHURN
    customer.subscription.paused  → Conditional per CEP.arr_policy
  SPECIAL CASE — Subscription ID change on upgrade:
    IF new subscription created shortly after cancellation for same Customer:
      AND amount is larger → FLAG as potential Expansion misclassified as Churn+New
      ASK CEP: "Is this subscription replacement or a genuine churn+new?"
      Record classification in CEP.subscription_lineage before creating ARR Movements
4.4 Currency Normalization
Stripe stores amounts in the smallest currency unit (cents for USD; similar for other currencies). All SMPL canonical monetary fields require decimal representation.
FOR every Stripe monetary field (unit_amount, amount_due, amount_paid, etc.):
  IF currency is zero-decimal (JPY, KRW, etc.):
    canonical_amount = raw_amount  (no division needed)
  ELSE:
    canonical_amount = raw_amount / 100
  THEN apply standard cross-currency conversion if
  CEP.functional_currency != transaction currency:
  (same pattern as ERP IMS-001 Section 4.4)

IMS-203 — Recurly
Recurly's defining implementation characteristic is the strongest dunning and decline-reason tracking of any connector in this library — enabling involuntary/voluntary churn classification that Stripe and Chargebee cannot match at equivalent confidence. The implementation agent should leverage this advantage explicitly in Churn Analysis capability activation, while applying standard Validated-maturity caution to the broader ARR and pipeline capabilities.
✱ ARCHITECT NOTE: Key departure from Stripe and Chargebee: Recurly's Account object is sometimes created per-subscription rather than per-customer — a data modeling choice that fragments canonical Customer Account identity and must be explicitly detected and reconciled during discovery. If undetected, the same customer appears as multiple Customer Accounts in the canonical store, producing duplicate ARR attribution.

4.1 Involuntary vs. Voluntary Churn Classification — Recurly's Distinctive Transformation
INVOLUNTARY/VOLUNTARY CHURN CLASSIFICATION:
FOR each subscription with status = expired (cancelled):
  RETRIEVE: last N transactions WHERE type IN (payment, declined)
  N = CEP.dunning_config.retry_intervals.count
  IF subscription has declined transactions matching dunning retry schedule
     AND cancellation follows exhausted retries:
     → ARR Movement.cancellation_type = INVOLUNTARY_CHURN
     → ARR Movement.decline_reason = transaction.error_code (normalized)
  IF subscription has no recent payment failures AND
     cancellation via explicit customer request (subscription.cancelled_at present):
     → ARR Movement.cancellation_type = VOLUNTARY_CHURN
  IF ambiguous (mixed signals):
     → ARR Movement.cancellation_type = UNKNOWN
     → FLAG_FOR_CEP for manual classification
Decline reason normalization (error_code → canonical):
  insufficient_funds → INSUFFICIENT_FUNDS
  card_declined → CARD_DECLINED
  expired_card → EXPIRED_CARD
  do_not_honor → CARD_ISSUER_DECLINED
  invalid_number → INVALID_PAYMENT_METHOD
  [other] → FLAG_FOR_CEP

IMS-205 — Zuora
Zuora is the most complex Billing connector in this library — the enterprise-tier equivalent of Oracle Fusion in the ERP library. Its Rate Plan/Rate Plan Charge structure is the most granular pricing model in the library, and RevPro (the Revenue Recognition module) is the most sophisticated revenue recognition of any Billing connector SMPL supports. Section 4 — Transformation Rules
4.1 Rate Plan Charge ARR Derivation — The Core Zuora Transformation
ZUORA ARR DERIVATION (per subscription):
FOR each Subscription:
  subscription_arr = 0
  FOR each ratePlan in subscription.ratePlans:
    FOR each charge in ratePlan.ratePlanCharges:
      IF charge.chargeType = "Recurring":
        IF charge.chargeModel = "FlatFee":
          charge_arr = charge.price × (12 / billing_period_months(charge.billingPeriod))
        ELIF charge.chargeModel = "PerUnit":
          charge_arr = charge.pricePerUnit × charge.quantity × (12 / billing_period_months(charge.billingPeriod))
        ELIF charge.chargeModel IN ("Tiered", "Volume"):
          FLAG_FOR_CEP: "Rate Plan Charge {charge.name} uses {model} pricing.
          What quantity tier should SMPL use for ARR computation?"
          charge_arr = 0  // pending CEP resolution
        ELIF charge.chargeModel CONTAINS "Discount":
          discount_arr += compute_discount(charge)
          charge_arr = 0  // applied separately
        subscription_arr += charge_arr
      ELIF charge.chargeType = "Usage":
        Apply CEP.arr_policy.usage_treatment
      ELIF charge.chargeType = "OneTime":
        EXCLUDE from ARR; include in Invoice Analytics only
  subscription.arr_value = subscription_arr - total_discounts
  VALIDATE: subscription.arr_value > 0 for any active, non-discounted subscription
  If = 0: FLAG — likely incomplete Rate Plan Charge enumeration
4.2 Amendment-Based ARR Movement Derivation
Zuora's Amendment object provides a more formally structured ARR Movement source than subscription event logs — the equivalent of SAP's BKPF document header in terms of providing clear, typed records of subscription changes.
FOR each Amendment:
  amendment.type → ARR Movement Category:
    NewProduct → NEW_BUSINESS (if first subscription for Account)
                 EXPANSION (if Account had existing active subscriptions)
    RemoveProduct → CONTRACTION (if subscription remains) / CHURN (if no products remain)
    UpdateProduct → Compute ARR delta before/after:
      delta > 0 → EXPANSION
      delta < 0 → CONTRACTION
      delta = 0 → No ARR Movement (metadata change only)
    Renewal → RENEWAL (confirm with CRM Renewal Opportunity if connected)
    Cancellation → CHURN
  FLAG: Amendment.type does not always equal the canonical movement category.
  An "UpdateProduct" with delta > 0 is EXPANSION.
  A "RemoveProduct" leaving one product remaining is CONTRACTION, not CHURN.
  Compute ARR delta rather than trusting amendment type directly.

Final Determination
The Billing Implementation Mapping Specification Library (IMS-201 through IMS-205) is complete. Implementation agents and human consultants have sufficient implementation knowledge to begin onboarding any Tier 1 Billing platform. HRIS IMS Library development may begin.
The Billing library introduces one IMS concept that had no direct equivalent in the ERP or CRM libraries: the distinction between a confidence degradation gate (CRM Stage Normalization: pipeline capabilities degrade while extraction continues) and a population block gate (Billing Subscription Normalization: ARR Movement creation is blocked, not just degraded, while extraction continues for all other objects). This distinction matters because incorrectly computed ARR is actively worse than missing ARR — a wrong number is used for decisions; a missing number is at least known to be absent. Blocking ARR Movement creation until the three policy questions are resolved ensures that the first ARR figure a customer sees is correct, not just present.
The cross-connector pattern from building all five simultaneously: every Billing connector's highest-severity implementation risk is a silent ARR computation error, not a data quality gap that surfaces in validation. Stripe's deprecated subscription.plan field, Chargebee's currency unit difference, Recurly's Account fragmentation, Maxio's native metric import, and Zuora's incomplete Rate Plan Charge enumeration all share the same failure mode: the canonical store is populated with data that appears complete but produces incorrect ARR figures. The Subscription Normalization Gate and connector-specific additional gates in Section 1 of each IMS exist specifically to prevent these silent errors — this is why the gate blocks ARR Movement creation rather than simply degrading its confidence.
