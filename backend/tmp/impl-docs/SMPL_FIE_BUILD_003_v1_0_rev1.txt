Platform Assembly Before Platform Scale. The platform must operate correctly for one customer before it is optimized for one thousand.
Purpose and Authority
FIE-BUILD-001 established WHAT gets built and in what order. FIE-BUILD-002 established HOW each engineer builds each service consistently. This document establishes HOW the assembled whole becomes one working, operable system — environments, infrastructure, startup order, integration testing, cutover, monitoring, failure recovery, disaster recovery, deployment, certification, and customer acceptance. It redesigns nothing: ABS, BIS, FIE, and both prior BUILD documents remain frozen and authoritative. Every recommendation here maps back to a specific section of one of them.

Section 6 — GPES Integration
GPES-001 is the platform's acceptance test — the reference trace every milestone should be measurable against. Per FIE-BUILD-001 §9's own clarification, GPES-001 was written assuming Path B (live connector) onboarding; the subset of its fixtures exercising Canonical-and-below behavior is path-agnostic and applies to every milestone, while its full connector-specific conformance applies specifically at FIE-BUILD-001 Milestone 8.
Every milestone in FIE-BUILD-001 §19 ends with: run the path-agnostic subset of GPES-001 against the current build
Everything passes: the milestone's own exit criteria plus the relevant GPES-001 fixtures both succeed

Section 11 — Disaster Recovery
Backups: automated, regular backups of every service's Postgres store, retained per the platform's data retention policy
Restore: a documented, tested restore procedure per service, exercised on a schedule, not only when an actual disaster occurs
Point-in-time recovery: available for every service's database, exploiting the platform's own append-only, versioned data model (FIE-BUILD-002 §8) — a PITR restore of an immutable, versioned store is inherently safer than restoring a mutable one, since there is no in-place edit history to lose partial context on
Infrastructure loss: documented recovery runbook per infrastructure component (Section 3), with clear ownership per FIE-BUILD-001's Engineering Ownership Matrix and this document's own Platform Ownership Matrix, below
Region failure: if the platform operates in multiple regions, documented failover procedure; if single-region at current scale, documented recovery time objective and communicated honestly as a current limitation, not silently assumed away
Data corruption: because the platform is append-only and versioned everywhere (FIE-BUILD-002 §8), a corruption event's blast radius is bounded to the specific rows affected — recovery is restoring or replaying from the last known-good version, never reconstructing a mutable table's edit history
Deployment failure: rollback per Section 2's per-environment rollback rules and FIE-BUILD-002 §12's rollback strategy

Day Zero Platform Initialization
The pipeline above governs ongoing deployments. The very first production deployment — bringing a brand-new production environment online — follows its own one-time operational sequence:
1. Provision infrastructure — every Section 3 component, in production configuration
2. Configure secrets — populated in the production secrets manager, never committed to a repository
3. Initialize databases — Postgres instances created for every service, per Section 4's startup order
4. Execute migrations — every service's migrations run forward-only, per FIE-BUILD-002 §8
5. Seed platform registries — Financial Concepts, Business Themes, Industry Templates, and any other platform-default registry data a customer's Methodology will reference
6. Deploy core BIS services — BIS-001 through BIS-006, per Section 4's startup order
7. Deploy FIE services — FIE-001 through FIE-005, per Section 4's startup order
8. Run health verification — every service's health and readiness endpoints confirmed green, per Section 4
9. Execute GPES validation — the path-agnostic GPES-001 subset (Section 6) run against the empty, freshly initialized platform
10. Activate first tenant — the first real (or design-partner) customer begins onboarding, per Section 7
11. Verify customer onboarding — Customer Go-Live Validation (Section 7) passes for that first tenant
12. Declare production operational — Section 13's certification checklist reviewed and signed off for that first customer cohort
This sequence runs once per environment's lifetime, not once per deploy — it is the answer to "how do we turn on a brand-new production environment," which Section 12's ongoing pipeline above does not address.

Operational Readiness Checklist
Certification represents operational readiness, not only software completeness. In addition to the domain-by-domain list above, confirm:
Monitoring dashboards are operational — Section 9's full suite, not just individual health endpoints
Alerts have been tested — a deliberately triggered failure actually produces the expected alert, not just a configured rule nobody has verified fires
Backup procedures have been validated — Section 11
Restore procedures have been exercised — not just documented, actually run at least once
Runbooks exist for all critical failures — Section 10's failure domains, each with a written recovery procedure
Support documentation is complete — whoever handles a customer's question can find the answer without escalating to the engineer who built the feature
Production feature flags are configured — per-customer cutover flags (Section 2) are set correctly for the cohort being certified
Customer communication procedures exist — per FIE-BUILD-001 §18.7's honest-discontinuity communication principle, someone owns actually telling the customer

New Principle: Platform Assembly Before Platform Scale
Correctness before scale. Repeatability before optimization.
This principle has been implicit throughout the BUILD series and is made explicit here because platform integration is where the temptation to violate it is strongest. It would be easy, once eleven services exist, to immediately optimize for one thousand customers — parallelize everything, cache aggressively, shard early. This document's own sequencing rejects that: FIE-BUILD-001's golden path proves the platform correct for one customer (Milestone 6) before FIE-BUILD-003's certification (Section 13) considers broader readiness, and Section 9's monitoring exists to prove repeatable correctness before Section 12's pipeline is trusted to deploy faster and more often.
Concretely: a platform that handles one customer's ARR narrative correctly, reproducibly, and explainably is a stronger foundation than a platform that handles a thousand customers' narratives quickly but with an unresolved confidence-propagation edge case. Every optimization in this document — caching (Section 3), parallel execution (referenced from FIE-003), scaled worker pools (Section 3) — is sequenced after the correctness properties (determinism, immutability, explainability) they would otherwise be tempted to trade away.
