Section 1 — Engineering Philosophy
Ten principles. Every one already exists somewhere in frozen architecture — this section names them once, together, so no engineer has to reconstruct them by reading eleven documents.
Canonical First
No service reads a source system directly except Connector Proxy (BIS-001). Every other service — every FIE service, Reporting, Validation, Knowledge — reads only Canonical Business Objects or another service's derived output. If a new feature seems to need a direct connector read, that is a signal the design is wrong, not that an exception is warranted.
Established in: BIS-003 §1.1; ABS-012 §2 Canonical Convergence
Deterministic Core
FIE-003 is the only service with no LLM anywhere in its execution path. Given identical Operating Model version, methodology/formula versions, and Observation/Revision inputs, it produces byte-identical output, forever. No engineer may introduce non-determinism (wall-clock time, random ordering, floating model temperature) into this path under any circumstance, including for performance.
Established in: FIE-003 §1.11, §Core Architectural Principle
AI Never Changes Numbers
AI participates in mapping proposals, methodology template guidance, and reasoning/narrative generation — never in calculation. FIE-005's Financial Reasoning Engine reasons about numbers FIE-003 already produced; it does not recompute them. See FIE-003 §1.2–1.3 (calculation is deterministic, no LLM anywhere in the path) and FIE-005 §1.3 (reasoning about, not recomputing, FIE-003 outputs) for the full AI boundary.
Established in: FIE-003 §1.2–1.3; FIE-005 §1.3
Small Services
Prefer many focused services over a small number of large ones. Each service owns one primary responsibility, exposes a well-defined contract (Section 6/15), and evolves independently of every other service's release cycle. This is not a new idea introduced here — it is the reason BIS-001 through BIS-006 and FIE-001 through FIE-005 exist as eleven separate specifications instead of one. A service that starts accumulating a second primary responsibility is a signal to split it, not to document an exception.
Established in: Reflects the architecture already established throughout BIS and FIE, restated here as an explicit engineering principle rather than left implicit
Immutability
Nothing in this platform is ever edited in place. A correction is a new version, a new row, a new run — never an UPDATE to an existing value, confidence, or timestamp field. Every schema in Appendix A must be reviewed against this rule before merge, with an explicit note on which columns have no UPDATE grant.
Established in: Universal — first established BIS-003 §1.5, restated in every subsequent document
Reference Instead of Copy
A fact or value owned by one service is referenced by ID from another, never duplicated as a second stored copy. This is the single most common category of design mistake this platform's own review process has caught (Driver Registry vs. Assumption Library, Decision Memory vs. FIE-001 values, Financial Evidence vs. Reasoning Package) — treat any PR that stores a value already owned elsewhere as a blocking review comment.
Established in: FIE-002 §1.1; FIE-004 §8
Fail Closed
When evidence is missing, confidence is insufficient, or verification cannot complete, the default behavior is to block, not to proceed with a caveat baked silently into the output. There is no code path where uncertainty is resolved by guessing in the direction of availability.
Established in: BIS-004 core principle; FIE-005 §1.10, §14
Explainability by Default
Every published value must be able to answer where it came from, without a special debug mode. Explainability is not a feature added later — it's satisfied by every table having lineage references from the day the table is created, per Section 17 below.
Established in: FIE-005 §1.6, §15
Version Everything
Registries (methodologies, formulas, drivers, templates, business themes, narrative policies) are append-only and versioned; a change creates a new version, never an in-place edit. This is what makes reproducibility (Deterministic Core) and auditability (Explainability) actually hold at the schema level, not just as documented intent.
Established in: FIE-002 §1.7–1.8; pattern repeated in every registry across the platform
Build Interfaces Before Implementations
Where a capability doesn't have a dedicated owning service yet (Explainability), specify its interface contract first and build an interim adapter against it — never build ad hoc, undocumented calls that a future extraction would have to reverse-engineer.
Established in: FIE-005 §1.11

Versioning Philosophy
"Version Everything" (Section 1) is not limited to financial registries. Reproducibility across this platform depends on version pinning consistently, everywhere:
APIs — versioned in path (Section 6); a breaking change is a new version, never an in-place contract change
Events — schema_version on every event envelope (Section 7), so a consumer can detect a shape it doesn't yet understand
Database schema — every migration is versioned and forward-only (Section 8)
Methodologies — every version pinned, per FIE-002 §1.7–1.8
Financial Operating Models — frozen at creation, never recomputed, per FIE-002 §1.7
Configuration — every configuration change is itself a versioned, auditable event, not a silent overwrite
Contracts — published to shared/contracts (Section 2) with their own version, imported by consumers, never copy-pasted at a point in time and left to drift
Registries — Business Themes, Narrative Policies, Driver definitions, Industry Templates — all append-only and versioned, per the pattern established since FIE-001 §1.9
The unifying reason all eight of these are versioned the same way: a historical result — a calculation, a narrative, a report — is only reproducible if every input that produced it can be resolved to the exact version that was active at the time. Version pinning is not a data-hygiene nicety; it is the mechanism the platform's entire reproducibility guarantee runs on.
Configuration Hierarchy
Where more than one configuration source could apply to the same setting, precedence resolves in exactly one order, highest to lowest:
Platform Defaults       ↓Industry Template       ↓Operating Model       ↓Customer Configuration       ↓Feature Flags       ↓Runtime Overrides   (highest precedence — applies last)
Platform Defaults — the platform's own out-of-the-box values, lowest precedence
Industry Template — a recommended starting configuration for a vertical (FIE-002 §11), overrides platform defaults
Operating Model — a specific customer's frozen, composed methodology set (FIE-002 §1.7), overrides template defaults
Customer Configuration — explicit customer-specific overrides layered on top of their Operating Model
Feature Flags — platform-controlled toggles (Section 5, Section 12) that can override customer configuration for rollout or rollback purposes
Runtime Overrides — the narrowest, most temporary layer (e.g. a single request specifying as_of or execution_mode) — applies last and never persists beyond the request that set it
This hierarchy exists to remove ambiguity, not to encourage overriding — most settings should resolve at Platform Defaults or Industry Template and never need a customer- or request-level override at all.

Section 5 — Engineering Standards
Standard
Guidance
Controllers contain no business logic
A controller's only job is marshaling — parse request, call a service method, marshal response. If a controller has an if/else branching on business state, that logic belongs in services/
Repositories never calculate
A repository returns rows or writes rows. Any derived value, sum, or conditional transformation belongs in services/, not repositories/
Services never know SQL
A service calls a repository method by name (e.g. findActiveByCustomer) and never constructs or sees a query string
No SQL in controllers
The strongest form of the above two — enforced by code review, not just convention
UTC everywhere
Every timestamp stored, transmitted, or logged is UTC; timezone conversion happens only at the final presentation layer (BIS-006)
ISO-8601 timestamps
No epoch integers, no locale-formatted strings in any API response or stored field
UUID primary keys
Every table's primary key is a UUID, matching every schema already specified across BIS-001 through FIE-005 — never an auto-incrementing integer, which would leak sequence information across tenants
Environment-driven configuration
No hardcoded connection strings, feature flags, or thresholds in code — every configurable value (Section 25/26-style config tables already specified per service) is environment-injected
Feature flags
Any behavior change that could affect a live customer (e.g. Section 18 of FIE-BUILD-001's per-customer cutover flag) is flag-gated, never a direct code branch on environment name
Dependency injection
Services receive their repository and client dependencies through constructor injection, never through direct instantiation or global singletons — this is what makes contract testing with mocked dependencies possible
Consistent error handling
Every service uses the same standard error envelope (Section 6) and the same EIS-001 error code taxonomy extended per service, never a locally invented error shape

Section 7 — Event Standards
Every platform event, regardless of producer, shares one envelope. The tenant-scoping field is named customer_id, matching the API envelope (Section 6), logging fields (Section 11), and database standards (Section 8) exactly — there is no separate tenant_id concept anywhere in this platform; using a different name for the same scoping concept in one layer is exactly the kind of silent drift Section 5's naming conventions exist to prevent.
{  "event_id": "UUID",  "event_type": "string",  "correlation_id": "UUID",  "customer_id": "UUID",  "producer": "string  (e.g. \"fie-003-calculation\")",  "timestamp": "ISO-8601 UTC",  "schema_version": "integer",  "payload": {}}
Retry philosophy: a consumer that fails processing an event retries with exponential backoff up to a configured limit before routing to a dead-letter queue — never silently drops an event
Dead-letter philosophy: a dead-lettered event is never discarded; it is retained and alertable, per Section 11's observability standards, and requires explicit human triage before replay or discard
Idempotency: every event consumer is written assuming at-least-once delivery — processing the same event_id twice must be a safe no-op, verified by a dedicated idempotency test per consumer
schema_version exists specifically so a consumer can reject or branch on an event shape it doesn't yet understand, rather than crash on an unexpected payload shape
Section 8 — Database Standards
Standard
Guidance
Migration strategy
Forward-only, versioned migrations; no migration is ever edited after it has run in any environment — a correction is a new migration
Indexes
Every foreign key column is indexed; every field appearing in a documented Query Pattern (per each service's own Query Patterns section) has a supporting index before that endpoint ships
Foreign keys
Declared at the schema level wherever one table references another within the same service; cross-service references are UUIDs with no database-level FK, since no service's database may directly reference another service's tables
Version columns
Every versioned entity (Section 1's 'Version Everything') carries an explicit integer version column, never inferred from row order or timestamp alone
Audit fields
created_at on every table, minimum; created_by/actor fields wherever a human or agent action produced the row
Soft delete policy
There is no soft-delete flag anywhere in this platform's core financial data model — records are archived (a status/lifecycle field, per FIE-004 §19's pattern) or superseded (a new version), never marked deleted, since deletion of financial history is not a concept this architecture supports
Append-only policy
No UPDATE grant exists on value, confidence, or timestamp columns for any row that has left DRAFT-equivalent status, enforced at the database permission layer wherever the underlying database supports it, not only at the application layer
Partitioning guidance
High-volume time-series tables (FIE-001 temporal_records, FIE-003 financial_intelligence_objects) are partitioned by customer_id and a time dimension (business_effective_date month), per FIE-001 §25's own partitioning guidance — apply the same pattern to any future table exceeding comparable volume

Section 9 — Performance Standards
Batch reads: every read of more than a handful of records uses a bulk-paginated endpoint (the pattern established by BIS-003/004 and reused by every FIE service) — never an N+1 loop of single-record calls
Streaming writes: high-volume ingestion (e.g. a large CSV upload) streams rows through validation and canonical write rather than loading the entire file into memory first
Caching: read-through caches are permitted only where a service's own spec explicitly allows one (e.g. FIE-002 §24's methodology resolution cache) and must implement the invalidation rule that spec defines — never a generic cache-everything default
Avoid N+1 queries: any code path issuing one query per item in a loop is a blocking review comment, not a performance nice-to-have
Pagination: every list-shaped response is paginated by default, even where present volume is low — this is a standard, not a scale-triggered optimization
Async jobs: any operation exceeding roughly one second of synchronous work is dispatched as a job (per EIS-002's worker pattern), never held open on a synchronous request
Concurrency: parallel execution (e.g. FIE-003's Graph Executor) respects each service's own documented concurrency ceiling — never unbounded parallelism against shared resources
Queue usage: every async job is dispatched through the standard job queue (BIS-002's dispatch model), never a service-specific ad hoc queue
Expected latency goals: every service's own Performance Targets section is the authoritative per-endpoint SLA; FIE-BUILD-001's Performance Targets section is the directional, platform-level goal — engineers build to the per-service spec, not the directional goal
Section 10 — Security Standards
Tenant isolation: customer_id scoping on every table and every query, with no code path capable of a cross-tenant read, verified by a dedicated cross-tenant-isolation test per service
RBAC: role checks are declarative (a decorator or middleware, not inline conditional checks scattered through business logic), matching each service's own documented role requirements (e.g. FIE-002 Addendum A's elevated approver role)
Least privilege: a service's database credentials grant only the tables and operations that service actually needs — no service's credentials span another service's schema
Secret management: no secret (API key, credential, connection string) is ever committed to a repository; all secrets are injected through the platform's secret manager at deploy time
Audit logging: every write to a governed entity (methodology approval, restatement approval, promotion decision) logs actor, timestamp, and decision, matching each service's own Logging section
Encryption: data at rest encrypted everywhere, matching every service's own stated Security section
Administrative actions: any action reachable only by an elevated role (BIS-005 promotion approval, FIE-002 Addendum A restatement approval) is logged with the same rigor as a customer-facing write, not treated as a lower-scrutiny internal action
Operational logging: infrastructure-level logs (deploys, config changes, scaling events) are kept separate from application audit logs, but both are retained per the platform's retention policy
ASSUMED  POC-stage exception: FIE-BUILD-001 §12 permits auto-approve for BIS-005 knowledge promotion during POC to avoid building a full review UI before it's needed. Any such bypass must be feature-flagged and explicitly labeled temporary in code and configuration — it must never become the default production behavior by omission, and the flag must default to full governance review in any environment beyond the specific POC customer set it was scoped for.
Section 11 — Observability Standards
Health endpoints: every service exposes GET /v1/health, per the pattern already specified in every BIS/FIE document's own API section
Readiness endpoints: distinct from health — readiness reflects whether the service can currently accept traffic (e.g. database connection established), health reflects whether the process is alive at all
Structured logging: every log line is structured JSON with the standard field set (request_id, customer_id, actor_type, actor_id, timestamp, plus service-specific fields already named in each service's own Logging section) — never unstructured free text
Distributed tracing: a trace ID propagates across every service boundary a single customer-facing request touches, so a slow narrative generation can be traced back through FIE-005 → FIE-003 → FIE-002 → FIE-001 → BIS-003 in one view
Metrics: every service exposes the Prometheus-style metrics already specified in its own Metrics section — this playbook adds no new metric, only the requirement that they exist and are scraped consistently
Audit events: governed decisions (Section 10) additionally emit a platform event, not only a log line, so downstream systems (e.g. FIE-004's Decision Memory) can react to them
Queue metrics: queue depth, processing latency, and dead-letter rate are tracked for every async job type, per Section 7
Performance metrics: p50/p95/p99 latency tracked per endpoint, compared against each service's own Performance Targets section
Dashboards: one dashboard per service, minimum, following the Dashboards subsection already specified in every service's own Observability section
Alert philosophy: alert on symptoms a human needs to act on (failure rate spikes, SLA breaches, dead-letter growth), not on every possible metric crossing an arbitrary threshold — alert fatigue is itself an observability failure

Environment
Purpose
Development
Local or shared dev environment; fixture data only, never real customer data
QA
Automated test execution environment; fixture and synthetic data
Staging
Production-like environment for pre-release validation; may include anonymized or design-partner data with explicit consent
Production

Section 14 — Engineering Anti-Patterns
Never
Why It's Dangerous
Bypass Canonical
Breaks Canonical Convergence — the single property (ABS-012 §2, §11) that lets every downstream service and every ingestion path work without knowing about each other. One bypass reintroduces exactly the fragmentation the whole architecture exists to prevent
Duplicate financial values
Creates two systems of record for the same fact — the specific failure mode this platform's own review process caught and fixed repeatedly (FIE-002 §1.1, FIE-004 §8). Two copies eventually disagree, and nobody can tell which one is right
Mutate immutable objects
Breaks reproducibility (Deterministic Core) and auditability (Explainability) simultaneously — a value that changed silently can never again be trusted as a historical fact
Store derived values as authoritative
This is exactly the mistake the existing prototype warehouse made (ABS-012 §10) — aggregate tables became the source of truth instead of a derived view, and the result had no canonical history underneath it to migrate from
Bypass Validation
Publishes unverified data into a platform whose entire premise (Section 18 of FIE-BUILD-001, Product Acceptance Criteria) is that every number can be trusted and explained
Calculate inside Reporting
Violates the content/presentation boundary (FIE-005 §1.5, BIS-006 §1) — Reporting renders, it does not compute; a calculation done there has no lineage, no confidence, and no place in the Explainability chain
Use AI inside deterministic execution
Breaks FIE-003's determinism guarantee at its root — the entire point of separating Calculation from Reasoning (Section 1's Deterministic Core / AI Never Changes Numbers) is to keep the one place numbers are computed free of model non-determinism
Publish without Verification
Defeats the platform's central trust premise before a customer ever sees the consequence — FIE-005 §1.10's fail-closed rule exists specifically to make this impossible, not just discouraged
Skip lineage
An unexplainable number is, per this platform's own Product Acceptance Criteria, not a shippable number — lineage is not a nice-to-have field, it's the mechanism the entire Explainability principle depends on
Skip confidence propagation
Silently makes a result look more trustworthy than its weakest input — the minimum-across-inputs rule (FIE-003 §1.8, FIE-005 §19) exists precisely to prevent this
Skip Orchestration
Reintroduces a second scheduling/dispatch mechanism outside BIS-002's ownership — every service that has needed to trigger work has deferred to Orchestration for exactly this reason (BIS-004 §1.8, FIE-001 §1.7, FIE-003's job-triggered model)

Dependency Direction Rules
Section 15's stack implies a strict direction. Made explicit here as engineering guardrails, not assumptions an engineer has to infer from the diagram:
Higher-level services may consume lower-level services. A service anywhere in the Section 15 stack may call any service below it
Lower-level services never depend upon higher-level services. Canonical does not call Observation; Observation does not call Methodology; and so on up the stack — a dependency arrow only ever points downward
Circular dependencies are prohibited, full stop. If two services appear to need each other, the design is wrong and one direction needs to be inverted or a third, lower-level service needs to own the shared concern
Services communicate only through published contracts (Section 2's shared/contracts) — never through direct database access to another service's schema, and never through an undocumented internal call
Reporting never performs calculations. It renders and exports FIE-005 content and FIE-003 FIOs; any number appearing in a report was computed upstream
Calculation never depends upon Reporting. FIE-003 has no code path that calls, imports from, or is aware of BIS-006's existence
Memory never recalculates Financial Intelligence Objects. FIE-004 references FIE-003 output by ID; it has no execution engine of its own
Reasoning never modifies Memory directly. FIE-005 creates Knowledge Objects exclusively through FIE-004's own governed API, never through a direct write
Service boundaries must remain intact even under schedule pressure. A shortcut that reaches across a boundary to save time is the single most common source of the anti-patterns in Section 14, and is never an acceptable tradeoff for a deadline
Section 16 — Confidence Standards
Confidence never disappears — every value that has confidence at capture retains it through every downstream transformation that references it
Confidence always carries lineage — a confidence value is meaningless without the reference back to what produced it; never store a bare confidence number with no traceable origin
Confidence explains origin — which of the four dimensions (Mapping, Data, Reasoning, Knowledge) is limiting a result, not just an aggregate score
Confidence explains timestamp — confidence is fixed at the moment it was assigned and never silently recalculated as if it were current
Confidence explains dependencies — a combined value's confidence names which inputs it took the minimum across (FIE-003 §1.8, FIE-005 §19)
Confidence explains calculation — the combination rule applied (minimum-across-inputs) is documented and consistent everywhere it's used, never reinvented per service

Repository Pattern
class TemporalRecordRepository:  function findByFinancialConcept(customer_id, concept_id, date_range):    return db.query(      table: temporal_records,      where: customer_id = customer_id        and financial_concept_id = concept_id        and business_effective_date within date_range,      order_by: business_effective_date    )  // No calculation. No business rule. Returns rows or nothing.
Service Pattern
class ObservationService:  constructor(repository: TemporalRecordRepository, canonicalClient: CanonicalClient):    this.repository = repository    this.canonicalClient = canonicalClient  // dependency injection — no direct instantiation, no global singleton  function captureObservation(request):    canonicalData = this.canonicalClient.bulkRead(request.scope)    observation = buildImmutableObservation(canonicalData, request.confidence_context)    return this.repository.insert(observation)    // business logic lives here — never in the repository or controller
Event Publishing
function publishEvent(event_type, payload, correlation_id, customer_id):  envelope = {    event_id: generateUUID(),    event_type: event_type,    correlation_id: correlation_id,    customer_id: customer_id,    producer: SERVICE_NAME,    timestamp: nowUTC_ISO8601(),    schema_version: CURRENT_SCHEMA_VERSION,    payload: payload  }  queue.publish(envelope)  // every event, every service, this exact shape — Section 7. customer_id, never tenant_id.
Job Handler
class GraphExecutorWorker:  function handle(job):    plan = executionPlanRepository.get(job.execution_plan_id)    for group in plan.parallel_groups:      results = executeConcurrently(group, maxConcurrency: profileConcurrencyLimit(job.calculation_profile))      persistResults(results)  // each result its own immutable FIO    markJobStatus(job, deriveOverallStatus(results))  // COMPLETE | PARTIAL | FAILED, never silently downgraded
API Controller
function postReasoningPackage(request):  validateSchema(request)              // api/ layer only  authCheck(request.caller, request.customer_id)  result = reasoningService.createPackage(request.body)   // delegate immediately  return standardEnvelope(status: SUCCESS, data: result)  // no branching on business state here — that's the service's job
Contract Validation
function validateAgainstContract(payload, contract_version):  schema = contractRegistry.get(SERVICE_NAME, contract_version)  errors = schema.validate(payload)  if errors.length > 0:    return INVALID_INPUT(errors)  return VALID  // contracts live in shared/contracts — never redefined locally per Section 2
Dependency Injection
class Application:  function wire():    repository = new TemporalRecordRepository(db)    canonicalClient = new CanonicalClient(config.canonical_base_url)    service = new ObservationService(repository, canonicalClient)    controller = new ObservationController(service)    return controller  // every dependency constructed once, injected explicitly — no global state, per Section 5

Final Engineering Review
Reviewed as a Principal Software Architect preparing a multi-team engineering organization to build against this playbook and FIE-BUILD-001 together, after incorporating two rounds of external review (Cursor's issue list and a structural revision pass).
Remaining Implementation Risks
The append-only, no-UPDATE-grant database discipline (Section 8) is easy to state and easy to violate under deadline pressure — the single highest-value automated guardrail this platform could add is a CI check that fails a migration granting UPDATE on a column this playbook or an owning spec has marked immutable
Multi-language implementation (Appendix C's deliberate language-agnosticism) means the standard response envelope, error taxonomy, and event envelope must be enforced by shared contract libraries per language, not by convention alone — if two languages end up with two subtly different envelope implementations, Section 6/7's consistency promise quietly breaks
FIE-003 and FIE-005's Very High complexity rating (FIE-BUILD-001's Complexity Assessment) means this playbook's standard build sequence (Section 4) will likely need the most deviation for exactly those two services — plan for that explicitly rather than being surprised by it
Recommended Future BUILD Documents
Formalized above in the BUILD Series Roadmap — FIE-BUILD-003 (CI/CD & Automated Governance) is the nearest-term recommendation, since it directly closes this section's first Remaining Implementation Risk. FIE-BUILD-004 through 008 are real but not urgent; none blocks using this playbook today.
