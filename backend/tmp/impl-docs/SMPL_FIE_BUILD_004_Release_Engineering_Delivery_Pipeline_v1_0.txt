Purpose and Authority
FIE-BUILD-001 established what gets built. FIE-BUILD-002 established how engineers build each service. FIE-BUILD-003 established how those services integrate into one deployable platform. This document establishes how a change moves, safely and auditably, from a developer's first commit to a real customer's production environment. It redesigns nothing — ABS, BIS, FIE, and BUILD-001 through BUILD-003 remain frozen and authoritative; every mechanism here operationalizes a principle one of them already established (determinism, immutability, fail-closed verification, customer trust) rather than inventing a new one.

Section 7 — Database Migration Strategy
Forward-only migrations — no migration is ever edited after running in any environment, per FIE-BUILD-002 §8; a correction is a new migration
Append-only architecture — no migration ever adds an UPDATE/DELETE grant on a column this platform's own architecture has marked immutable (FIE-BUILD-002 §8, §14's 'Mutate immutable objects' anti-pattern)
Idempotent migrations — safely re-runnable without duplicating effect, verified by a dedicated test per migration
Safe retries — a migration interrupted mid-run can be safely re-attempted from the beginning without corrupting state
Online migrations — no migration locks a production table for longer than a documented, reviewed threshold; large-table changes use batching (below) instead
Large-table batching — a migration touching a high-volume table (FIE-001 temporal_records, FIE-003 financial_intelligence_objects) runs in bounded batches with progress checkpointing, never a single long-running transaction
Roll-forward philosophy — the default response to a migration problem discovered post-deploy is a corrective forward migration, not a destructive rollback, consistent with this platform's universal append-only discipline
Rollback guidance — where a true schema rollback is unavoidable (e.g. a migration that hasn't yet been used by any written data), it is documented and tested before the forward migration ships, never improvised after the fact
Customer migration sequencing — a migration affecting customer-visible behavior is sequenced against Section 16's customer release strategy, never applied to all customers simultaneously by default
Section 8 — Feature Flag Governance
OFF     ↓Internal              (engineering-only visibility)     ↓Design Partners        (opt-in, consented data per FIE-BUILD-003 §2)     ↓Pilot Customers     ↓General Availability     ↓Platform Standard      (flag retired — behavior is now unconditional)
Feature flags are retired, not accumulated. A flag that has been at Platform Standard for a defined grace period is removed from the codebase entirely — permanent feature flags are themselves a form of undocumented architecture, and this platform does not carry undocumented architecture anywhere else, per FIE-BUILD-002's Engineering Decision Records discipline. Every flag has a named owner (Section 14) responsible for both its rollout and its eventual retirement.
Section 9 — Release Promotion
Development     ↓QA     ↓Integration     ↓Staging     ↓Pilot            (a small, named subset of production customers — new relative to FIE-BUILD-003 §2's five environments)     ↓Production
ASSUMED  Pilot is a release-engineering concept layered on top of FIE-BUILD-003 §2's Production environment, not a sixth physical environment — it is a subset of real production customers (Section 16's Pilot Customers stage) receiving a release before General Availability, running on the same infrastructure FIE-BUILD-003 §2 already describes. FIE-BUILD-003 §2 remains the authoritative environment list; this section adds a customer-cohort dimension within its Production tier.
Promotion to each stage requires certification from the previous stage — a release does not skip from Integration to Staging without Integration's own gates (Section 5) passing, and does not reach Production without Staging's certification (Section 11) and, for anything customer-visible, at least a Pilot cohort's worth of real-world validation.
Section 10 — Backward Compatibility
Compatibility Type
Expectation
API compatibility
A previous API version continues to be served for at least one deprecation window after a new version ships, per FIE-BUILD-002 §6
Event compatibility
schema_version (FIE-BUILD-002 §7) allows a consumer to detect and reject or branch on a shape it doesn't understand — never a silent break
Schema compatibility
A migration never removes a column or table a still-deployed prior service version reads, until that version is fully retired
Contract compatibility
shared/contracts (FIE-BUILD-002 §2) versions independently of the service implementing them
Registry compatibility
A new Business Theme, Narrative Policy, or Industry Template version never invalidates a reference to a prior version — append-only, per every owning spec
Configuration compatibility
A new configuration key ships with a default that preserves prior behavior; removing a key follows the same deprecation window as an API
Customer compatibility
A customer's existing Methodology, Operating Model, and Narrative Policy continue to resolve correctly across a platform release unless they explicitly opt into a new version
No breaking change ships without an explicit version increment, per Section 6 — this is the release-engineering enforcement of FIE-BUILD-002 §6's versioning standard, not a new rule.

Section 12 — Rollback Strategy
Feature Flag           (fastest — toggle off, no redeploy)     ↓Service Rollback        (redeploy prior version of one service)     ↓Release Rollback        (redeploy prior version of the full release)     ↓Database Mitigation     (roll-forward corrective migration, per Section 7 — never a destructive schema rollback against live data)     ↓Customer Rollback       (per-customer cutover flag reverted, per FIE-BUILD-001 §18 / FIE-BUILD-003 §8)     ↓Platform Recovery       (disaster recovery procedures, per FIE-BUILD-003 §11 — the last resort)
This hierarchy is ordered fastest-and-narrowest to slowest-and-broadest. Every production release demonstrates at least the top two tiers' rollback capability before Section 11 certification is granted — a release nobody has verified can be flagged off or redeployed backward is not a certified release, regardless of how confident the team is in the forward path.

Section 16 — Customer Release Strategy
Internal     ↓Design Partners     ↓Pilot Customers        (Section 9's Pilot stage)     ↓Early Access     ↓General Availability     ↓Platform Standard
Feature flags (Section 8) support gradual customer adoption at every stage above. A release is customer-safe by construction when tenant isolation (FIE-BUILD-002 §10) guarantees one customer's flag state has no effect on another's — this is what makes Pilot a meaningful stage rather than a formality: a Pilot customer genuinely runs different code than a General Availability customer, safely, at the same time, on the same infrastructure.
Section 17 — Emergency Releases
Critical Issue     ↓Hotfix Branch          (cut from the current production tag, per Section 3)     ↓Targeted Testing        (the specific fix and its immediate blast radius, not the full Testing Pyramid)     ↓Architecture Validation  (never skipped, even under emergency pressure)     ↓Production     ↓Post-Incident Review     ↓Merge Back to Main
An emergency release compresses Section 2's lifecycle, it does not bypass Section 5's Architecture Compliance gate — the one gate this document treats as truly non-negotiable even under incident pressure, since an architecturally-unsound hotfix trades a customer-visible incident for a harder-to-detect structural one. Every emergency release requires a Post-Incident Review before it is considered closed, and its fix is merged back to main promptly so the hotfix branch does not silently diverge from the ongoing release train (Release Trains, below).

Release Trains
Continuous feature deployment (per-PR release candidates, Section 4) and a release cadence are not mutually exclusive — release candidates are built continuously; promotion to Production follows a train schedule.
Cadence
Use Case
Tradeoff

Bug fixes, small non-breaking improvements
Fast feedback, but too frequent for customers who need advance notice of any change
Monthly Feature Releases

Architecture Compliance Automation
The Architecture Validation stage in Sections 2 and 4 is not a single generic check — it is a specific, growing set of automated rules, each one a mechanical version of an anti-pattern FIE-BUILD-002 §14 already named in prose.
Automated Rule
Prevents (FIE-BUILD-002 §14 / Dependency Direction Rules)
No dependency direction violations
A lower-level service importing from or calling a higher-level one
No duplicate domain ownership
Two services independently storing the same fact — the Reference Instead of Copy principle, checked mechanically via schema/field naming conventions
No direct connector access outside BIS-001
'Bypass Canonical' — any service other than BIS-001 importing a connector SDK or credential
No non-deterministic execution within FIE-003
A wall-clock call, random seed, or LLM invocation appearing inside FIE-003's Graph Executor or Execution Planner code paths
No prohibited cross-service references
A service importing another service's internal (non-contracts/) module directly, bypassing shared/contracts
The objective stated plainly: architecture becomes executable engineering policy, not just a document a reviewer has to remember to check against. Every rule here should have a corresponding, specific test — 'no non-deterministic execution within FIE-003,' for instance, is enforceable by static analysis flagging any wall-clock or randomness API call inside that service's package boundary.
Customer-Safe Releases
Can this feature be safely enabled for one customer without affecting every other customer? If the answer is no, the release does not proceed.
This is the single question every release answers before Production, and it is answerable concretely, not rhetorically, because of three mechanisms this document and its predecessors already establish:
Feature flags (Section 8) — a new behavior can be enabled for exactly one customer cohort without a code branch per customer
Tenant isolation (FIE-BUILD-002 §10) — a flag enabled for one customer_id has no code path capable of affecting another's data or behavior
Staged rollout (Section 16) — Pilot Customers validate a release against real, consenting customers before General Availability, so the answer to the question above is empirically tested, not just architecturally asserted
A release that cannot honestly answer this question yes should not proceed to Production, regardless of Section 5's other gates passing — this is the release-engineering restatement of FIE-BUILD-003 §14's customer acceptance questions, checked one release earlier than a customer ever sees the result.

1. Are There Remaining Release Engineering Gaps?
No blockers. Two items are named rather than silently assumed: the specific static-analysis tooling behind Architecture Compliance Automation is left to the implementing team's language choice (consistent with FIE-BUILD-002's language-agnostic stance), and Section 9's Pilot stage is explicitly marked as layered on FIE-BUILD-003's existing environment list rather than a sixth physical environment, so the two documents don't quietly diverge on how many environments actually exist.
2. Should Any Recommendations Become Future BUILD Documents Instead?
Detailed on-call rotation, incident severity classification, and runbook content beyond Section 17's emergency release process belong in FIE-BUILD-005 Production Operations, per the authoritative roadmap
Formal compliance certification (SOC 2, ISO, or similar) referenced implicitly by Section 11's Security Review belongs in FIE-BUILD-007 Security, Compliance & Governance, not as an expansion of this document's Release Certification
Nothing else in this document's scope is misplaced — release engineering is a cohesive enough domain that it holds together as one document, per the same judgment FIE-BUILD-003 made for platform integration
3. Is FIE-BUILD-004 Ready to Become the Authoritative Release Engineering Handbook?
Yes. Every one of the twenty required sections plus all three additional recommendations are present, every mechanism traces back to a specific principle already established in ABS/BIS/FIE or a prior BUILD document, and the one naming variance against the roadmap is named explicitly with a low-urgency fix rather than either ignored or treated as a reason to reopen a frozen document. Recommend freezing FIE-BUILD-004 and proceeding to FIE-BUILD-005 (Production Operations) per the authoritative roadmap.
