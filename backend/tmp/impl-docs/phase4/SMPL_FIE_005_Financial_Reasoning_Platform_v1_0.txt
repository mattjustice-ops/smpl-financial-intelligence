Section 1 — Scope Decisions
The FIE-005 conceptual model is frozen and is not redesigned here. This section restates its Section 1 Architectural Reconciliation in the numbered format used since BIS-001, and adds five further resolutions the build requires — most importantly, giving Financial Findings and Business Insights the independent, addressable identity the conceptual review's final round established, without disturbing anything else in the frozen model.
1.1 Financial Reasoning vs. Observation Engine
The Observation Engine (FIE-001) owns immutable financial facts. This service consumes Observation Snapshots and Revisions through FIE-001's existing timeline API and never creates, corrects, or writes an Observation or Revision of its own.
1.2 Financial Reasoning vs. Methodology Engine
The Methodology Engine (FIE-002) owns financial definitions. This service resolves and consumes Methodologies, Formulas, and Drivers through FIE-002's existing resolution API and never creates or modifies a methodology, formula, or driver definition.
1.3 Financial Reasoning vs. Calculation Engine
The Calculation Engine (FIE-003) owns deterministic execution and produces Financial Intelligence Objects. This service consumes FIOs — including their full lineage and Financial Evidence (FIE-003 §1.7) — and never recalculates a financial value or writes to any FIE-003 table.
1.4 Financial Reasoning vs. Organizational Memory (FIE-004)
FIE-004 preserves organizational knowledge; this service reasons over it. This service never writes directly to a FIE-004 Knowledge Object. Every durable conclusion this service produces — a Recommendation Candidate always, a Financial Finding or Business Insight when explicitly promoted (Section 13) — enters FIE-004 exclusively through FIE-004's own governed POST /v1/knowledge-objects workflow, never through a direct table write or an assumed side channel.
1.5 Financial Reasoning vs. Reporting Platform (BIS-006)
This service supplies content — Reasoning Packages and Narrative Objects. BIS-006 supplies presentation — report assembly, PDF/DOCX/PPTX rendering, board package production, exactly the boundary BIS-006 §1 already draws against Canonical, Validation, and CAL. A Narrative Object is a first-class content object this service owns; a rendered board deck containing it is a BIS-006 report_artifact (BIS-006 §7) that references it. Additionally, this service inherits BIS-006 §17's Narrative Generation Rules as its own foundation rather than re-deriving equivalent rules independently — never fabricate a missing result, never suppress a blocker, always cite evidence, label estimates clearly — since FIE-005 is functionally the generalization of narrative generation from the implementation domain (BIS-006) to the financial domain, and the two should not develop divergent narrative-safety rules.
1.6 The Explainability Platform Is Not Owned by This Service
Financial Explainability — Data Lineage, Calculation Lineage, Business Context, Confidence Context, and Financial Tie-Out — is a shared platform capability this service consumes, not a component this service builds or owns. This is a deliberate architectural position, not a deferred decision: every fact Explainability surfaces already has a system of record (FIE-001 for data lineage, FIE-003 §1.7 for calculation lineage and evidence, FIE-004 for business context, FIE-001/003/004 for the three-plus-one confidence dimensions, BIS-006 §18 for the general evidence-attribution pattern this generalizes). Building Explainability inside this service would duplicate all four. Section 15 defines the interface contract this service requires from Explainability and how MVP satisfies it before a dedicated Explainability service exists.
1.7 Inherited Limitation from FIE-003/FIE-004
Per FIE-004 §1.6, which itself restated FIE-003 §1.9: Governed execution's full historical restatement remains dependent on a FIE-002 addendum that does not yet exist. This service inherits that limitation a second time and, per the pattern both prior documents established, restates rather than rediscovers it: Question Understanding (Section 8) classifies every question as either a current-understanding question (answerable from live FIE-003 execution and FIE-004 knowledge) or a historical-understanding question (answerable only from what FIE-004 preserved at the time, per FIE-004 §1.6). A historical-understanding question that would require unavailable restatement returns its answer grounded in preserved organizational knowledge and explicitly labels it as such — it never silently presents a preserved belief as if it were a live recalculation, and never attempts the recalculation and fails partway through.
1.8 New Resolution — Financial Findings and Business Insights Are Independently Addressable, FIE-005-Scoped Objects
Per the conceptual review's final resolution: Findings and Insights are not trapped inside a Reasoning Package's private structure. Each is its own immutable, versioned row with a stable finding_id or insight_id (Section 11–12) from the moment it is created — addressable, referenceable, and reusable across Reasoning Packages — but remains entirely FIE-005-scoped and invisible to the rest of the platform unless explicitly promoted. This resolves the tension the conceptual model left unstated: a Narrative Object's "Financial Finding References" field (Section 17) requires something stable to reference, which a Finding buried inside a Reasoning Package's internal structure cannot provide. Addressability and promotion are two independent properties — a Finding can be permanently addressable within FIE-005 and never once become FIE-004 organizational memory.
1.9 New Resolution — Recommendation Candidates and Findings Follow Deliberately Different Tracks
This is a stated asymmetry, not an oversight. A Recommendation Candidate has no FIE-005-local existence at all — per Section 1.4 and the conceptual model, it is created directly via FIE-004's Knowledge Object API and this service stores nothing beyond a reference to the resulting knowledge_object_id (Section 13). A Finding or Insight, by contrast, is always FIE-005-local first (Section 1.8) and promoted to FIE-004 only as an explicit, separate second step (Section 13). The asymmetry reflects a real difference in stakes: a Recommendation suggests action and carries governance weight from the moment it exists, warranting FIE-004's audit trail immediately; a Finding is an observational conclusion that may never need to leave this service's own store.
1.10 New Resolution — Verification Fails Closed; Draft Mode Is the Only Exception
Per the conceptual model: Verification fails closed by default, and Narrative publication is blocked on failure unless the request explicitly specifies Draft Mode. This document makes the consequence concrete: a Narrative Object generated under a failed Verification always persists with lifecycle_state=DRAFT and a non-null verification_failure_reason (Section 17); it can never transition to PUBLISHED (Section 20) while that failure reason remains unresolved, regardless of caller intent. Draft Mode exists for internal review and iteration, never as a route to publishing an unverified conclusion — there is no API path that both requests Draft Mode and requests publication in the same call.
1.11 New Resolution — Explainability Interface Contract and Interim Adapter
Per Section 1.6, this service does not own Explainability, but it cannot function without it, and no dedicated Explainability service exists yet to depend on. This document therefore specifies the interface contract this service requires — five read operations: resolve_data_lineage, resolve_calculation_lineage, resolve_business_context, resolve_confidence_context, resolve_tie_out (Section 15) — and satisfies it at MVP through an internal Explainability Adapter component (Section 6) that implements this exact contract by calling FIE-001, FIE-003, FIE-004, and BIS-006 directly. When a dedicated, shared Explainability service is built, this service's Verification and Narrative Generation components change nothing about how they call the adapter — only the adapter's internal implementation is replaced, never the contract.

Section 8 — Question Understanding and Evidence Planning
Question Understanding classifies incoming intent into a controlled taxonomy (VARIANCE_ANALYSIS, BOARD_COMMENTARY, FORECAST_REVIEW, CASH_ANALYSIS, RISK_REVIEW, PIPELINE_REVIEW, EXECUTIVE_SUMMARY, RECOMMENDATION_REQUEST) and assigns understanding_mode (CURRENT or HISTORICAL, per Section 1.7). Evidence Planning then determines the specific evidence types required for that classification — Observation Snapshots, FIOs, Methodology versions, Knowledge Objects, and so on — without retrieving anything or drawing any conclusion. Both steps are deterministic given the same classified intent; neither invokes the Financial Reasoning Engine.
Section 9 — Evidence Assembly
Retrieves exactly what Evidence Planning specified, from FIE-001's timeline API, FIE-002's methodology resolution API, FIE-003's FIO and evidence APIs, and FIE-004's knowledge query API. Assembly performs no filtering for relevance beyond what was planned and draws no conclusions; an assembly that cannot satisfy the Evidence Plan returns status=INSUFFICIENT_EVIDENCE on the Reasoning Package (Table FIE5-7.1) rather than proceeding with a partial evidence set silently.
Section 10 — Financial Reasoning Engine
The only component permitted to produce a Financial Finding, Business Insight, or Recommendation Candidate. It consumes exclusively the evidence Section 9 assembled — never a live call back to FIE-001 through FIE-004 mid-reasoning — which is what makes a Reasoning Package's output reproducible given the same evidence_refs. Its output is written as new financial_findings and business_insights rows (Section 11–12) and, where applicable, an immediate FIE-004 Recommendation Candidate call (Section 13); the reasoning_packages row itself stores only references to all three, never their content.
Section 11 — Financial Finding Model
A Finding is an objective, evidence-traced conclusion — "enterprise pipeline conversion decreased" — never an interpretation. Its supporting_evidence_refs must resolve through the Explainability Adapter (Section 15) before the Finding can be persisted; a Finding whose evidence cannot be resolved is not written at all, consistent with Section 1.6's fail-closed philosophy applied at creation as well as at Verification. Findings are reusable: a second Reasoning Package covering the same period and concept resolves to the same finding_id rather than creating a duplicate, checked by a straightforward lookup on (customer_id, statement_hash, evidence_refs) before creating a new one.
Section 12 — Business Insight Model
An Insight interprets one or more Findings — "enterprise capacity constraints are reducing conversion" — and always carries interpreted_finding_ids rather than re-deriving supporting evidence independently. This is the structural rule that keeps Findings and Insights genuinely distinct rather than two names for the same thing: a Finding never references another Finding; an Insight always references at least one.
Section 13 — Recommendation, Finding, and Insight Promotion
Per Section 1.9's stated asymmetry: a Recommendation Candidate is created directly via a call to FIE-004's POST /v1/knowledge-objects (knowledge_type=RECOMMENDATION_CANDIDATE) the moment the Financial Reasoning Engine produces it — this service stores only the resulting fie004_knowledge_object_id reference in reasoning_packages.recommendation_candidate_refs, never a local Recommendation row. A Finding or Insight, by contrast, exists locally first and is promoted only via an explicit call to Table FIE5-4.3, which itself calls FIE-004's own knowledge-object API — this service never writes to a FIE-004 table directly under any circumstance, for Recommendations or for promoted Findings/Insights alike.
Section 14 — Verification
Before a Narrative Object can reach verification_status=PASSED, the Verification Engine confirms, via the Explainability Adapter (Section 15): every referenced Finding/Insight/FIO/Knowledge Object resolves; every financial value reconciles through Financial Tie-Out; every confidence dimension meets the customer's configured threshold; no two referenced Findings contradict one another. Any single failure sets verification_status=FAILED with a specific verification_failure_reason and, per Section 1.10, blocks Table FIE5-4.4's publish endpoint unconditionally — there is no override path, only correcting the underlying evidence gap and generating a new narrative_version.

Section 16 — Narrative Generation
Renders a Reasoning Package into a Narrative Object for a specific audience by resolving the requested audience to an active narrative_policy_id/version (Table FIE5-7.5) and generating content through the LLM runtime under BIS-006 §17's inherited Narrative Generation Rules (Section 1.5). Generation always runs before Verification, never after — a Narrative Object is created with verification_status determined by Section 14's check performed against its actual generated content, never a pre-check against the Reasoning Package alone.
Section 17 — Narrative Object Model
Implements Table FIE5-7.4 exactly: immutable content, version, and four-dimensional confidence; independently transitioning lifecycle_state. A Narrative Object always references a specific reasoning_package_id and specific finding_refs/insight_refs — never a copy of Finding or Insight content — so that a later correction to an underlying Finding (via a new finding_version) is visible through the reference without requiring the Narrative to regenerate, though Section 20 governs whether such drift triggers a recommended regeneration.
Section 18 — Narrative Policy Model
A Narrative Policy governs tone, length, terminology, and formatting only — presentation_rules never contains a reasoning rule, a confidence threshold, or an evidence requirement, all of which are fixed platform-wide by Sections 10 and 14 regardless of audience. This is the schema-level enforcement of the conceptual model's principle that "only presentation changes; reasoning never changes" — there is no field in narrative_policies capable of altering what a Narrative is permitted to claim.
Section 19 — Four-Dimensional Confidence Propagation
Findings, Insights, and Narratives all carry Mapping, Data, Reasoning, and Knowledge Confidence as four separate fields, never collapsed into one score, per the frozen model. Combination follows FIE-003 §1.8's minimum-across-inputs rule, extended with a fourth dimension: a Finding drawing on an FIO (Mapping/Data/Reasoning populated) and a FIE-004 Knowledge Object (Knowledge Confidence populated) takes the minimum across whichever inputs populate each dimension — a dimension with no contributing input on a given Finding remains null, exactly as FIE-003 §14 established for Revision-derived nulls.

Section 28 — Multi-Model Support
The Financial Reasoning Engine and Narrative Generator both invoke the LLM runtime through Tool Gateway / Prompt Registry (EIS-003), never a direct model API call — the same discipline BIS-006 §27 already established. llm_version and prompt_version are recorded on every Narrative Object (Table FIE5-7.4) specifically so that a model or prompt change is auditable against every narrative it produced; a model upgrade never silently changes what an already-PUBLISHED Narrative claims, since that Narrative's content is immutable, per Section 1.10's storage-layer bounding of non-determinism — the same technique BIS-006 §1.10 pioneered for its own narrative generation, applied here to a domain where the stakes of an unreviewed model-version drift are considerably higher.

The most consequential decision in this document is Section 1.8, and it is worth being honest about why it was cheap to make here and would have been expensive to make later. Findings were proposed as content living quietly inside a Reasoning Package, promoted to real identity only on request — a reasonable, minimal design. But the same document's own Narrative Object already needed a stable 'Financial Finding Reference' field, which only means something if the thing on the other end of it can't disappear or get renumbered. Noticing that a document's own two requirements were in tension, before a single migration existed to make fixing it costly, is the entire value of running four rounds of conceptual review before writing an engineering specification instead of one.
