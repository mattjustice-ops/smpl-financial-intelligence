Section 1 — Scope Decisions
The FIE-004 conceptual model is frozen and is not redesigned here. This section restates its Section 1 Architectural Reconciliation in the numbered format used since BIS-001, and adds five further resolutions the build requires to be engineering-ready.
1.1 Memory vs. Observation Engine
The Observation Engine (FIE-001) owns immutable financial facts — Observations and Revisions. This service owns organizational knowledge related to those facts — why a decision was made, what was believed, what context surrounded a change. This service never writes to FIE-001 and never duplicates a value FIE-001 already records; every reference to a fact is a lineage pointer (Section 9), never a copy.
1.2 Memory vs. Methodology Engine
The Methodology Engine (FIE-002) remains the sole authoritative system of record for methodology definitions. This service preserves the organizational narrative around a methodology's evolution — why ARR's definition changed, what it was expected to affect — as a Methodology Context Knowledge Object (Section 8) that references, but never contains a copy of, the FIE-002 methodology_id and version it concerns.
1.3 Memory vs. Calculation Engine
The Calculation Engine (FIE-003) owns deterministic execution and produces Financial Intelligence Objects. This service preserves organizational knowledge associated with those FIOs — a Decision that led to a scenario being run, the reasoning behind approving one forecast version over another — and never recalculates, never writes to FIE-003, and never stores an FIO value independently of the FIO record itself.
1.4 Memory vs. Narrative Intelligence (FIE-005)
Narrative Intelligence reasons over Memory to generate commentary; it consumes this service's retrieval APIs (Sections 13–14) and has no write path into any Knowledge Object. This service performs no reasoning, pattern discovery, or narrative generation of its own — Pattern Records and Recommendation Candidates (Sections 8, 12–13 of the conceptual model) are preserved here but originate entirely from FIE-005 or other future Intelligence services.
1.5 Memory vs. Knowledge Platform (BIS-005)
BIS-005 remains the sole authoritative store for reusable platform knowledge — implementation guidance, best practices, mappings, and organizational learning intended for reuse across customers. This service owns Customer Organizational Memory exclusively and maintains no second Platform Memory repository of its own. The Promotion Pipeline (Section 15) is the only path by which content originating here can ever reach BIS-005, and it is never automatic — this is the fourth reconciliation of this kind in the documentation set (after BIS-005 §1.1 vs. EIS-004, BIS-006 §1.7 vs. the interim Memory proposal, and FIE-002 §1.5 vs. BIS-005), and the first one resolved inside the conceptual freeze itself rather than during engineering.
1.6 Inherited Limitation from FIE-003
Per FIE-003's own closing note, this service explicitly restates rather than silently rediscovers: FIE-003 §1.9 narrows Governed execution to effective-date-based methodology resolution only, deferring full historical restatement windows pending a FIE-002 addendum. Forecast Memory (Section 4 of the conceptual model, Section 8 here) therefore preserves the organizational understanding that existed at a given point in time — what was believed, and why — independently of whether FIE-003 can currently recompute what the historical calculation would have been under a since-changed methodology. Where a user asks "what would this forecast look like restated under today's methodology," this service correctly returns EVIDENCE_UNAVAILABLE (Section 25) for the recalculation, while still returning the preserved historical belief itself without degradation — the two questions are answered independently, and only one of them depends on a capability this service does not have.
1.7 New Resolution — Business Theme Registry Follows the Established Versioned-Registry Pattern
Business Themes (conceptual model Decision 7) are controlled-vocabulary entries, not Knowledge Objects — the same structural role Financial Concept plays in FIE-001 and Calculation Intent plays in FIE-002. business_themes is therefore a small, admin-governed, append-only versioned table (Section 11), never a free-text tag field on Knowledge Objects that could silently fork into near-duplicate spellings of the same theme.
1.8 New Resolution — Evidence Chains Are a Typed Reference Table, Not a JSON Blob
Per Decision 8, Evidence Chains are structural infrastructure rather than Knowledge Objects. At the schema level this is implemented as a typed, queryable reference table (evidence_chain_refs, Section 7.4) — the same pattern FIE-003 §7.4 uses for fio_lineage_refs — rather than an opaque JSON array on each Knowledge Object. This is what makes Section 22's evidence-based query patterns ("every Knowledge Object with evidence referencing this Calculation Run") a direct index lookup rather than a full-table JSON scan.
1.9 New Resolution — Lifecycle Is a Governed State Machine, Independent of Version Immutability
Per Decision 19, Lifecycle differs from version history: a Knowledge Object's version number increases every time its content changes (immutably, per Section 16); its lifecycle_state (Proposed → Accepted → Active → Superseded → Archived) can change independently of, and without requiring, a new version. Correcting a typo in a Decision's description creates a new version; that Decision being superseded by a later organizational decision changes lifecycle_state without necessarily changing content. These are deliberately two separate fields with two separate transition rules, detailed in Section 19.
1.10 New Resolution — Semantic Retrieval Is Specified but Not Built at MVP
Decision 16's own conditional language ("if implemented") signals this was never mandatory for freeze. Per the same discipline BIS-004 §1.11 applied to FIDS and BIS-006 §16 applied to financial waterfalls: this document names the capability, specifies its reproducibility requirement (pinned embedding_model_version, Section 14), and reserves its API surface (Section 4.4), but does not build embedding generation, vector storage, or similarity search at MVP. Deterministic retrieval (Section 13) is the only retrieval mechanism available at launch; semantic retrieval is backlogged in Section 34 pending a concrete FIE-005 use case that structured filtering cannot serve.
1.11 New Resolution — Provenance Is a Controlled Vocabulary, Not Free Text
Per Decision 18, provenance ∈ {HUMAN, AI_GENERATED, IMPORTED, IMPLEMENTATION, FINANCIAL_GOVERNANCE, FUTURE_INTELLIGENCE} — a fixed enum requiring an engineering/admin review to extend, the same controlled-vocabulary treatment FIE-001 §1.9 applies to relationship_type and FIE-002 §15 applies to calculation_intent. A Knowledge Object's provenance is set once at creation and is immutable, consistent with every other field on a given version.

Section 8 — Knowledge Object Model
Every knowledge_type shares the schema in Table FIE4-7.1; content's JSONB shape is type-specific but structurally validated against a per-type schema at write time (Section 25). Decision Memory and Forecast Memory content always carries reference fields (e.g. observation_ref, fio_ref, methodology_ref) rather than copied values, enforced by the same MISSING_EVIDENCE-style validation Table FIE4-4.1 applies at creation — a Decision naming a dollar figure without a resolvable Observation or FIO reference fails validation rather than being silently accepted as a duplicated value.
Section 9 — Evidence Chain Model
Implements Section 1.8: every Knowledge Object's evidence is one or more rows in evidence_chain_refs, typed by evidence_type. A Knowledge Object's Knowledge Confidence (Section 17) is set by whoever creates it, informed by — but not mechanically derived from — the strength of its Evidence Chain; this service does not compute confidence from evidence count or type, since that would reintroduce exactly the retroactive-recalculation risk Section 1.9 was written to prevent.
Section 10 — Relationship Model
A relationship is asserted, never inferred, at the same time as or after a Knowledge Object's creation — the API accepts related_knowledge_object_ids directly in the write request (Table FIE4-4.1) or via a subsequent explicit call, and this service runs no correlation or similarity logic to discover relationships after the fact, mirroring FIE-001 §16's identical rule for Observation/Revision relationships.
Section 11 — Business Theme Registry
Business Themes are created and versioned exclusively through an admin-governed write path (POST /v1/business-themes, Table FIE4-4.4) — no Knowledge Object write can implicitly create a new theme by referencing an unrecognized theme name. A knowledge_objects write referencing a business_theme_id that does not exist fails with BUSINESS_THEME_NOT_FOUND, per Table FIE4-4.1, closing off the silent-duplicate-spelling risk a free-text tag field would carry.
Section 12 — Timeline Model
GET /v1/timeline (Table FIE4-4.4) is purely a query over knowledge_objects.business_effective_date and created_at, filtered by any combination of Section 13's axes — it has no dedicated storage. This mirrors FIE-001's identical treatment of its own timeline endpoint over Temporal Records: a view, not a materialized structure, so there is never a risk of the timeline and its underlying Knowledge Objects drifting out of sync.
Section 13 — Retrieval Architecture
Deterministic retrieval (GET /v1/knowledge-objects/query, Table FIE4-4.2) supports filtering by knowledge_type, business_theme_id, financial_concept_id (via evidence_chain_refs joins), decision/meeting/methodology/calculation_run references, confidence threshold, tags, lifecycle_state, and an as_of parameter resolving to the version active at a past date — the same bi-temporal query shape FIE-001 §4.3 and FIE-002 §4.3 both already established. This is the only retrieval mechanism available at MVP, per Section 1.10.
Section 14 — Semantic Retrieval Architecture (Reserved, Not Implemented)
POST /v1/knowledge-objects/semantic-query (Table FIE4-4.4) is specified but returns NOT_IMPLEMENTED at MVP, per Section 1.10. When built, it will require an embedding_model_version field pinned on each Knowledge Object's semantic index entry — a separate, additive table, never a modification to knowledge_objects itself — so that retrieval remains reproducible for a given embedding version exactly as Decision 16 requires, and so that adding semantic retrieval later is a purely additive schema change, not a migration.
Section 15 — Promotion Pipeline
Implements Decision 14 and Section 1.5 exactly: Customer Organizational Memory → Governance Review → Anonymization → Approval → BIS-005. A promotion_requests row moves from PENDING_REVIEW to APPROVED or REJECTED only through an explicit POST /v1/promotion-requests/{id}/review call by an authorized governance reviewer (Table FIE4-4.4); only an APPROVED transition triggers a call into BIS-005's own knowledge-record creation endpoint, using the anonymization_plan to strip or generalize customer-identifying content before that call is made. This service never writes to a BIS-005 table directly — it calls BIS-005's own API, the same arm's-length relationship every other cross-service write in this platform maintains.
Section 16 — Versioning
PATCH /v1/knowledge-objects/{id} (Table FIE4-4.4) always creates a new version row sharing the same knowledge_object_id; no field on an existing version is ever updated in place except lifecycle_state, per Section 1.9. GET /v1/knowledge-objects/query's as_of parameter resolves to the version whose created_at was the most recent as of the requested date — the same reproducibility guarantee FIE-002 §1.7 provides for methodology versions.
Section 17 — Knowledge Confidence
knowledge_confidence is supplied at write time by the creator (human or upstream service) and is never recalculated by this service. It is explicitly distinct from FIE-001's Mapping/Data/Reasoning confidence dimensions — a Knowledge Object may reference high-confidence Observations while itself carrying lower Knowledge Confidence, if the organizational interpretation of those facts remains contested, or the reverse.
Section 18 — Provenance
Set once at creation from the controlled vocabulary in Section 1.11, immutable thereafter. AI_GENERATED provenance is used for Pattern Records and Recommendation Candidates originating from FIE-005 or future services; this service performs no validation of the substance of an AI-generated Knowledge Object beyond the same structural schema check every knowledge_type receives — it preserves what it is given, per the Core Architectural Principle.

Section 20 — Administrative Metadata
Per Decision 21, every Knowledge Object exposes name, description, knowledge_type, owner, status, version, confidence, lifecycle, business_theme_ids, related_knowledge_object_ids (via Section 10), evidence_count (a derived count over evidence_chain_refs, not a stored field), visibility, and approval_status — all either direct fields on knowledge_objects or cheap derived reads, never a redundant second copy, consistent with FIE-003 §19's identical treatment of administrative metadata as read-through references rather than separately entered data.
Section 21 — Graph Representation
The Organizational Knowledge Graph is knowledge_relationships (Section 10) plus knowledge_objects as nodes — there is no separate graph database or materialized graph structure at MVP. GET /v1/knowledge-objects/{id}/relationships (Table FIE4-4.4) provides one-hop traversal; multi-hop traversal is deferred to Section 34's backlog, mirroring FIE-002 §14's identical deferral for its own dependency graph.

Section 24 — Retry Strategy
All writes are idempotent by idempotency_key, consistent with every prior BIS/FIE document
A failed write is safely retryable on timeout or 5xx; a 4xx requires input correction before retry
Lifecycle transitions are safely re-callable — a repeated transition request to a state already reached is a no-op success, per the same pattern FIE-002 §19 uses for its own governance state machine
Promotion review decisions are not retryable once made — an APPROVED or REJECTED promotion_requests row is terminal; a reconsideration requires a new promotion request
