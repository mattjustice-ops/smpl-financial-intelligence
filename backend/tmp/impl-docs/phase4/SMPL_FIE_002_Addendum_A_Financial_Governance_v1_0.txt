This addendum adds capability to FIE-002. It does not redesign it, and it requires zero schema changes to FIE-003, FIE-004, or FIE-005.
Why This Addendum Exists
FIE-003 §1.9 narrowed Governed execution to effective-date-based methodology resolution only, deferring "custom historical restatement windows" and "full historical rebuilds" pending this exact addendum. FIE-004 §1.6 restated the same gap rather than rediscovering it, distinguishing preserved historical belief from unavailable historical recalculation. FIE-005 §1.7 restated it a third time, requiring every historical-understanding question to be explicitly labeled as grounded in preserved knowledge rather than live recalculation. This addendum closes the gap all three were built around.
Section 1 — Scope Decisions
1.1 Relationship to FIE-002 v1.0
Nothing in FIE-002 v1.0 is redesigned. Every existing table, endpoint, and governance rule remains exactly as specified. This addendum adds two new fields to methodologies, three new tables, and a set of new endpoints layered on top of the existing API. A methodology with no retirement_date and no attached restatement_policy behaves identically to FIE-002 v1.0 today — this addendum is additive and opt-in per methodology, not a platform-wide behavior change.
1.2 Retirement Date vs. Effective Date vs. Lifecycle State
Three independent fields now govern a methodology version, each answering a different question. effective_date (existing) answers "when did this version become the operative one going forward?" retirement_date (new) answers "as of what date does this version stop being the correct answer for a GOVERNED as_of query?" lifecycle_state (existing, DRAFT→...→ARCHIVED) answers "where is this version in its own approval workflow?" These three are deliberately decoupled, the same Lifecycle/Version independence FIE-004 §1.9 already established: a version can be ACTIVE in the registry sense with a retirement_date already in the past for governance-resolution purposes, and a version's retirement_date can be set without any change to its lifecycle_state.
1.3 Restatement Policy Is Attached, Never Assumed
A methodology carries no restatement behavior unless a restatement_policy is explicitly attached to it. Three modes exist:
Mode
Behavior
RESTATE_FORWARD_ONLY
Default for every methodology unless explicitly overridden — a new version applies only from its effective_date forward; no historical period is ever recalculated. Identical to all FIE-002 v1.0 behavior today.
RESTATE_FULL_HISTORY
A new version, once its Restatement Event is approved (Section 4), triggers recalculation of every prior period back to the methodology's inception
RESTATE_WINDOW
A new version's Restatement Event recalculates only a bounded historical range specified at Restatement Event creation (e.g. the current fiscal year)
Table A-1.3 — Restatement Policy modes. Attaching a policy changes nothing by itself — restatement only ever happens through an approved Restatement Event, per Section 1.4.
1.4 New Resolution — Restatement Approval Is a Separate, Elevated Governance Gate
A Restatement Event is never approved through FIE-002's existing methodology governance state machine (Draft→Review→Approved→Active→Deprecated→Archived). It has its own, stricter approval flow (Section 5), reflecting that retroactively changing what a historical period's numbers were carries materially higher stakes — audit, board, and investor implications — than approving a new methodology version for forward use. A methodology version can reach ACTIVE status through ordinary governance while its associated Restatement Event remains independently PENDING_APPROVAL; the two approvals are never conflated into one action.
1.5 New Resolution — Cascade Resolution Through the Dependency Graph Is Mandatory
Per FIE-002's existing methodology_dependencies graph (FIE-002 §14): a Restatement Event targeting one methodology automatically resolves every downstream dependent methodology (e.g. restating ARR requires Bookings, Revenue, and Cash — whichever the graph declares depend on it) and requires them to be included in the same Restatement Event by default. Excluding a dependent from the cascade is possible only with an explicit, recorded justification at Restatement Event creation (Section 4) — never a silent omission. This prevents the platform from ever producing an internally contradictory state where one restated methodology's dependents still reflect the prior methodology version.
1.6 New Resolution — FIE-005 Gains a First-Class Restatement Comparison Question Type
RESTATEMENT_COMPARISON is added to FIE-005's Question Understanding taxonomy (FIE-005 §8) as a named, directly askable question type — "what would this look like under today's methodology" becomes a discoverable capability, not something a user must know special syntax to request. Section 10 below specifies exactly how FIE-005 resolves this question type once this addendum exists.
1.7 New Resolution — Restatement Never Edits History; It Creates New Runs
An approved Restatement Event never modifies an existing FIE-003 Calculation Run, FIE-003 Financial Intelligence Object, or FIE-001 Observation/Revision. It produces a new Financial Operating Model version (per FIE-002 §1.7's existing freeze-on-creation model) and dispatches new FIE-003 Calculation Runs, in GOVERNED execution mode, against every period the Restatement Event's scope covers. The original runs remain permanently valid, unmodified, and queryable — a restated period simply gains a second, later set of runs against the new Operating Model version. This is the identical "new version, never edit in place" discipline FIE-002 and FIE-003 already apply everywhere else, extended one level up rather than introduced as a new rule.

Section 6 — Cascade Resolution Logic
At POST /v1/restatement-events, the primary_methodology_id is traversed through methodology_dependencies (FIE-002 §14) to find every downstream dependent — the same one-hop-then-transitive traversal FIE-002 §14 already defers to a future consumer for multi-hop cases; this is that consumer, exercised for the first time. Every methodology reached is added to cascade_methodology_refs, each pinned to its own currently-ACTIVE version. A caller may remove an entry from the cascade only by resubmitting with an excluded_dependents entry carrying a non-empty justification (Table A-2.3); the submit endpoint (Table A-3.1) rejects an empty or missing justification for any exclusion, closing off silent gaps in the restated set.
Section 7 — FIE-005 Restatement Comparison Question Type
RESTATEMENT_COMPARISON (Section 1.6) resolves by: (1) identifying the applicable methodology and period from the question, (2) checking whether a COMPLETE Restatement Event exists covering that methodology and period, and (3a) if so, retrieving both the original and restated Financial Intelligence Objects and reasoning over the difference as an ordinary Financial Finding (FIE-005 §11) with both FIO references in supporting_evidence_refs, or (3b) if no completed Restatement Event exists, returning a Reasoning Package with status=INSUFFICIENT_EVIDENCE and a specific, user-facing explanation that a restatement would need to be run to answer this question — never a fabricated or approximated comparison.
Section 8 — Impact on FIE-003 Governed Mode
FIE-003 §1.9's narrowing is lifted exactly to the extent a restatement_policy and COMPLETE Restatement Event exist for the methodology and period in question — and no further. A GOVERNED as_of query against a methodology with RESTATE_FORWARD_ONLY (the default) behaves identically to today. Against a methodology with a completed RESTATE_FULL_HISTORY or RESTATE_WINDOW event, the same query now resolves to the restated Operating Model version for periods within scope. No FIE-003 code changes — this is entirely a consequence of FIE-002 returning richer resolution answers, per Section 1.8.
Section 9 — Impact on FIE-004 Forecast Memory
FIE-004 §1.6's distinction between preserved historical belief and unavailable historical recalculation remains structurally exactly as specified — this addendum does not change FIE-004 at all. What changes is that "unavailable" becomes "available" for any period a completed Restatement Event now covers, and FIE-004's existing Decision Memory (Section 4 of this addendum) automatically gains a durable record of every restatement decision made, available for exactly the kind of longitudinal query FIE-004 was built to answer — "did we ever restate this, and why."
Section 10 — Impact on FIE-005 Historical-Understanding Questions
FIE-005 §1.7's CURRENT/HISTORICAL question classification is unchanged in structure. A HISTORICAL question that previously always returned a preserved-knowledge-grounded answer now, for covered periods, has the option (Section 7) of answering as a live comparison instead, or of returning both: the preserved belief at the time, and the restated figure, explicitly labeled as two different things answering two different questions — never conflated into one number.

Section 12 — Security and Governance Controls
required_approver_role is configured per customer and enforced at the API layer — approve/reject fail closed with INSUFFICIENT_APPROVAL_ROLE for any caller lacking it, per Section 1.4
A Restatement Event's cascade_methodology_refs, once APPROVED, are immutable — no code path allows adding or removing a methodology from an already-approved event
Every approval decision is permanently logged both in restatement_approvals and as a FIE-004 DECISION Knowledge Object, giving the decision two independent, cross-checkable audit trails
A REJECTED or FAILED Restatement Event is terminal and retained, never deleted, consistent with the platform's universal no-deletion posture

The one guarantee this addendum could not be allowed to weaken is the platform's central immutability promise — that history, once recorded, is never rewritten. A restatement is, on its face, exactly the kind of feature that could violate that promise if built carelessly: its entire purpose is to change what a historical period's numbers say. Section 1.7 is the resolution: a restatement never edits a record, it creates new ones, at a new Operating Model version, leaving the original permanently intact beside it. The feature that sounds most like an exception to the platform's core rule turns out, built this way, to be another instance of it.
