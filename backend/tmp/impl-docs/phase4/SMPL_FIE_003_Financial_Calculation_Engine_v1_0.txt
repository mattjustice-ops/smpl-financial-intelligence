Section 1 — Scope Decisions
The FIE-003 conceptual model is frozen and is not redesigned here. This section translates its Scope Boundaries into the numbered, restated-plus-new-resolutions format used since BIS-001, and adds six further resolutions — three closing execution-level ambiguities the conceptual model left to "the engineering specification," and one closing a real dependency gap this document's own Governed execution mode surfaced against FIE-002 as actually built.
1.1 Calculation Engine vs. Observation Engine
The Observation Engine (FIE-001) records financial history as immutable Observations and Revisions. This service reads Snapshots and Revision references through FIE-001's existing timeline and snapshot APIs and never calls a FIE-001 write endpoint under any circumstance — not even for scenario approval, per Section 1.6 below. Every calculation input is a reference to a FIE-001 record; no calculation input is ever fabricated when a reference is unavailable (Section 17).
1.2 Calculation Engine vs. Methodology Engine
The Methodology Engine (FIE-002) owns Methodologies, the Formula Registry, the Driver Registry, Financial Operating Models, and governance state. This service resolves a specific Financial Operating Model version through FIE-002's GET /v1/operating-models/{id} and GET /v1/methodologies/resolve endpoints and executes exactly what they return. It holds no write path into any FIE-002 table and performs no independent judgment about which methodology version is correct for a given moment beyond the Execution Mode rules in Section 1.9.
1.3 Calculation Engine vs. Financial Memory (FIE-004)
This service produces Financial Intelligence Objects. Financial Memory reasons across them over time — forecast accuracy, recurring drivers of variance, longitudinal pattern recognition. This service performs no cross-run reasoning of its own; it produces the FIOs, in full, with lineage, that make such reasoning possible downstream.
1.4 Calculation Engine vs. Narrative Intelligence (FIE-005)
This service produces explainable FIOs with complete Calculation Lineage (Section 8) and Financial Evidence (Section 1.7). Narrative Intelligence consumes that evidence to generate commentary; it never recalculates a value and has no write path into this service's tables.
1.5 Calculation Engine vs. Reporting Platform (BIS-006)
This service produces financial intelligence. Reporting presents it, following exactly the same read-only relationship BIS-006 already has with Canonical, Validation, and CAL — see BIS-006 §1.2–1.4. Reporting reads Published-visibility FIOs (Section 8) through this service's query API; it never triggers a calculation and never sees Internal-visibility FIOs unless explicitly scoped to a debugging or audit context (Section 24).
1.6 New Resolution — Scenario Approval Write Path Never Passes Through This Service
Per the conceptual model's Decision 9: Scenario execution produces an ordinary, independent Calculation Run (Execution Mode = SCENARIO, per Section 12) and creates no FIE-001 Revision. When a scenario is approved, the caller is Financial Governance (a FIE-002 capability) acting through Orchestration (BIS-002), which reads the approved Scenario Calculation Run's output FIOs and calls FIE-001's POST /v1/revisions directly, supplying the approver identity FIE-001 requires and referencing the Scenario Calculation Run's FIOs as related_observation_refs. This service's own API surface has no endpoint capable of writing to FIE-001, closing the boundary the conceptual review flagged as contradicted between this document's Scope Boundaries and its original Decision 9.
1.7 New Resolution — Financial Evidence Is Assembled on Read, Never Persisted
Per Decision 14: a Financial Evidence Package is computed at query time (GET /v1/evidence/{fio_id}, Section 4.4) by joining a Financial Intelligence Object to its Calculation Run and to every upstream FIO its lineage references, recursively. No evidence_packages table exists. This keeps evidence permanently consistent with its underlying Calculation Run — there is no second copy that could drift — at the cost of a join-heavy read path, which Section 26 sets an explicit, separate performance target for rather than folding it into ordinary FIO read latency.
1.8 New Resolution — Confidence Propagation Combination Rule
Per Decision 13, this document requires the combination rule be explicitly defined rather than left implicit. Every FIO retains the full three-dimensional confidence structure established in FIE-001 (Mapping, Data, Reasoning). Where a formula combines multiple inputs — Observations, Revisions, or upstream FIOs — each of the three confidence dimensions on the resulting FIO is the minimum of that dimension across every direct input, never an average or a weighted blend. A formula is only as trustworthy as its least-trustworthy input; this is the same conservative posture BIS-006 §17 already applies to narrative generation ("never inflate confidence"), extended here to numeric propagation. Where an input dimension is null (e.g. a Revision's Mapping/Data Confidence, per FIE-001 §15), that dimension is excluded from the minimum for that input but still evaluated across all other contributing inputs — a Revision-derived input never silently forces a null result.
1.9 New Resolution — Governed Execution Mode Scoped to What FIE-002 Currently Supports
The conceptual model's Decision 15/16 describes Governed execution as resolving methodology versions against Financial Governance policies including retirement dates and restatement windows — capabilities FIE-002, as actually built, does not yet expose (its governance model provides effective_date and the six-state lifecycle in BIS/FIE2 §16, but no retirement_date field and no restatement_policy concept). Rather than build against fields that do not exist, this document scopes MVP Governed execution to exactly what FIE-002 supports today: resolving "which methodology version was ACTIVE as of a given business_effective_date," using FIE-002's existing as_of parameter on GET /v1/methodologies/resolve. Custom historical restatement windows and full historical rebuilds are explicitly deferred to Section 31's backlog, pending a FIE-002 addendum introducing retirement_date and a restatement_policy entity — this service's Governed mode is designed to extend to that capability without a redesign once it exists, but does not implement it now.
1.10 New Resolution — Cache Key and Staleness Model
Per Decision 8: a Calculation Run is cache-eligible, and reusable in place of re-execution, exactly when a prior COMPLETE run exists with an identical (snapshot_ids, financial_operating_model_version, calculation_intent) tuple. Snapshot IDs are drawn directly from FIE-001's Domain and Composite Snapshot identifiers (FIE-001 §12–13), which already carry their own completeness and supersession semantics — this service performs no independent Observation-level change detection. A new Observation Event that produces a new Snapshot automatically invalidates cache eligibility for any Calculation Run referencing the superseded snapshot, and only those runs, giving Incremental Execution (Section 15) its blast-radius calculation for free rather than requiring a second mechanism.
1.11 New Resolution — This Is the Only FIE Service With No LLM in Its Execution Path
Worth stating as an explicit architectural property, not an incidental fact: unlike BIS-006's narrative generation or FIE-005's future commentary, no step in this service's execution path invokes an LLM. This is precisely what makes Decision 15 (the platform's determinism guarantee) achievable at the source rather than bounded after the fact — BIS-006 §1.10 had to guarantee narrative stability through immutable storage because the LLM generating it is inherently non-deterministic; this service is deterministic in its actual computation, and immutability (Section 9) exists here to guarantee reproducibility of a process that was already deterministic, not to contain one that wasn't.

Section 8 — Financial Intelligence Object Model
Per Decision 2: every meaningful node in an Execution Graph — not only the terminal outputs a caller requested — produces its own FIO. A Board KPI request against the Pipeline→Bookings→Revenue→Gross Margin→Operating Income→EBITDA→Rule of 40→Board KPIs graph produces eight independently addressable FIOs, not one. The seven upstream nodes are written with visibility=INTERNAL unless independently requested as a target_financial_concept; the terminal node(s) explicitly requested are visibility=PUBLISHED. This is what makes Incremental Execution (Section 15) possible — each node's result is independently identifiable and independently cache-checkable — and what closes the conceptual review's "intermediate results" ambiguity: there is no separate intermediate-results concept, only INTERNAL-visibility FIOs.
Section 9 — Calculation Run Model
A Calculation Run is the immutable record of one execution: which Operating Model version, which Snapshots, which Execution Mode and Profile, and the resulting status. Every FIO it produces references it. A Calculation Run is never re-executed in place — a cache miss or a forced re-run always creates a new calculation_run_id, even if every input happens to be identical to a prior run (in which case Section 1.10's cache resolution would have returned the prior run before a new one was ever created).
Section 10 — Execution Graph Model
The Execution Graph is built at run time from FIE-002's declarative methodology_dependencies edges (FIE-002 §14), scoped to exactly the target_financial_concepts requested and their transitive upstream dependencies — not the customer's entire dependency graph. It is stored per-run in calculation_runs.execution_graph as a resolved, concrete structure (specific methodology and formula versions at each node), distinct from FIE-002's abstract, version-independent declarative graph.
Section 11 — Execution Plan Model
Generated once, before any node executes, and never modified. The Execution Planner performs circular dependency detection (Decision 10) at this stage — a CIRCULAR_DEPENDENCY error here means the Execution Plan is never created and the run fails immediately, before any computation is attempted. Detecting cycles at plan time rather than mid-execution keeps a bad dependency declaration from ever producing a partially-computed, inconsistent Calculation Run.

Section 13 — Dependency Resolution
This service resolves execution order, parallel grouping, incremental scope, and cycle detection from FIE-002's declarative edges; it never resolves which methodology version is correct — that is Section 1.9's Execution Mode responsibility, kept structurally separate so a dependency-resolution bug can never accidentally alter which methodology gets executed.
Section 14 — Confidence Propagation
Implements Section 1.8's minimum-across-inputs rule at every Graph Executor node. A node with two inputs — an upstream FIO (all three dimensions populated) and a driver value resolved to a FIE-001 Assumption Revision (Reasoning Confidence only) — computes its own Mapping and Data Confidence as the minimum across only the FIO input (the Revision contributes nothing to those two dimensions), and its own Reasoning Confidence as the minimum across both inputs. This is computed once at write time and never recalculated after the FIO is persisted, consistent with FIE-001's confidence-immutability discipline.
Section 15 — Incremental Execution
When a new FIE-001 Snapshot supersedes a prior one, every Calculation Run referencing the superseded snapshot_id becomes cache-ineligible, per Section 1.10. A subsequent calculation request against the same target concepts triggers execution only for the graph nodes whose required Snapshot or Revision set actually changed, plus every downstream node depending on them — nodes on independent branches (e.g. Headcount Forecast when only Pipeline changed) are served from their existing cached FIOs untouched.
Section 16 — Caching
Cache resolution is a lookup, not a heuristic: given (snapshot_ids, financial_operating_model_version, calculation_intent) for a requested node, the Cache Resolver checks for an existing FIO produced by a COMPLETE Calculation Run with an identical tuple. A hit returns the existing fio_id directly; the new Calculation Run (if one was created for other nodes in the same request) references the existing FIO via an UPSTREAM_FIO lineage ref rather than duplicating it. This guarantees Decision 8's requirement that caching never compromises reproducibility — a cache hit is definitionally identical to a fresh computation of the same inputs, not an approximation of one.
Section 17 — Materialization Strategy
Every FIO is materialized — there is no calculate-on-demand-and-discard mode in this MVP, since Section 1.7's evidence-assembly model depends on every lineage node being a persisted, queryable FIO. What Decision 11 leaves open — the balance between performance and storage — is addressed through Section 16's caching (avoiding recomputation, not avoiding storage) and Section 8's INTERNAL-visibility model (avoiding unnecessary customer-facing exposure, not avoiding persistence). A future storage-tiering strategy for FIOs, analogous to FIE-001's Hot/Warm/Cold model, is backlogged in Section 31 rather than assumed here.
Section 18 — Parallel Execution
The Graph Executor dispatches every node in a given execution_plans.parallel_groups entry concurrently; a node begins only once every node in its direct dependency set has reached a terminal state. Parallelism is bounded per Calculation Profile (Section 12) — INTERACTIVE caps concurrency to protect shared resources during a live dashboard session; BATCH and SCENARIO allow the platform's full configured ceiling (Section 25).
Section 19 — Administrative Metadata
Per Decision 18: every Calculation Run and FIO exposes a stable, human-oriented metadata surface (name, description, business purpose reference, owner, impacted downstream FIOs and reports) even though this service has no administrative UI of its own. This metadata is derived, not separately entered — name and description are resolved from the FIO's financial_concept_id and calculation_intent through FIE-002's registry; owner is resolved from the Financial Operating Model's constituent methodology ownership (FIE-002 §7.1). No new free-text administrative field is stored redundantly in this service; every administrative attribute is a read-through reference to the service that actually owns that fact.

Section 24 — Retry Strategy
Calculation Run creation is idempotent by idempotency_key
A failed run is safely retryable on timeout or 5xx; a 4xx requires input correction before retry
A cancelled run (Section 4.4) can be safely re-submitted as a new calculation_run_id
A PARTIAL run is not automatically retried by this service — the caller (typically Orchestration) decides whether to re-request once the missing input becomes available
Evidence assembly failures are safely retryable; they never affect the underlying FIO or Calculation Run they describe
