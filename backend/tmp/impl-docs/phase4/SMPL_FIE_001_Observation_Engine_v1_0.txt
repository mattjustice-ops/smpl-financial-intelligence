Section 1 — Scope Decisions
The FIE-001 conceptual model is frozen and is not redesigned here. This section translates the frozen model's Scope Boundaries into the numbered, restated-plus-new-resolutions format every BIS document has used since BIS-001, and adds the five further resolutions the build requires to be engineering-ready. This is the first document in the Financial Intelligence Engine series; it inherits the discipline of BIS-001 through BIS-006 rather than starting a new documentation convention.
1.1 Observation Engine vs. Canonical Platform
The Canonical Platform (BIS-003) is the system of record for current, trusted business objects. The Observation Engine stores historical Temporal Records derived from canonical objects at the moment they were observed. It reads canonical data through BIS-003's paginated list endpoints, following the exact bulk-read pattern BIS-004 §1.7 and BIS-006 §1.2 already established against the same API. It never writes to, mutates, or duplicates canonical storage — a Temporal Record is a historical derivative, not a competing copy.
1.2 Observation Engine vs. Validation Platform
Validation (BIS-004) determines whether canonical data can be trusted, at the moment validation runs. The Observation Engine permanently records the confidence state of a Temporal Record at capture time, per Section 15. If confidence for the underlying canonical data later improves or degrades, that change is reflected in new Validation results and, if relevant, new Observations going forward — it never rewrites the confidence already stored on a historical Temporal Record. This is the same immutability discipline BIS-004 §1.6 applies to validation_results, extended to this service's own store.
1.3 Observation Engine vs. Reporting Platform
Reporting (BIS-006) explains state to a human audience across every implementation-stage report type. The Observation Engine has no narrative or presentation responsibility at all — it stores structured, queryable Temporal Records and exposes them through Section 18's query patterns. Reporting, and later Narrative Intelligence (FIE-005), are expected consumers of this service's read API; this service is never a consumer of Reporting's output.
1.4 Observation Engine vs. Financial Memory (FIE-004)
The Observation Engine captures financial history as discrete, immutable facts and revisions. Financial Memory reasons across that history — recognizing recurring patterns, evaluating forecast accuracy over time, and answering longitudinal questions no single Temporal Record can answer alone. This service performs no cross-record reasoning, pattern detection, or accuracy scoring; those are FIE-004 responsibilities reading this service's output as an input, the same directional relationship BIS-004 has to CAL.
1.5 Observation Engine vs. Orchestration Service
Scheduling — cadence timers, business-event triggers, month-end/quarter-end coordination — remains owned entirely by the Orchestration Service (BIS-002). The Observation Engine exposes no scheduler, cron, or polling loop of its own; per Section 14, it only ever records a Temporal Record in direct response to a call it received. This mirrors the synchronous, job-triggered pattern BIS-003 §1.10, BIS-004 §1.8, and BIS-006 §1.9 already established across the platform — this is the fourth service to adopt it, not a new pattern.
1.6 New Resolution — Bulk Read Pattern from Canonical Platform
Consistent with BIS-004 §1.7 and BIS-006 §1.2: this service reads canonical data exclusively through BIS-003's paginated list endpoint at BIS-003's stated default and maximum page sizes. A single Entity State Observation capture pass for 10,000 opportunities issues on the order of 10 paginated read calls, not 10,000 — the difference between meeting and missing Section 24's performance targets, and the third document in the series to require this exact clarification.
1.7 New Resolution — Capture Trigger Model: Push, Job-Triggered, Never Self-Scheduled
Per Section 1.5, this service never initiates its own capture. Every Observation or Revision write originates from an explicit POST call — dispatched by an Orchestration-scheduled job (Section 14's Recording Policy trigger), a business-event handler (forecast approval, month-end close), or a manual/API request. There is no background scanner in this service comparing canonical state to the last known Observation and deciding independently that a new one is due. This keeps capture behavior fully auditable to a specific triggering call, per Section 21's logging requirement that every write traces to a request_id.
1.8 New Resolution — Financial Concept and Composite Snapshot Definition Are Versioned Registry Artifacts
Financial Concepts (Section 8) and Composite Snapshot Definitions (Section 13) are not free-text labels chosen at write time — they are versioned, engineering- or admin-managed registry entries, the same governance model BIS-004 §1.5/§1.9 applies to validation rules and BIS-006 §4.4 applies to report_templates. A Temporal Record references a specific financial_concept_id and, where relevant, composite_snapshot_definition_id with its version; updating a definition creates a new version rather than mutating the one already referenced by historical records, so a Composite Snapshot's completeness can always be evaluated against the exact definition that was active when it was captured.
1.9 New Resolution — Revision Confidence Storage: Nullable Dimensional Fields, Not a Separate Schema
Per the frozen model, Observations carry all three confidence dimensions (Mapping, Data, Reasoning) while Revisions carry only Reasoning Confidence directly, with Mapping and Data Confidence evaluable only indirectly through referenced Observations. At the schema level, this is implemented as the same three nullable columns on every Temporal Record row, not two different row shapes: an Observation row populates all three; a Revision row populates only reasoning_confidence and leaves mapping_confidence and data_confidence null. This keeps Temporal Record genuinely one inheritance hierarchy at the storage layer, consistent with Section 1 of the frozen model stating Observation and Revision are siblings under one parent, rather than requiring two physically different table shapes that a query layer must reconcile.
1.10 New Resolution — Storage Tier Transitions Are Metadata Changes, Never Data Rewrites
Hot/Warm/Cold transitions (Section 17) change where and how a Temporal Record is stored and how expensive it is to query — they never change the record's content, confidence, or timestamps. A tier transition is implemented as a background lifecycle job that relocates or recompresses storage and updates a storage_tier field; it holds no code path capable of altering business_effective_date, system_recorded_date, value fields, or confidence fields. This is what makes Section 1.2's confidence-immutability guarantee a storage-layer fact rather than a documented intention, following the exact discipline BIS-004 §1.6 applied via its explicit "no UPDATE path" design note on validation_results.

Section 8 — Recording Policy Model
Every Financial Concept owns exactly one active Recording Policy at a time, versioned per Section 1.8. A policy defines observation_cadence, comparison_cadence, refresh_trigger, and retention_policy. Policies may be platform-default (customer_id null) or customer-specific overrides. The Capture API rejects a write whose financial_concept_id has no active policy with INVALID_INPUT, and rejects a write whose triggering event does not match the policy's refresh_trigger with a warning-level log entry (not a hard failure, since manual and API-triggered captures per Section 1.7 are always permitted outside the configured cadence).
Section 9 — Temporal Record Model
Implements the frozen model's Temporal Record concept and the storage decision in Section 1.9: one table, two sibling record_family values, discriminated but never hierarchical. Every field common to both families — business_effective_date, system_recorded_date, customer_id, financial_concept_id, source_system, relationship references, confidence context — lives directly on temporal_records (Section 7.1). No field is duplicated under a different name for Revisions, closing the gap the conceptual review round explicitly flagged before freeze.
Section 10 — Observation Model
An Observation row (record_family = OBSERVATION) populates all three confidence dimensions and one of the two Observation subtypes:
Metric Observation (record_subtype = METRIC) — a scalar value_payload, e.g. {"metric": "cash_balance", "value": 4200000, "currency": "USD"}
Entity State Observation (record_subtype = ENTITY_STATE) — the state of one business object at the lowest meaningful grain, e.g. {"entity_type": "opportunity", "entity_id": "...", "stage": "...", "amount": ...}
Observations are never edited. A corrected value is a new Observation row with a later system_recorded_date and the same or a corrected business_effective_date; the prior row remains permanently queryable, satisfying the bi-temporal "what did we believe back then" requirement in Section 4.3.
Section 11 — Revision Model
A Revision row (record_family = REVISION) populates reasoning_confidence only, leaves mapping_confidence and data_confidence null, and requires at least one related_observation_refs entry supplying the Observations it is based on (enforced at the API layer, Section 4.2). The four record_subtype values — FORECAST_REVISION, BUDGET_REVISION, SCENARIO_REVISION, ASSUMPTION_REVISION — share identical storage shape and differ only in this discriminator and, by convention, the vocabulary used in value_payload.reason. A Scenario Revision that is adopted is never rewritten into a Forecast Revision; per the Scenario Promotion Rule, a new Forecast Revision row is created with a PROMOTED_FROM relationship (Section 7.8) to the originating Scenario Revision.
Section 12 — Snapshot Model
A Domain Snapshot represents one Financial Concept at one business_effective_date, assembled by the Snapshot Assembler from the constituent Observations captured for that moment. Its status is COMPLETE only if every source_system the active Recording Policy expects for that concept contributed at least one Observation; otherwise PARTIAL (some sources present), FAILED (no sources present), or SUPERSEDED (a later snapshot for the same concept and date has since been assembled). coverage_pct and missing_sources give downstream callers a quantified, not just categorical, view of completeness.
Section 13 — Composite Snapshot Definitions
Per Section 1.8, a Composite Snapshot Definition is a named, versioned template (e.g. MONTH_END_CLOSE) declaring the Financial Concepts that must each produce a COMPLETE Domain Snapshot, sharing one business_effective_date, for the composite to count as that named business event. The MVP completeness_rule is ALL_REQUIRED_COMPLETE — a composite is COMPLETE only if every required concept's Domain Snapshot is COMPLETE; a THRESHOLD_PCT rule is defined in the schema (Section 7.6) for future use but not exercised by any MVP definition. publication_rules determine whether a PARTIAL composite may still be exposed to downstream callers (e.g. Reporting) with an explicit PARTIAL flag, or is withheld until COMPLETE — configured per definition, since a Friday Sales Review tolerating partial data is a different business judgment than a Month-End Close requiring full data.
Section 14 — Event Processing
An Observation Event is registered (POST /v1/observation-events) before or atomically with the capture calls that reference it. Processing is synchronous per capture call — there is no event queue internal to this service. For Orchestration-scheduled cadences, the calling worker registers the event, then issues one or more capture calls referencing observation_event_id, then optionally triggers Domain/Composite Snapshot assembly once it knows all expected captures for that event are complete. This service never determines on its own that "all expected captures" have arrived; that determination is the calling worker's responsibility, informed by the Recording Policy's declared sources.
Section 15 — Confidence Handling
Per Section 1.9 and the frozen model's Confidence resolution: an Observation's mapping_confidence and data_confidence are copied at capture time from the Validation Platform's (BIS-004) current object-level confidence for the canonical object(s) the Observation derives from; reasoning_confidence, where populated on an Observation, reflects any interpretation applied during capture (e.g. currency conversion, unit normalization). A Revision's reasoning_confidence is supplied by the approver or capturing process and reflects confidence in the judgment itself, not in underlying data — data confidence for a Revision is only evaluable by a downstream consumer walking its related_observation_refs to the Observations it cites. No confidence field on any persisted row is ever recalculated or rewritten after creation, per Section 1.10.
Section 16 — Relationship Handling
Relationships are recorded only when explicitly asserted by the capturing caller — the Capture API accepts related_temporal_record_ids (for Observations, optional) or related_observation_refs (for Revisions, required) directly in the write request and persists them as temporal_record_relationships rows in the same transaction as the Temporal Record itself. This service runs no correlation, similarity, or pattern-matching logic to discover relationships after the fact; per Section 1 of the frozen model, that reasoning belongs to later Financial Intelligence services, and this service's API surface has no endpoint capable of creating a relationship without an explicit source and target supplied by the caller.

Section 20 — Retry Strategy
Observation and Revision capture is idempotent by idempotency_key (Sections 4.1–4.2)
A failed capture can be retried safely on timeout or 5xx; a 4xx requires input correction before retry
Snapshot assembly is safely re-callable — re-assembling a Domain or Composite Snapshot for the same concept/date produces a new snapshot_id with status=SUPERSEDED applied to the prior one, never an in-place overwrite
Storage tier transitions are retryable at the individual-record level; a partial batch failure does not affect records that already completed their transition

FIE-001 is complete and ready for engineering to begin implementation. It is the foundational service of the Financial Intelligence Engine layer: every Observation and Revision captured here becomes the substrate FIE-002 (Methodology Engine) interprets, FIE-003 (Calculation Engine) computes from, FIE-004 (Financial Memory) reasons across, and FIE-005 (Narrative Intelligence) explains. The next document in the series is FIE-002, and it should open its own Section 1 the same way this one did — by restating this document's scope boundaries rather than assuming them, since that discipline is what has kept eleven documents across two platform layers from silently drifting apart.
The most consequential decision in this document is Section 1.9 — collapsing the frozen model's Observation/Revision sibling relationship into one physical table with nullable confidence columns rather than two table shapes. The conceptual review process spent three rounds making sure Observation and Revision were never modeled as parent/child; it would have been easy to reintroduce exactly that hierarchy at the schema layer by giving Revision a separate, narrower table that a query layer has to special-case. One table, one discriminator, and a documented rule for which columns a given record_family populates is what keeps the sibling relationship real all the way down to the row.
