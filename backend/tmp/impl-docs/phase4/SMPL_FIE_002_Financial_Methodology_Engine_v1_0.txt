Section 1 — Scope Decisions
The FIE-002 conceptual model is frozen and is not redesigned here. This section translates the frozen model's Scope Boundaries into the numbered, restated-plus-new-resolutions format every prior document has used since BIS-001, and adds the six further resolutions the build requires to be engineering-ready — most of them closing gaps the conceptual review's second pass identified between this document and FIE-001 or BIS-005.
1.1 Methodology Engine vs. Observation Engine — Definitions vs. Values
The Observation Engine (FIE-001) records financial reality as immutable Observations and Revisions. The Methodology Engine defines how that reality should be interpreted and calculated. This boundary has one specific, previously ambiguous consequence made explicit here: Driver definitions (unit, cadence, default, description) live in this service's Driver Registry (Section 10); Driver values over time — a specific Close Rate on a specific date, with its reason, approver, and confidence — live exclusively in FIE-001 as Assumption Revisions or Observations, per Section 8's Driver Types split. This service's Assumption Library is a logical view over FIE-001 records filtered by driver_id, not a second store. There is exactly one system of record for historical driver values, and it is FIE-001.
1.2 Methodology Engine vs. Calculation Engine (FIE-003)
Methodology owns the definition — what should be calculated, using which formula, with which drivers and dependencies. Calculation owns execution — actually running a formula against actual Observation and Revision data to produce a result. This service stores no calculation results, no execution history, and no runtime state of any kind. The Formula Registry (Section 9) it owns contains declarative formula definitions only; FIE-003 reads them but never stores its own competing copy, per Section 1.4 below.
1.3 Methodology Engine vs. Financial Memory (FIE-004)
This service stores current and historical methodology definitions — what a methodology said at any point in time. Financial Memory reasons about how those methodologies performed once executed by FIE-003 — forecast accuracy, recurring override patterns, and longitudinal effectiveness. This service performs no effectiveness scoring or historical performance analysis of its own methodologies.
1.4 Methodology Engine vs. Narrative Intelligence (FIE-005)
Narrative Intelligence consumes methodology definitions — for example, to explain that a variance is partly attributable to a Close Rate assumption changing mid-quarter — but never defines, modifies, or overrides a methodology. This service exposes no write path reachable by Narrative Intelligence.
1.5 New Resolution — Methodology Engine vs. Knowledge Platform (BIS-005)
Per the conceptual review's Revision 7: the Knowledge Platform (BIS-005) stores reusable implementation knowledge, guidance, best practices, mappings, and organizational learning — content that helps a human or an implementation agent do something correctly. The Methodology Engine stores structured, executable financial methodologies — content a Calculation Engine can run. Knowledge may reference a methodology_id for context ("this customer's ARR Methodology excludes services revenue because..."); a Methodology may reference a knowledge_record_id for supporting rationale. Neither service owns the other's artifacts, and neither has a write path into the other's tables. This is the third boundary reconciliation of this kind in the documentation set — see BIS-005 §1.1 (vs. EIS-004) and BIS-006 §1.7 (vs. the interim Memory proposal) for the two prior instances of the same discipline.
1.6 New Resolution — Calculation Intent Is Part of the Methodology Registry's Identity
Per Revision 4: methodology lookup requires (financial_concept_id, calculation_intent), not financial_concept_id alone. Board ARR, Investor ARR, Operational ARR, and Sales ARR are independent, independently versioned Methodology Registry rows sharing a financial_concept_id, not one methodology branching internally on intent. This keeps every individual methodology's formula and driver set simple and avoids conditional logic inside a single formula definition, consistent with the composable architecture principle stated throughout the conceptual model.
1.7 New Resolution — Financial Operating Model Is a Frozen, Versioned Bundle
Per Revision 6: a Financial Operating Model is not a live pointer to "whichever methodology versions are currently Active." It is itself a versioned object whose composition — a specific methodology_version_id for every included methodology — is fixed at creation and never changes. A new Financial Operating Model version is created whenever any constituent methodology advances; the prior version remains permanently valid and queryable. This is the mechanism that makes Revision 11's (FIE-002 conceptual model) reproducibility guarantee real: a historical calculation references a specific Financial Operating Model version, which in turn resolves to an exact, unchanging set of methodology and formula versions, with no ambiguity about what was active at calculation time.
1.8 New Resolution — Provenance Link to FIE-001 Lives in Calculation Engine, Not Here
FIE-001 is frozen and is not modified to add a methodology_version_id or financial_operating_model_id column. The link between a specific Forecast Revision (or any FIE-001 record) and the Financial Operating Model version used to produce it is owned by FIE-003's own execution record (a calculation_run row, out of scope for this document), which references the FIE-001 temporal_record_id via an explicit FIE-001 relationship assertion (relationship_type = INFORMED_BY, per FIE-001 §16) alongside its own financial_operating_model_version_id. This service exposes the Financial Operating Model version as a stable, resolvable reference; it does not itself track which calculations used it.
1.9 New Resolution — Dependency Graph Is Declarative Only; No Execution State in This Service
Per Revision 5: this service stores and serves the dependency graph (Section 14) as a static, declarative structure — which methodologies depend on which others. It performs no runtime impact analysis, no recalculation planning, and holds no record of which calculations exist or are stale. When a methodology's status changes, this service's only action is to make the updated graph and version available for FIE-003 to query; FIE-003 owns entirely determining what is impacted and re-triggering recalculation. This is the same signal-not-enforce pattern BIS-004 §1.10 established for validation blockers — the fourth instance of it across the documentation set.
1.10 New Resolution — Driver Types Determine Value Source, Never Definition Shape
Per Revision 8: every Driver Registry entry is tagged driver_type ∈ {OBSERVED, ASSUMED}, determining only where its values are expected to come from — Observed Drivers (FX, DSO, actual headcount) resolve to FIE-001 Observations; Assumed Drivers (Close Rate, Sales Capacity, hiring plan) resolve to FIE-001 Assumption Revisions. The Driver Registry schema itself (Section 10) is identical for both types; driver_type is a lookup discriminator for the Assumption Library view (Section 1.1), not a fork in the data model.
1.11 New Resolution — Ownership Is Independent of Lineage
Per Revision 9: every Methodology Registry version carries both an owner (CUSTOMER | SMPL | PARTNER — who is accountable for this version) and, independently, a lineage reference (which Industry Template, if any, it was derived from). A customer-derived methodology retains its template lineage permanently for traceability while its owner is CUSTOMER from the moment it diverges from the template, per Revision 7 of the conceptual model (customer overrides inherit without modifying the template). These are two separate, non-overlapping fields on the same row, never conflated.

Section 8 — Methodology Registry Model
A methodology is uniquely identified for lookup purposes by (customer_id, financial_concept_id, calculation_intent); methodology_id is the stable identity across versions of that same triple. Only one version per triple may hold status=ACTIVE at a time — activating a new version automatically transitions the previously active version to DEPRECATED in the same write, per Section 16's governance state machine. Every methodology references exactly one formula (pinned by version at methodology-version creation) and zero or more drivers.
Section 9 — Formula Registry Model
A formula is a declarative expression tree over named driver references and constants — never executable code, and never stored or interpreted by this service beyond structural validation (Section 19). Formula versions are independent of methodology versions: a formula can be reused unchanged across multiple methodology versions, and a methodology version pins a specific formula_version at creation, per Table FIE2-7.1.
Section 10 — Driver Registry Model
Implements Section 1.10 exactly: one schema, a driver_type discriminator, no confidence field. Resolving a driver's actual values for a given customer and date range is never a local table read — it is always a call through the Driver Value Proxy (Section 5) to FIE-001's GET /v1/timeline/{financial_concept_id} endpoint, filtered to this driver's related Observations or Assumption Revisions. This guarantees the one-source-of-truth property Section 1.1 requires structurally, not just by convention.
Section 11 — Industry Template Model
A template is a named, versioned bundle of recommended (financial_concept, calculation_intent, formula, drivers) tuples — a starting point, never a constraint. Selecting a template during implementation does not itself create methodology rows; it creates methodology_overrides rows (Section 12) that reference the template and copy its recommendations as a customer's initial DRAFT methodologies, immediately editable and independently versioned from that point forward.
Section 12 — Customer Override Model
An override always produces a new, independently-owned methodology row (owner=CUSTOMER from creation, per Section 1.11) with a permanent lineage_template_id reference. The source template row is read-only from this flow's perspective — no override operation has a code path capable of writing to industry_templates. overridden_fields captures a field-level diff against the template at derivation time for audit and "how does this customer differ from the recommended template" reporting.
Section 13 — Financial Operating Model
Composing a Financial Operating Model resolves every methodology_version_ref supplied in the request into its concrete formula and driver versions and writes the result into resolved_composition once, at creation. INCOMPLETE_COMPOSITION is returned if any referenced methodology_version is not status=ACTIVE at composition time — a Financial Operating Model can only be built from methodologies the customer has actually approved into active use, never from Draft or Review versions. Once created, a Financial Operating Model version is the permanent, immutable contract Calculation Engine (FIE-003) references for every calculation run against it, per Section 1.7.
Section 14 — Dependency Graph Model
methodology_dependencies stores directed edges only — upstream_methodology_id feeds downstream_methodology_id. This service provides no traversal beyond one-hop GET /v1/dependencies/{methodology_id} (Section 4.4); multi-hop traversal (e.g. "everything ultimately affected by a Pipeline Methodology change") is a Calculation Engine responsibility reading the full edge set, per Section 1.9 and consistent with FIE-001 §31's identical deferral of relationship-graph traversal to a future consumer.
Section 15 — Calculation Intent Model
calculation_intent is a controlled-vocabulary text field (BOARD, INVESTOR, OPERATIONAL, SALES, MANAGEMENT, TREASURY, FORECAST, and customer-extensible values registered through the same admin flow as Financial Concepts) rather than a fixed enum, since the conceptual model's own examples (Board ARR, Investor ARR, Treasury Cash, Forecast Cash) suggest intents are domain-specific and likely to grow. New intent values require an engineering or admin review before use, mirroring FIE-001 §1.9's controlled-vocabulary treatment of relationship_type.

Section 19 — Retry Strategy
All registry writes are idempotent by idempotency_key, consistent with every prior BIS/FIE document
A failed write is safely retryable on timeout or 5xx; a 4xx requires input correction before retry
Governance state transitions are safely re-callable — a repeated transition request to a state already reached is a no-op success, not an error
Formula structural validation (Section 9) runs synchronously at write time so a malformed formula never reaches ACTIVE status to fail unpredictably later inside FIE-003

The most consequential decision in this document is Section 1.7 — freezing the Financial Operating Model as an immutable, versioned bundle rather than a live pointer to "whatever's currently active." It would have been simpler to let an Operating Model be a named alias that always resolves to current ACTIVE methodologies; it would also have quietly broken the reproducibility guarantee the conceptual model spent its own final round establishing, since a board deck generated in March and regenerated in June would silently use different methodology versions with no record that anything had changed. Resolving the composition once, at creation, and never again, is what keeps a historical calculation a historical fact rather than a moving target.
