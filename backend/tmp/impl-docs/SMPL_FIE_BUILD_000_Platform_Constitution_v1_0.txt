What This Document Is, and Isn't
This is not an architecture document — it introduces no new service and redefines nothing. It is not an engineering specification — FIE-BUILD-002 already owns engineering standards, and this document does not compete with it. BIS-000 through FIE-BUILD-008 collectively answer, in enormous and necessary detail, how every piece of this platform works. This document answers a different question: given all of that, where does a reader actually start, and how do the pieces relate to each other as one coherent system?
Read this first. Everything else is where you go next, and this document tells you exactly which "next" is right for you.
What SMPL Is, and Why It Exists
Every SaaS company should be able to operate like it has a world-class CFO team. Finance teams run on spreadsheets, manual data pulls, and reactive reporting — closing the books, building a forecast, or preparing a board deck means stitching together numbers from the CRM, the billing system, the ERP, and the data warehouse by hand. When a number changes, nobody can quickly answer why. When someone leaves the team, their knowledge of "how we've always calculated this" leaves with them.
SMPL exists to fix that — not by replacing the ERP, CRM, billing system, or data warehouse, but by sitting on top of all of them as an intelligence and orchestration layer that turns fragmented data into trusted, explainable financial insight. It is not a reporting tool or a dashboard generator. It is a decision-making engine.
Every architectural decision documented across this entire platform traces back to one goal: a platform a finance professional can actually stake their reputation on.
The Eight Founding Principles
Every section, every service, and every BUILD document that follows answers to these eight principles. Where a specific document enforces a principle mechanically — not just philosophically — that enforcement point is cited.
Evidence Before Trust
No claim is accepted, published, or acted on without a traceable source. This is FIE-005's entire reason for existing, and BIS-006's narrative discipline before it.
Enforced in: FIE-005 §1.6, §14–15; BIS-006 §17
Canonical Before Intelligence
Every ingestion path — live connector, CSV upload, or hybrid — converges on the same Canonical Business Objects before anything downstream ever sees the data. Nothing reasons about data that hasn't first become canonical.
Enforced in: BIS-003 §1.1; ABS-012 §2
Determinism Before Automation
The one service that actually computes a financial number — FIE-003 — has no LLM anywhere in its execution path. Automation and AI assist, interpret, and explain; they never compute.
Enforced in: FIE-003 §1.11; FIE-BUILD-002's Deterministic Core / AI Never Changes Numbers principles
Explainability By Design
Every published value can answer where it came from, without a special debug mode, from the moment its table is created — not bolted on after the fact.
Enforced in: FIE-BUILD-002 §17; FIE-003 §1.7's Financial Evidence Package
Governance Before Flexibility
A capability that could be misused — restating history, promoting knowledge to shared use, granting elevated access — is gated by explicit, recorded approval before it is convenient. Convenience is never the deciding factor.
Enforced in: FIE-002 Addendum A; FIE-004 §15; FIE-BUILD-007 §4, §9
Version Everything
Registries, schemas, methodologies, contracts, and releases are append-only. A change is a new version, never an edit in place — this is what makes reproducibility and audit possible at all.
Enforced in: FIE-BUILD-002's Versioning Philosophy; restated in every owning specification's own schema
Humans Remain Accountable
Automation executes; a named human or named discipline owns the outcome. Every governance table in this platform names an owner, not just a process.
Enforced in: FIE-BUILD-005 §2; FIE-BUILD-007 §1
Customer Outcomes Above Engineering Activity
A technically complete milestone that leaves a customer unable to trust the output has not succeeded. Implementation success is measured by what the customer can do with the platform, not by what shipped.
Enforced in: FIE-BUILD-001's Customer Readiness; FIE-BUILD-008's Customer Success Principle

How the Layers Relate
Layer 1 — Architecture Standards   (GPES, ABS, SKA/CKR/IMS, EIS)     ↓  governs how customer data enters the platformLayer 2 — Implementation Foundation  (BIS-001–006)     ↓  produces trusted Canonical dataLayer 3 — Financial Intelligence Engine  (FIE-000–005)     ↓  turns trusted data into calculated, explained financial intelligenceLayer 4 — BUILD Series  (FIE-BUILD-001–008, 000)     →  turns all three layers above into an actually-built, actually-operated,        actually-adopted production platform
A request from a real customer moves through all four layers on every single interaction: a connector or CSV upload (Layer 1) populates Canonical (Layer 2), which FIE-001 through FIE-005 turn into a verified Narrative (Layer 3), delivered through a platform that was built, released, operated, scaled, secured, and onboarded according to the discipline in Layer 4. No layer skips another. This is the single most important structural fact about the entire platform — see FIE-000 §5–6 and FIE-BUILD-003 §1–2 for the full runtime diagram.
Document Authority and Precedence
Architecture (Layers 1–3) is authoritative over engineering execution (Layer 4). A BUILD document that appears to conflict with architecture is wrong, and the architecture wins — this rule is stated explicitly at the top of every BUILD document in this series
Within a layer, a more specific document wins over a more general one for its own specific topic — e.g. FIE-002 Addendum A governs restatement specifics; FIE-002 itself remains authoritative for everything else
A frozen document is never silently reopened. A gap discovered in a frozen document becomes a named backlog item (Known Open Items, below) or a new addendum — never an unannounced edit
Where two documents name the same concept differently or use the same abbreviation for different things, that collision is resolved explicitly, in both documents, the moment it's found — never left ambiguous for a future reader to guess at. See the SDR collision (FIE-BUILD-006 vs. FIE-BUILD-007) for a worked example of how this is handled
Ownership-matrix tables (FIE-BUILD-001's Engineering Ownership Matrix, FIE-BUILD-003's Platform Ownership Matrix, FIE-BUILD-004's Release Governance, FIE-BUILD-005's Operational Governance, FIE-BUILD-007's Security Governance) are reconciled toward whichever was established first whenever they overlap

The Discipline That Holds This Together
Thirty-plus documents stayed internally consistent across an enormous amount of iteration for one reason: a small set of habits, applied every time, without exception. Any future contributor — human or AI — extending this documentation set should follow the same habits.
Reference, never duplicate — a fact or value owned by one document is cited by section number in another, never restated in a way that could drift out of sync
Restate inherited limitations, don't rediscover them — when Document B inherits a gap from Document A, Document B says so explicitly in its own Section 1, so Document C doesn't have to discover the same gap a third time
Name collisions the moment they're found — two documents using the same term or abbreviation for different things is fixed in both places immediately, never left for a future reader to puzzle out
State what's true, flag what isn't built yet — a document describing target-state capability says so; a document describing what's actually running says so; the two are never blurred into one present-tense voice
Every backlog item gets an owner and a trigger condition — never a vague "someday," always a specific condition that means it's time to act
A frozen document is extended, not reopened — new capability becomes an addendum (FIE-002 Addendum A) or a new document, never a silent edit to something already frozen
Every new document's Section 1 reconciles against what came before it — the same discipline applied nine times running across FIE-001 through FIE-BUILD-008

How to Extend This Documentation Set
A new document — architecture, BIS, FIE, or BUILD — follows the same pattern every prior one has:
Open with a Section 1 (or equivalent) that restates the boundaries of every document it touches, rather than assuming them
State explicitly what it does NOT own, not only what it does
Cite, don't duplicate, any content already specified elsewhere
If it inherits a limitation from an earlier document, restate that limitation explicitly rather than silently working around it
If it introduces a term, abbreviation, or pattern that might collide with an existing one, check first — and if a collision is found anyway, resolve it in both documents
Close with a build-readiness or final-review assessment naming any remaining gaps honestly, including ones that reflect on the document itself
Add any newly-discovered gap to this document's Known Open Items table, with an owner and a trigger condition
This is not bureaucracy for its own sake — it is the specific, demonstrated reason a documentation set this large has stayed coherent rather than accumulating silent contradictions. Every future contributor inherits the benefit of that discipline only by continuing to practice it.
Closing
The platform remembers. The platform calculates the same way every time. The platform explains itself, or it says nothing. That is the whole system, and every document in this set exists to make one part of it real.
This document has no authority to change anything it describes. Its only job is to make sure the next person — or the next agent — reading this documentation set for the first time knows where they are, why it's built this way, and exactly where to go next.
