The Universal CRM Implementation Principle — Stage Normalization Gate
The single most important implementation principle shared across every CRM IMS in this library has no equivalent in the ERP library: every CRM implementation has a mandatory stage normalization step that must be resolved before any meaningful pipeline canonical mapping can proceed. This is not equivalent to the ERP library's pre-extraction gates (which prevent data from being extracted at all if unresolved) — CRM data can be extracted without stage resolution, but the resulting pipeline objects carry Low confidence until every stage name is mapped to the SCBM canonical stage taxonomy.
The stage normalization gate governs the same capability set across all five CRM connectors: Pipeline Analytics, Pipeline Waterfall, Stage Conversion, and any capability derived from stage progression. Without resolved stage mapping, these capabilities reach at most 40% confidence regardless of how much data has been extracted.
Unlike the ERP library's pre-extraction gates, the CRM stage normalization gate does not BLOCK extraction — it degrades capability confidence until resolved. The CEP drives resolution through Pre-POC Discovery, and each CRM's Section 4 (Transformation Rules) documents how that resolution works for each vendor's stage data structure.
Cross-CRM Principles
SMPL is always read-only. No CRM IMS specifies write operations.
Closed Won ≠ Confirmed Revenue. This principle is stated in every connector's Transformation Guidance and is the most consequential CRM-domain caveat for Financial Intelligence. Closed Won reflects sales intent; confirmed revenue requires Billing and ERP cross-validation. The implementation agent surfaces this caveat explicitly during capability activation for every connector in this library.
Customer Health is not a CRM-native object. CRM connectors contribute partial signals (account status, renewal risk flags, lifecycle stage) to the canonical Health Score, but the Health Score itself is owned by the Customer Success domain. No CRM IMS maps any object to a canonical Customer Health Score — only to Health Score signal contributors.
Stage normalization is always customer-specific, never platform-assumed. Even for platforms with vendor-standard stage names (HubSpot), the implementation agent confirms stage business meaning via CEP before mapping proceeds. A customer's stage named "Closed Won" may or may not represent the same business event as another customer's stage named "Closed Won."
Pipeline is intent; Billing is execution. The cross-validation pattern established in the Billing IMS Library (Stripe Billing connector confirms Closed Won Opportunities from CRM connectors) applies symmetrically here — every CRM's Connector Synergies section documents the CRM+Billing cross-validation pair.
IMS-101 — Salesforce
Salesforce is the most customizable CRM in this library and the most complex to implement — not because of API complexity, but because of the breadth of customer-specific configuration the implementation agent must discover and resolve before canonical pipeline mapping is reliable. The primary implementation challenge is not data extraction; it is stage taxonomy normalization across potentially multiple Record Types with independent stage sets.
✱ ARCHITECT NOTE: Key departure from simpler CRM connectors in this library: Salesforce's Transaction-equivalent is the Opportunity Record Type — a customer-defined construct that determines which stage taxonomy applies to a given Opportunity. An enterprise Salesforce implementation with four Record Types has four independent stage taxonomies requiring four independent CEP resolution cycles. Discovering all active Record Types during Section 1 (Connector Discovery) is not optional — proceeding without this inventory produces a canonical pipeline that silently excludes Opportunities from unresolved Record Types.

1.2 Record Type Inventory — The Primary Discovery Step
Salesforce Record Types are the CRM equivalent of SAP's Controlling Area structure — they determine which field layouts, picklist values, and stage taxonomies apply to each Opportunity. Every active Record Type on the Opportunity object must be inventoried before stage normalization begins. Skipping this step is the single most common Salesforce implementation error.
DISCOVER active Opportunity Record Types:
  SOQL: SELECT Id, Name, IsActive, Description
        FROM RecordType
        WHERE SObjectType = 'Opportunity'
        AND IsActive = true
  FOR each returned RecordType:
    Record in CEP.record_types:
      [{id, name, description, is_active}]
  FOR each active RecordType:
    DISCOVER its stage taxonomy:
    SOQL: SELECT DefaultPicklistValues
          FROM RecordTypeInfo
          WHERE RecordTypeId = '{id}'
    RECORD stage list in CEP.record_type_stages[RecordType.id]
  IF count(active RecordTypes) = 0:
    Single stage taxonomy applies to all Opportunities
    Proceed with standard stage normalization
  IF count(active RecordTypes) >= 1:
    EACH RecordType requires independent CEP stage resolution
    DO NOT start CEP resolution for one RecordType while another
    is pending — complete full inventory first, then resolve in parallel

Section 4 — Transformation Rules
4.1 Opportunity Stage Normalization — The Core Transformation Rule
Stage normalization is the highest-priority transformation in every CRM IMS. The implementation agent maps each customer's stage names to the SCBM canonical pipeline stage taxonomy. This mapping is always customer-specific — even standard Salesforce stage names may represent different business concepts for different customers.
The SCBM canonical stage taxonomy (from the CKR CRM Registry Standard): MQL → SQL → Opportunity → Proposal → Negotiate → Closed Won → Closed Lost. These are intent stages, not revenue events. Closed Won is the last pipeline stage; actual revenue confirmation belongs to the Billing and ERP domains.
FOR EACH active RecordType in CEP.record_types:
  stages = CEP.record_type_stages[RecordType.id]
  FOR each stage_name in stages:
    LOOKUP in SMPL CRM Stage Pattern Library:
    ├─ Exact match found → apply canonical stage mapping
    ├─ Fuzzy match found (edit distance <= 2) → apply with FLAG_FOR_CEP
    └─ No match → FLAG_FOR_CEP with stage_name; confidence = Low
  VALIDATE completeness:
    canonical stage "Closed Won" must map from exactly one stage_name
    canonical stage "Closed Lost" must map from exactly one stage_name
    ├─ Zero "Closed Won" mappings → FLAG: pipeline cannot be complete
    └─ Multiple "Closed Won" mappings → FLAG_FOR_CEP: ambiguous closure
  RECORD resolved mapping in CEP.stage_mapping[RecordType.id]:
    {stage_name_raw: stage_canonical, confidence: H/M/L}
  FOR all Opportunities of this RecordType:
    opportunity.stage_canonical = CEP.stage_mapping[RecordType.id][StageName]

4.4 Owner Hierarchy Construction
Salesforce User.ManagerId builds a reporting hierarchy equivalent to the organizational hierarchy in HRIS. For pipeline rollup calculations (e.g., pipeline by VP of Sales, which includes all direct and indirect reports), the hierarchy must be traversed from leaf to root.
BUILD owner hierarchy:
  1. Extract all active Users with ManagerId (Section 1.4)
  2. Build adjacency list: {user_id: manager_id}
  3. Validate: no cycles (a user cannot be their own manager, directly or transitively)
     ├─ Cycle detected → FLAG the specific user IDs forming the cycle; break cycle
     └─ No cycle → hierarchy is valid
  4. Assign depth: root users (no manager) = depth 0; each report level +1
  5. For each Opportunity: record owner_hierarchy_path from owner to root
     This enables pipeline aggregation at any level of the hierarchy
ADDITIONALLY — if Territory Management 2.0 active:
  Build parallel Territory hierarchy (separate from User hierarchy)
  Record Opportunity.Territory2Id → Territory hierarchy path
  Pipeline can be aggregated by both User hierarchy AND Territory hierarchy independently
4.5 Campaign Attribution Normalization
Salesforce's Campaign attribution model uses a Primary Campaign Source (Opportunity.CampaignId) plus multi-touch attribution via CampaignMember. SMPL's canonical Campaign Attribution model captures both.
PRIMARY ATTRIBUTION:
  opportunity.campaign_id → Opportunity.CampaignId
  Map to Campaign canonical object if CampaignId is non-null
MULTI-TOUCH ATTRIBUTION (if Campaigns active):
  SOQL: SELECT CampaignId, LeadOrContactId, Status
        FROM CampaignMember
        WHERE LeadOrContactId IN ({all Contacts on this Opportunity})
  Creates MQL Attribution Movement records linking Campaigns to Contacts
  to Opportunities through the Contact role path
  CONFIDENCE: D-M — multi-touch attribution via CampaignMember is available
  but requires the customer to have maintained Campaign membership records
  consistently, which is not universal even when Campaigns are active.

Section 10 — AI Implementation Workflow
Salesforce is the most workflow-intensive CRM implementation in this library due to Record Type proliferation. The workflow branches multiple times before any canonical Opportunity mapping begins.
SALESFORCE — IMPLEMENTATION WORKFLOW
DISCOVER:
  1. OAuth authentication + Org ID + environment type (Production/Sandbox)
  2. RECORD TYPE INVENTORY — all active Opportunity Record Types
     "This step is the Salesforce equivalent of ACDOCA ledger designation.
     Every active Record Type must be inventoried before mapping begins."
  3. Module inventory (Collaborative Forecasts, TM2, CPQ, Campaigns)
  4. Sales hierarchy extraction (Users + Managers)
  5. Territory hierarchy (if TM2 active)
  6. Custom ARR object inquiry during Pre-POC Discovery
BRANCH 1 — Multiple active Record Types?
  YES (typical for enterprise Salesforce):
    BRANCH for each RecordType — independent stage resolution required
    Begin CEP stage resolution for all RecordTypes simultaneously
    DO NOT wait for one before starting others
  NO → Single stage taxonomy; proceed to Stage Resolution Gate
STAGE RESOLUTION GATE (unique to CRM library):
  CEP.stage_mapping must be complete for ALL active Record Types
  ├─ All resolved → pipeline capabilities proceed normally
  ├─ Partial resolution → extract with UNRESOLVED tags; capabilities PARTIAL
  └─ Zero resolution → extract with all stages UNRESOLVED;
                         capabilities degraded to 40% confidence ceiling
  NOTE: Unlike ERP BLOCK conditions, this is a confidence degradation gate,
        NOT an extraction BLOCK. Extraction proceeds; confidence reflects resolution status.
ANALYZE: Map all objects (Table IMS-101.2.1)
NORMALIZE:
  Stage normalization per RecordType (Section 4.1)
  Forecast category normalization (Table IMS-101.4.2)
  Opportunity type normalization (Table IMS-101.4.3)
  Campaign attribution (Section 4.5)
TRANSFORM:
  Owner hierarchy construction (Section 4.4)
  Territory hierarchy (if TM2 active)
  Period-level pipeline aggregates (after all Opportunities populated)

IMS-102 — HubSpot CRM
HubSpot is the fastest CRM implementation in this library for standard configurations. Its more opinionated data model — fewer customization surface areas than Salesforce, a standardized default stage taxonomy, and native Marketing Hub integration — means the implementation agent can proceed to canonical population faster with less CEP resolution. The primary complexity drivers are multiple deal pipelines (when present) and Sales Hub/Marketing Hub tier mismatches (which affect GTM capability availability).
✱ ARCHITECT NOTE: Key departure from Salesforce IMS: HubSpot uses Deals (not Opportunities), Companies (not Accounts), and the Property History API (not OpportunityHistory) for stage-change audit trails. HubSpot's single Object Schema means there are no Record Types — a Deal always has the same base field set, with pipeline assignment determining the applicable stage taxonomy rather than a Record Type designation. This simplifies the stage resolution workflow considerably: one pipeline = one stage set to resolve, not one Record Type = one stage set.

Section 4 — Transformation Rules
4.1 Pipeline Stage Normalization
HubSpot stage normalization differs from Salesforce's in one important way: HubSpot stages are identified by opaque ID strings (e.g., "appointmentscheduled"), not display names. The implementation agent must first map stage IDs to display names, then map display names to canonical stages.
FOR EACH active pipeline in CEP.active_pipelines:
  pipeline_stages = CEP.pipelines[pipelineId].stages
  FOR each {stageId, label} in pipeline_stages:
    STEP 1: ID → Display Name (already available from pipeline inventory)
    stage_display_name = pipeline_stages[stageId].label
    STEP 2: Display Name → SCBM Canonical Stage
    LOOKUP in HubSpot Standard Stage Pattern Library:
    ├─ Exact match (standard HubSpot stage) → D-H confidence
    ├─ Fuzzy match → FLAG_FOR_CEP; apply tentative mapping with D-M confidence
    └─ No match → FLAG_FOR_CEP with display_name; Low confidence until resolved
    RECORD: CEP.stage_mapping[pipelineId][stageId] = {
      stage_canonical, confidence, display_name
    }
    VALIDATE: hs_probability field for Closed Won stage should be 1.0 (100%)
    Validate: Closed Lost stage should have hs_probability = 0.0
    These are HubSpot-enforced defaults; deviation indicates custom override.

IMS-103 — Microsoft Dynamics 365 Sales
Dynamics 365 Sales shares the Dataverse platform and OData API surface with Dynamics 365 Finance (IMS-004). This shared foundation means the implementation agent can reuse the authentication pattern and OData query construction from IMS-004, while applying CRM-specific canonical object mapping logic. The primary CRM-specific complexity driver is the Business Process Flow (BPF) model — Dynamics 365 Sales's equivalent of Salesforce's Record Types.
✱ ARCHITECT NOTE: Key departure from HubSpot IMS: Dynamics 365 Sales uses Business Process Flows (BPFs) as its stage management mechanism — a more flexible but less standardized model than either Salesforce Record Types or HubSpot Pipelines. Multiple BPFs can be active for the same Opportunity, and BPF stage configurations carry less SMPL implementation history than Salesforce's or HubSpot's equivalent structures. The implementation agent should expect to accumulate new pattern data during early Dynamics 365 Sales implementations that is not yet in the SMPL Tier 2 pattern library.

Sections 5–10 Summary — Dynamics 365 Sales
Sections 5 through 10 follow the identical structure established in IMS-101 (Salesforce) and IMS-102 (HubSpot) with Dynamics 365 Sales-specific content. Key differences:
Validation (Section 5): BPF stage normalization gate applies the same logic as Salesforce Record Type gate — pipeline capabilities capped at 40% until BPF stages resolved. Additional validation: Dataverse change tracking activation must be confirmed before incremental sync is trusted.
Canonical Population (Section 6): BPF stage resolution gate at Step 6, same position as Salesforce and HubSpot. Opportunity stage requires processsession join, not a direct Opportunity field — this additional query step is documented as a unique performance consideration for large D365 implementations.
Confidence (Section 7): All base confidence scores are reduced by 10–15% relative to Salesforce/HubSpot equivalents, reflecting Validated (Level 2) maturity — consistent with the maturity-based confidence framing established in the CKR registry and applied across the ERP library for Validated-maturity connectors.
Capability Activation (Section 8): Win Rate Analysis is READY (binary outcome regardless of BPF stage taxonomy). Pipeline Analytics and Waterfall are PARTIAL until BPF stages resolved and additional SMPL implementation experience accumulates. Section 4 — Transformation Rules (Excerpt — Audit Log Stage Extraction)
The Audit Log stage extraction is the most technically distinctive transformation in this library. It applies only to Zoho CRM and requires careful processing to reconstruct a reliable stage-change event sequence from a general-purpose activity log.
AUDIT LOG-BASED STAGE HISTORY EXTRACTION:
  STEP 1: Retrieve Audit Log for Deals
  GET /crm/v2/settings/auditlog?module=Deals&action=edit
  Filter: entries where changed_fields includes "Stage"
  STEP 2: For each audit log entry with Stage change:
    Record: deal_id, old_value (previous stage), new_value (new stage), modified_time
  STEP 3: Sort by modified_time (ascending) per deal_id
    Reconstruct the stage-change sequence for each Deal
  STEP 4: Apply stage normalization to old_value and new_value
    Same CEP.stage_mapping logic as other CRM connectors
  VALIDATION: Cross-check reconstructed stage history against
    current Deal.Stage — the final entry in the reconstructed history
    must match the current stage (or flagged as a data integrity issue)
  CONFIDENCE: D-M (not D-H) — audit log extraction is less reliable than
    dedicated history objects because:
    - Audit logs may be paginated differently from financial APIs
    - Some older audit entries may be purged per Zoho's retention policy
    - Concurrent edits can produce log entries in unexpected order
Section 4.4 — Zoho Books Cross-Validation (When Zoho One Active): When the customer uses Zoho Books alongside Zoho CRM within a Zoho One suite, the Contact and Account entities may be shared. The implementation agent checks for shared entity IDs and, when confirmed, uses this for higher-confidence identity resolution between CRM Deals and Zoho Books invoices — a compound-mapping opportunity unique to Zoho One customers.
Sections 5–10 Summary — Zoho CRM
Section 5 (Validation): Audit Log completeness check — the implementation agent validates reconstructed stage history against expected Deal count. Missing history for > 5% of Deals produces a FLAG.
Section 6 (Population): Audit Log stage extraction runs as a separate step after standard Deal population. Zoho One: Books entity cross-reference step if CEP.zoho_one_active.
Section 7 (Confidence): Audit Log stage events receive D-M base (vs. D-H for Salesforce OpportunityHistory and HubSpot Property History). Zoho One Books cross-validation: +10% on identity confidence when active.
Section 8 (Capability Activation): Win Rate Analysis READY (binary outcome); Pipeline Waterfall PARTIAL (audit log confidence ceiling); GTM Dashboards PARTIAL (Zoho Campaigns activation varies). Validated maturity reduces all non-binary capabilities to PARTIAL until additional implementations accumulate.
Section 9 (Exception Handling): Audit log retention limit exception — if Zoho has purged older entries, historical pipeline waterfall data will be incomplete. This is flagged explicitly as a data artifact, not a mapping error.
IMS-105 — Pipedrive
Pipedrive is the simplest CRM implementation in this library — a deliberately narrow, opinionated object model with the lowest CEP discovery burden and the fastest path to canonical Opportunity population. Its implementation philosophy is QBO-equivalent in the CRM domain: simpler schema, faster implementation, structural ceilings on forecasting and territory sophistication.
✱ ARCHITECT NOTE: Key departure from every other CRM in this library: Pipedrive has NO vendor-default stage names. Every customer defines their pipeline from scratch, including what stage names they use and what order they appear. This means the stage normalization gate is universally required and CEP resolution is non-negotiable — there is no pattern library shortcut available for Pipedrive stage normalization. This is simultaneously the connector's primary complexity driver and its primary speed advantage once resolved: a narrow, consistent object model with few CEP resolution edge cases beyond stages.

4.2 Deal Flow Log — Stage Event Reconstruction
Pipedrive's deal flow log (GET /api/v1/deals/{id}/flow) is a reliable, structured event log that records stage changes with timestamps — more directly usable than Zoho's Audit Log, though it requires per-deal requests rather than a single bulk endpoint.
FOR each active or recently closed Deal:
  GET /api/v1/deals/{id}/flow
  Filter: items where object = "dealChange" and field.field_key = "stage_id"
  FOR each matching flow event:
    Record: deal_id, old_stage_id, new_stage_id, log_time
    Apply: CEP.stage_mapping[pipeline_id][old_stage_id] → old_canonical
           CEP.stage_mapping[pipeline_id][new_stage_id] → new_canonical
  Performance note: Pipedrive's narrow object model and typically smaller
  deal counts (SMB customer base) mean per-deal flow requests are
  practical at the scale of Pipedrive implementations.
  For larger Pipedrive deployments (Power/Enterprise tier with many deals):
  implement parallel requests with rate limit awareness.

Closed Won ≠ Confirmed Revenue — Cross-CRM Reminder
This principle is universal across all five CRM connectors and is restated explicitly here, once, rather than in every connector's executive summary:
Every CRM connector in this library records commercial intent, not financial reality. A Deal, Opportunity, or BPF record marked Closed Won confirms that a sales representative recorded a win — it does not confirm that a subscription was created, an invoice was sent, or that cash was collected. Trusted Financial Intelligence from CRM data requires Billing cross-validation for bookings confirmation and ERP cross-validation for revenue-to-pipeline correspondence. This principle is applied without exception across all five CRM connectors and all five Billing connectors in the SMPL Implementation Mapping Library.

Final Determination
The CRM Implementation Mapping Specification Library (IMS-101 through IMS-105) is complete. Implementation agents and human consultants have sufficient implementation knowledge to begin onboarding any Tier 1 CRM platform. Billing IMS Library development may begin.
The CRM library introduces one implementation concept that had no equivalent in the ERP library: the confidence degradation gate (as opposed to the ERP library's extraction BLOCK). CRM data can be extracted regardless of stage resolution status — but pipeline capabilities are capped at 40% confidence until stage normalization is complete. This is the correct behavior: a partially-resolved CRM provides valuable data (account identity, opportunity amounts, owner assignment) even while stage normalization is ongoing, and blocking all extraction while a single stage is unresolved would unnecessarily delay value delivery.
The cross-connector pattern that emerges from building all five CRM specs simultaneously: every CRM connector's most consequential confidence variable is not the connector's maturity level — it's the customer's stage taxonomy resolution status. A Validated-maturity connector with fully resolved stages produces higher pipeline confidence than a Production-Ready connector with unresolved stages. This means the implementation agent's highest-priority action in any CRM implementation is stage resolution, regardless of which connector is being implemented.
