Section 0 — Engineering Context and Pre-Build Design Decisions
EIS-003 operationalizes the ABS-011 AI Role Playbooks into production prompt artifacts: system prompts, execution configurations, tool permission grants, output schemas, evaluation tests, and deployment governance. Three design decisions address execution risks identified during the playbook specification that must be resolved at the prompt engineering layer.
 
0.1 Design Decision 1 — Task-Level Temperature Overrides
Problem: The ABS-011 playbooks assign roles to workers, but each Connector Worker executes multiple task types within a single job — some deterministic (account type normalization, required field validation, confidence calculation) and some requiring controlled variation (fuzzy stage name matching, custom field business meaning assessment, CEP question text generation). A single temperature setting per role produces either brittle fuzzy matching or non-deterministic normalization.
Solution: The Prompt Registry defines a base temperature per role and a task_type_overrides map that the runtime applies when the agent's active task is deterministic. The override is enforced by the Agent Runtime Service before each LLM call — it is not left to the prompt to self-regulate. Temperature overrides are:

0.2 Design Decision 2 — Prompt Assembly Budget
Problem: Injecting the full CEP snapshot, the active IMS section, extraction state, prior log summary, gate state, and tool list into a single prompt context can exhaust the available context window before the agent has capacity for reasoning. This is most acute for Connector Workers executing Section 5 (Validation) after extracting a large object set — validation state summaries, IMS validation rules, and canonical object references compete for the same context.
Solution: The Prompt Assembly Budget allocates a maximum token count per variable category. The Agent Runtime Service enforces these budgets during prompt construction — if a variable exceeds its budget, the overflow handler for that category is applied before injection. Budgets are designed for a 16,000-token effective context (accommodating major model context windows with a safety margin).

0.3 Design Decision 3 — Machine-Executable Evaluation Scenario Schema
Problem: "Each scenario should include expected decisions, expected status, expected tool calls, and expected outputs" describes manual test cases. Without a machine-executable format, these scenarios are documentation that degrades into specifications nobody verifies. Every prompt version change should trigger automated scenario execution as a CI gate.
Solution: Evaluation scenarios are stored as structured JSON alongside each prompt version. The SMPL Prompt Test Harness (defined in Section 7) consumes these scenarios and asserts against them. A prompt version cannot be deployed until all its evaluation scenarios pass. The schema is defined in Section 7.1.
 
Section 1 — Prompt Registry Structure
The Prompt Registry is a versioned store of all production prompt configurations for SMPL. Every AI role execution — every Connector Worker job, every CAL assessment, every CEP question — is governed by a registry entry. No LLM call happens without a registry-traced prompt.
 
1.1 Registry Entry Format
Every Prompt Registry entry is a structured record in Postgres with an associated prompt body file in version control. The Postgres record is the metadata and execution configuration; the version-controlled file is the prompt text. Both are required — the runtime loads the Postgres record to find the file version; it loads the file to construct the prompt.
 
prompt_registry table (Postgres):
  prompt_id           VARCHAR(64) PRIMARY KEY
             -- Format: PR-{NNN}_{ROLE_NAME}
             -- Examples: PR-001_IMPLEMENTATION_COORDINATOR
             --           PR-006_ERP_DOMAIN_AGENT
  version             VARCHAR(16) NOT NULL
             -- Semantic version: MAJOR.MINOR.PATCH
             -- PATCH: wording changes only (no behavior change)
             -- MINOR: new optional output fields (backward compatible)
             -- MAJOR: output schema changes or behavior changes
  role_playbook_id    VARCHAR(16) NOT NULL
             -- Reference to ABS-011 playbook: APB-001 through APB-012
  owning_worker_type  VARCHAR(32) NOT NULL
             -- ORCHESTRATOR | CONNECTOR | CANONICAL | CAPABILITY | REPORTING
  execution_contexts  VARCHAR[] NOT NULL
             -- When this prompt is loaded (may be multiple)
             -- Examples: session_start, erp_implementation, canonical_merge
  base_temperature    DECIMAL(3,2) NOT NULL
             -- Role-level base temperature; task-level overrides in model_settings
  max_tokens          INTEGER NOT NULL
             -- Maximum response tokens for this role
  model               VARCHAR(64) NOT NULL
             -- The specific model version this prompt is tested against
             -- Example: gpt-4o-2024-11-20 | claude-opus-4-6
  tool_choice         VARCHAR(32) NOT NULL
             -- auto | required | none
             -- required: model MUST use a tool (for data retrieval steps)
             -- none: model MUST NOT use tools (for pure reasoning steps)
             -- auto: model chooses (for mixed steps)
  prompt_file_ref     VARCHAR(256) NOT NULL
             -- Path to prompt body file in version control
             -- Example: prompts/PR-001_IMPLEMENTATION_COORDINATOR/v1.0.0.md
  output_schema_ref   VARCHAR(256) NOT NULL
             -- Path to JSON Schema file for output validation
  allowed_tools       VARCHAR[] NOT NULL
             -- Tool names from EIS-001; Tool Gateway enforces
  cep_read_scope      VARCHAR[] NOT NULL
             -- Dot-notation CEP field paths this prompt may read
  deployment_status   VARCHAR(32) NOT NULL
             -- DRAFT | REVIEW | APPROVED | ACTIVE | DEPRECATED | SUNSET
  created_at          TIMESTAMPTZ NOT NULL
  created_by          UUID NOT NULL
  approved_by         UUID
             -- Required for APPROVED status; null for DRAFT and REVIEW
  deployed_at         TIMESTAMPTZ
  sunset_at           TIMESTAMPTZ
             -- Date after which this version may not be used; old versions retained for audit
  evaluation_pass     BOOLEAN NOT NULL DEFAULT false
             -- Set to true only when all evaluation scenarios pass
             -- ACTIVE status requires evaluation_pass = true

System Prompt
You are the SMPL Implementation Coordinator. You orchestrate the end-to-end execution of SMPL customer implementations from Customer Discovery through Financial Intelligence Ready. Your job is routing, not implementation: you dispatch agents, track job statuses, advance SOF stages, and route human-in-the-loop decisions. You have exactly four decision outputs available for every situation you encounter: CONTINUE (proceed automatically), PAUSE_FOR_CEP (route a business decision to the CEP Agent), ESCALATE (surface a complex condition to the human Implementation Consultant), or ERROR (log a technical failure and apply the retry policy). If you cannot determine which of these four applies, choose ESCALATE — it is always safer to surface ambiguity than to proceed incorrectly.

Section 4 — Prompt Execution Lifecycle
This section documents the complete lifecycle of a single prompt execution — from job receipt through output artifact storage. Engineers implementing the Agent Runtime Service use this as the execution protocol.
 
4.1 Execution Protocol
PROMPT EXECUTION LIFECYCLE (Agent Runtime Service):
01. Worker dequeues job from queue.
    Loads job fields: role_playbook_id, task_type, task_payload, allowed_tools.
02. Resolve prompt_id from role_playbook_id:
    SELECT prompt_id FROM prompt_registry
    WHERE role_playbook_id = {job.role_playbook_id}
    AND deployment_status = 'ACTIVE'
    AND evaluation_pass = true
    ORDER BY version DESC LIMIT 1
03. Load prompt registry entry from Postgres.
    Load prompt body file from version control at prompt_file_ref.
    Load output schema from output_schema_ref.
04. Validate required inputs:
    Check that all required_inputs for this prompt are present in job.task_payload.
    If any required input is missing → return ERROR: INVALID_INPUT immediately.
    Do not attempt LLM call with missing inputs.
05. APPLY PROMPT ASSEMBLY BUDGET (Section 0.2):
    For each variable category, measure token count.
    If over budget, apply overflow handler for that category.
    Apply budget overflows in order: IMS section → CEP snapshot → gate state
    → tool list → log summary. Never truncate system prompt or task description.
06. Inject scoped variables into Variable Injection Template:
    SECURITY CHECK: scan all injected variables for raw credential patterns.
    Pattern: sk_live_*, Bearer *, api_key=, password=, -----BEGIN PRIVATE KEY-----
    If any match found: BLOCK injection; emit SECURITY_VIOLATION audit event;
    return ERROR: INVALID_INPUT.
07. Configure model settings:
    model = prompt_registry.model
    temperature = prompt_registry.base_temperature
    max_tokens = prompt_registry.max_tokens
    tool_choice = prompt_registry.tool_choice
    tools = [Tool Gateway schema for each tool in prompt_registry.allowed_tools]
08. APPLY TASK-LEVEL TEMPERATURE OVERRIDE (Section 0.1):
    IF job.task_type IN task_type_override_map:
      temperature = task_type_override_map[job.task_type]
    Tool Gateway receives the final temperature with each tool call.
09. Execute LLM call via Agent Runtime Service:
    All LLM calls route through Agent Runtime Service — never directly to provider.
    Emit PROMPT_EXECUTED log event: {prompt_id, prompt_version, model, temperature,
      input_token_count, max_output_tokens}.
10. TOOL CALL LOOP:
    While model returns tool_use blocks:
      For each tool_use block:
        a. Forward to Tool Gateway: {tool_name, inputs, agent_id, session_id,
           allowed_tools_list}
        b. Tool Gateway enforces: permission check, rate limit, idempotency,
           PII redaction for logs.
        c. Tool Gateway returns result.
        d. Append result to conversation as tool_result block.
      Continue conversation with tool results included.
11. Validate output against JSON schema from output_schema_ref:
    If validation fails: retry once with an error feedback message appended.
    If second attempt also fails: return ERROR: INTERNAL_ERROR with validation details.
12. Write outputs:
    Store output artifacts in object storage (keyed by job_id).
    Update job.output_artifact_refs in Postgres.
    Emit JOB_COMPLETE log event.
13. Return job response to Agent Orchestration Service.
    Job status → COMPLETE | COMPLETE_WITH_GAPS | PARTIAL | PAUSED_FOR_CEP |
                  BLOCKED | ESCALATED | ERROR.
