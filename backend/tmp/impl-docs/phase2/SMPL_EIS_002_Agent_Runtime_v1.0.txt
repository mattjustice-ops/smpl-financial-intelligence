Section 0 — Engineering Context and Pre-Build Design Decisions
EIS-002 defines the runtime that executes the SMPL platform. It translates the EIS-001 tool contracts into deployable workers, services, queues, state stores, and recovery mechanisms. Three design decisions in this document address execution risks identified during the tool registry and playbook specification phases.
 
0.1 Design Decision 1 — IMS Pre-Fetch Strategy
Problem identified: The IMS Content Service serves sections on-demand via get_ims_section. If a Connector Worker fetches IMS sections mid-extraction — between individual record transformations — retrieval latency accumulates in the implementation critical path. A SAP ACDOCA extraction with 500,000 records, pausing to fetch Section 4.2 (signed amount convention) mid-batch, adds unacceptable latency.
Solution: IMS Pre-Fetch runs as the first step of every Connector Worker job, before any extraction begins. When the Connector Worker receives a job, it calls load_ims_spec with the execution_stage parameter for each stage it will execute (typically DISCOVER through POPULATE), receives the section index with estimated_token_count per section, fetches all sections relevant to that connector and stage set, and loads them into worker-local memory before the first extract_object_batch call. Retrieval is moved entirely out of the extraction critical path.
Pre-fetch budget: Connector Workers are allocated a pre-fetch token budget of 32,000 tokens per job invocation. For connectors whose total IMS content exceeds this budget (SAP, Oracle Fusion), the pre-fetch prioritizes sections by execution_stage order and fetches remaining sections on demand between extraction batches — not between individual records. The pre-fetch manifest is stored as a job checkpoint so that recovery after failure does not re-fetch already-loaded sections.
 
0.2 Design Decision 2 — Fan-Out / Fan-In Job Dependency Graph
Problem identified: The SOF requires COORD-001 to advance to Stage 4 (Canonical Integration) only after all parallel Connector Worker jobs reach terminal status. Without a defined mechanism for knowing when all parallel children are complete, the Orchestrator Worker must poll each child job indefinitely — creating O(n) polling overhead that scales with connector count.
Solution: The job queue uses an explicit dependency graph model. Every job has a parent_job_id and optional dependency_job_ids. The Orchestrator Worker creates a fan-out job group at Stage 3 dispatch — one parent job (the Stage 3 coordination job) with N child jobs (one per Connector Worker). The queue service tracks the parent job's completion gate: the parent moves from RUNNING to COMPLETE only when all child jobs reach terminal status (COMPLETE, COMPLETE_WITH_GAPS, or PARTIAL). Stage 4 is dispatched as a job with dependency_ids pointing to the Stage 3 parent job — it cannot dequeue until the dependency is satisfied.
Partial completion handling: If a Connector Worker job reaches BLOCKED or ERROR with retry_exhausted, it is marked as TERMINAL_BLOCKED. The parent job's completion gate treats TERMINAL_BLOCKED as satisfying the child's gate condition — the Stage 4 job dispatches with the available canonical objects, and the TERMINAL_BLOCKED connector is flagged in the Session State for human resolution. This prevents a single blocked connector from holding up the entire implementation indefinitely.
 
0.3 Design Decision 3 — Memory Tier Model
Problem identified: The EIS-002 brief includes "implementation patterns," "resolved mappings," and "historical error resolutions" in the memory scope. Without a strict tier model, there is a governance risk: customer-specific implementation data could inadvertently flow into a shared pattern cache, violating customer data isolation.
Solution: Memory is divided into three tiers with strict boundary enforcement at the Implementation Memory Service layer:
Tier 1 — Customer-Scoped Memory: all data derived from a specific customer's implementation. Scoped strictly to that customer's session and canonical store. Never shared across customers. Examples: CEP decisions, resolved stage mappings, confirmed FTE methodology. Retained for the duration of the customer relationship; deleted on customer offboarding.
Tier 2 — Anonymized Pattern Cache: connector-specific patterns derived from multiple implementations, with all customer-identifying data removed before storage. Examples: common stage name → canonical stage mappings (e.g., "Proposal" → Proposal with D-H confidence in 94% of Salesforce implementations), common account type edge cases, typical SAP ACDOCA filter patterns. Populated only through an explicit generalization pipeline that strips customer context before writing.
Tier 3 — Engineering Knowledge Base: SMPL-authored patterns, IMS content, CKR data, and playbook specifications. Read-only at runtime. Updated only through architecture releases, not from customer data.
Boundary enforcement: the Implementation Memory Service API enforces tier boundaries at write time. A write to Tier 2 requires an anonymization_certificate — a signed attestation that the generalizing pipeline has stripped customer-identifying data from the input. The API rejects Tier 2 writes without this certificate. Customer data never reaches Tier 2 or Tier 3 without explicit human-reviewed generalization.
 
Section 1 — Worker Model
The SMPL runtime deploys five worker types for MVP. Each worker is a long-running process that dequeues jobs, loads the relevant role playbook, calls tools through the Tool Gateway, and returns results to the job queue. Workers are stateless between jobs — all persistent state lives in the Session State Store, CEP Service, and Canonical Data Service.

1.2 Orchestrator Worker — Specification
The Orchestrator Worker is the runtime's SOF executor. It owns one implementation session end-to-end and runs continuously for the session's duration. At MVP, one Orchestrator Worker instance per active implementation session is the correct scaling model — sessions are infrequent enough that per-session isolation is both practical and desirable.
 
Property
Specification
Process model
Long-running async process; one per active session; terminates on session COMPLETE or ERROR_UNRECOVERABLE
Memory footprint
Low — Orchestrator holds session_state and CEP snapshot in memory; all durable state is in Session State Store; target < 256MB RSS per instance
Playbooks loaded
APB-001 and APB-002 loaded at process start; no dynamic playbook loading during session
LLM usage
Minimal — Orchestrator uses LLM only for: (a) parsing ambiguous human responses to CEP questions, (b) generating escalation summaries for human consultants. All SOF routing logic is deterministic and does not require LLM inference.

Failure behavior
On Orchestrator Worker crash: Session State Store preserves all state; a new Orchestrator Worker instance loads the session_state checkpoint and resumes from the last completed stage. Recovery is automatic with no data loss if checkpoints are written correctly (see Section 5).
CEP embedding
COORD-002 logic runs in the same process as COORD-001 at MVP. The CEP Service is a separate data store; the Orchestrator Worker calls it via the Tool Gateway like any other service. Separation of concerns is maintained at the data layer; the process consolidation is an MVP deployment decision only.

1.3 Connector Worker — Specification
The Connector Worker is the most resource-intensive worker in the system. It handles data extraction, transformation, and canonical population for one connector domain per job. Multiple Connector Worker instances run in parallel during Stage 3.
 
Property
Specification
Process model
Job-scoped process; starts when a connector job is dequeued; terminates when job reaches terminal status. Multiple instances run in parallel — one per active connector domain job.
Memory footprint
Higher than other workers due to extraction batch buffering. Target < 1GB RSS per instance for standard connectors; < 2GB for high-volume ERP connectors (SAP, Oracle Fusion). Extraction batches are streamed to object storage, not held in memory.
Playbooks loaded
One domain playbook per job (APB-006, APB-007, APB-008, or APB-009). Connector-specific sub-agent behavior is encoded in the playbook and IMS sections — no sub-agent processes are spawned.
LLM usage
Moderate — LLM is used for: (a) executing transformation rules that cannot be expressed as pure functions (e.g., fuzzy stage name matching, custom field business meaning assessment), (b) parsing ambiguous API responses when IMS section does not cover the specific edge case, (c) generating PAUSE_FOR_CEP question text. All normalization, validation, and confidence calculation is deterministic and does not use LLM.
IMS pre-fetch
On job start: load_ims_spec → fetch all sections for this connector and execution stage set → store in worker-local cache keyed by section_id. See Section 0.1 for pre-fetch budget and overflow handling.
Extraction streaming
extract_object_batch returns an extraction_id, not records. Records are fetched in pages via get_extracted_records with record_limit=100 (configurable). This prevents large extraction batches from filling the worker's memory or context window.
Gate enforcement
Domain-specific gate logic (Subscription Normalization Gate, Stage Normalization Gate, Organizational Normalization Gate, ERP pre-extraction gates) is enforced by the worker before dispatching extraction jobs. Gate enforcement is deterministic — the worker reads the gate status from CEP via read_cep and either proceeds or emits a PAUSE_FOR_CEP response without calling LLM.
Failure behavior
On Connector Worker crash mid-extraction: the job is returned to the queue with retry_count incremented. The next worker instance resumes from the last written extraction checkpoint (page_cursor stored in job state). No re-extraction of already-processed batches.

2.2 Tool Gateway — Detail
The Tool Gateway is the most critical single service in the runtime. Every tool call from every worker passes through it. It is the enforcement point for permissions, logging, rate limits, tool versioning, and PII redaction.
 
Responsibility
Implementation
Permission enforcement
On every inbound tool call: verify agent_id is in the tool's callable_by list (from EIS-001 tool registry). Reject with PERMISSION_ERROR if not. This is enforced at the gateway — workers cannot bypass by calling services directly.
Tool version enforcement
Tool registry includes the current version and sunset versions for each tool. Calls to sunset versions are rejected after the sunset date. Workers must specify tool_version in every call.
Audit logging
Every tool call → write to Logging Service before routing to the target service (request log). Every tool response → write to Logging Service after receiving the response (response log). Two log events per tool call minimum.
PII redaction
Input parameters are passed through redact_sensitive_fields at classification_level=LOG_SAFE before writing to logs. The original unredacted inputs are forwarded to the target service — redaction applies to logs only, not to execution.
Rate limit budget injection
For any tool in Category 3 or 4 (Connector Discovery and Data Extraction): the Tool Gateway queries the Connector Proxy Service for the current rate limit budget before routing the call. If budget = 0: return RATE_LIMIT_ERROR without calling the target service.
Idempotency enforcement
For IDEMPOTENT tools: check the idempotency cache (Redis, TTL 1 hour) for the idempotency_key. If found: return cached result immediately without calling the target service. If not found: call target service, cache result, return.
Health checking
Tool Gateway maintains a health status for each downstream service. If a service is unhealthy: return CONNECTOR_UNAVAILABLE or INTERNAL_ERROR immediately rather than timing out on the target call.
Table EIS2-2.2 — Tool Gateway responsibilities. The gateway is the single enforcement point — no worker should have code that bypasses it.
 
2.3 Connector Proxy Service — Detail
The Connector Proxy Service is the only service that holds or resolves raw customer credentials. It manages every external API call to customer systems. No other service or worker ever sends network requests to customer systems directly.
 
Responsibility
Implementation
Credential resolution
Receives credential_reference_id from Tool Gateway; resolves to actual credential by calling Credential Vault. The resolved credential is used for the API call and immediately discarded — never stored in Connector Proxy memory beyond the single request lifetime.
Read-only enforcement
Before every external API call: verify the HTTP method is GET (or the equivalent read operation for the connector's API style). Any attempt to use POST, PUT, PATCH, or DELETE against a customer system causes an immediate PERMISSION_ERROR and is logged as a SECURITY_VIOLATION audit event.
Rate limit management
Per-connector rate limit budgets tracked in Redis token buckets. Token bucket parameters (refill rate, capacity) are set from the IMS registry (IMS Section 1 rate limit documentation per connector). Budget allocation per session is computed at job dispatch time (see Section 4, Parallelism).
Response normalization
Connector Proxy normalizes HTTP response formats to a standard envelope before returning to the calling worker: {status_code, headers, body, connector_id, latency_ms}. Workers never parse raw HTTP responses — they work with normalized envelopes.
Sandbox/livemode enforcement
For connectors with sandbox/livemode distinction (Stripe, Chargebee, NetSuite): Connector Proxy reads the session's connector_environment from CEP before every call. If environment=SANDBOX but the credential resolves to a production endpoint (or vice versa), the call is rejected with a SECURITY_VIOLATION audit event.

3.3 Fan-Out / Fan-In Pattern
Stage 3 (Connector Implementation) is the primary fan-out point. The following is the exact job creation sequence for a four-connector implementation (NetSuite + Salesforce + Stripe + Workday):
 
STAGE 3 FAN-OUT — Orchestrator Worker creates:
  job_A (ORCHESTRATOR / STAGE_ADVANCE):     ← Stage 3 coordination job (parent)
    job_id: UUID-A
    parent_job_id: Stage_2_job_id
    dependency_job_ids: []   ← no dependencies; starts when Stage 2 COMPLETE
    status: RUNNING          ← Orchestrator sets RUNNING immediately on creation
  job_B (CONNECTOR / ERP_IMPLEMENT_IMS-001): ← NetSuite job
    parent_job_id: UUID-A
    dependency_job_ids: []   ← no dependencies; all connector jobs start in parallel
    status: QUEUED
  job_C (CONNECTOR / CRM_IMPLEMENT_IMS-101): ← Salesforce job
    parent_job_id: UUID-A
    dependency_job_ids: []
    status: QUEUED
  job_D (CONNECTOR / BILLING_IMPLEMENT_IMS-201): ← Stripe job
    parent_job_id: UUID-A
    dependency_job_ids: []
    status: QUEUED
  job_E (CONNECTOR / HRIS_IMPLEMENT_IMS-301): ← Workday job
    parent_job_id: UUID-A
    dependency_job_ids: []
    status: QUEUED
  ──────────────────────────────────────────────
  EXECUTION: jobs B, C, D, E run in parallel.
  Agent Orchestration Service tracks: pending_children[UUID-A] = {B, C, D, E}
  ──────────────────────────────────────────────
STAGE 3 FAN-IN — when each child job reaches terminal status:
  Agent Orchestration Service removes child from pending_children[UUID-A].
  IF pending_children[UUID-A] is EMPTY (or all remaining are TERMINAL_BLOCKED):
    SET job_A.status = COMPLETE
    TRIGGER creation of Stage 4 job:
  job_F (CANONICAL / CANONICAL_INTEGRATE):
    parent_job_id: Stage_4_coordination_job_id
    dependency_job_ids: [UUID-A]  ← depends on Stage 3 parent COMPLETE
    status: QUEUED → auto-dequeues when UUID-A COMPLETE

Section 5 — Checkpointing
Checkpoints allow the runtime to resume from a known-good state after worker failure without restarting a full implementation. Every major stage boundary produces a checkpoint. The rule: if an operation takes more than 2 minutes or produces data that would be expensive to re-generate, it checkpoints before completion.

5.2 Checkpoint Recovery Protocol
ON Orchestrator Worker restart (session_id known):
  1. LOAD session_state from Postgres WHERE session_id = {id}
  2. LOAD all active jobs WHERE session_id = {id} AND status IN (RUNNING, QUEUED)
  3. FOR each RUNNING job:
     IF job.worker_type = CONNECTOR AND job.checkpoint_ref IS NOT NULL:
       Mark job as RESUMING; re-queue with existing page_cursor
     IF job.worker_type = ORCHESTRATOR:
       Resume Orchestrator loop from current_sof_stage
     IF other worker types:
       Re-queue job (idempotent operations; safe to restart)
  4. FOR each QUEUED job:
     Verify dependencies still satisfied; re-queue if so
  5. RESUME normal Orchestrator loop
ON Connector Worker restart (job_id known):
  1. LOAD job from Postgres WHERE job_id = {id}
  2. LOAD checkpoint from object storage at job.checkpoint_ref
  3. RESTORE: page_cursor, pre-fetch manifest, canonical_population_progress
  4. CONTINUE from last checkpoint:
     IF checkpoint.phase = PRE_FETCH → skip to extraction
     IF checkpoint.phase = EXTRACTION → resume from page_cursor
     IF checkpoint.phase = TRANSFORMATION → resume from last canonical_id
     IF checkpoint.phase = POPULATION → resume from last upserted canonical_id
  5. COMPLETE job normally; write final checkpoint

6.2 Rate Limit Budget Allocation
ON Stage 3 dispatch (N connector jobs created for the same session):
  FOR each connector C in connector_list:
    max_rate = IMS_rate_limits[C.connector_id]  // from IMS Content Service
    active_sessions_using_C = Connector_Proxy.count_active_sessions(C.connector_id)
    // Platform-wide rate limit sharing across all customers
    platform_budget = max_rate / MAX(1, active_sessions_using_C)
    // Within-session budget (multiple domains on same connector is rare but possible)
    within_session_jobs = connector_list.count(connector_id == C.connector_id)
    session_budget = platform_budget / MAX(1, within_session_jobs)
    WRITE to Redis: rate_bucket:{session_id}:{connector_id} = {
      tokens: session_budget,
      refill_rate: session_budget per minute,
      last_refill: now()
    }
  Each extract_object_batch call:
    1. Tool Gateway checks rate_bucket:{session_id}:{connector_id}
    2. IF tokens >= 1: decrement; proceed with call
    3. IF tokens < 1: return RATE_LIMIT_ERROR with retry_after_seconds
       computed from refill_rate
    4. Response includes remaining_budget_pct for worker self-regulation

7.2 Failed Job Resume Protocol
WHEN a failed job is re-queued after error resolution:
  1. VERIFY the error condition is resolved:
     AUTH_ERROR: new credential_reference_id written to CEP
     CEP_REQUIRED: cep_field is now HUMAN_CONFIRMED or DEFAULT_APPLIED
     BLOCK_CONDITION: human resolution received and written to session_state
  2. LOAD job checkpoint from job.checkpoint_ref (object storage)
     IF checkpoint exists: resume from checkpoint phase
     IF no checkpoint (early-stage failure): restart job from beginning
     (idempotency of extraction and canonical writes prevents data duplication)
  3. INCREMENT job.retry_count
     IF retry_count > max_retries: TERMINAL_BLOCKED (do not re-queue)
  4. RE-QUEUE with same job_id (idempotency key ensures no duplicate)
     Priority: HIGH if the failure was blocking other jobs; NORMAL otherwise
  5. UPDATE session_state: remove from blocked_jobs; add back to active_job_ids
 
Section 8 — Human-in-the-Loop Runtime Behavior
Human input enters the runtime through two paths: the Implementation Consultant interface (which can write to the CEP, submit escalation responses, and confirm Stage 6 review) and the customer portal (which can answer specific CEP questions surfaced by COORD-002). All human input flows through the CEP Service — it never directly modifies job state.
 
8.1 CEP Question Lifecycle
CEP QUESTION LIFECYCLE (runtime sequence):
  1. Worker encounters a decision that cannot be auto-resolved.
     Worker returns PAUSED_FOR_CEP status with pending_cep_items in response.
  2. Orchestrator Worker receives PAUSED_FOR_CEP.
     Calls create_cep_question via Tool Gateway → CEP Service.
     Stores cep_item_id in session_state.pending_cep_items.
     Updates job status to PAUSED_FOR_CEP.
     Does NOT block other running jobs.
  3. Notification Service (triggered by CEP Service on item creation):
     BLOCKING urgency → immediate email + in-app notification to
       Implementation Consultant.
     NORMAL urgency → batched notification (max 4h delay).
     LOW urgency → included in next daily digest.
  4. Human responds via Implementation Consultant interface OR customer portal:
     Response written to CEP Service via update_cep (source = HUMAN_CONFIRMED).
     cep_item marked RESOLVED.
     Notification Service fires: CEP_ITEM_RESOLVED event.
  5. Orchestrator Worker receives CEP_ITEM_RESOLVED event (event-driven):
     OR detects via periodic session_state poll (every 30s fallback).
     Reads resolved value from CEP.
     Calls notify_waiting_agent for the blocked job.
     Re-queues blocked job with HIGH priority.
     Removes cep_item_id from session_state.pending_cep_items.
  6. IF no human response within:
     BLOCKING with default_value: 48h → apply default; log DEFAULT_APPLIED.
     BLOCKING without default_value: 48h → ESCALATE to human consultant.
     NORMAL: 72h → apply default if available; flag for Stage 6 review.
     LOW: 7 days → apply default; add to Stage 6 known_defaults list.
 
8.2 Stage 6 Customer Review — Runtime Behavior
STAGE 6 RUNTIME (Orchestrator Worker behavior):
  1. Orchestrator detects all Stage 5 jobs COMPLETE.
  2. Dispatches Reporting Worker: GENERATE_CUSTOMER_REVIEW_PACKET.
  3. Updates session_state: current_sof_stage = 6, status = PAUSED_FOR_HUMAN.
  4. Sends notification to Implementation Consultant:
     "Implementation review packet ready. Customer review session required."
  5. HALTS all further job dispatch until Stage 6 completion signal received.
     (This is the only mandatory human gate that completely pauses the runtime.)
  DURING Stage 6 session (what the Orchestrator still processes):
  - Incoming CEP resolutions from Stage 6 review session → written to CEP
  - New connector additions confirmed in Stage 6 → added to Stage 2 queue
    (will execute as a phased addition after Stage 7)
  STAGE 6 COMPLETION SIGNAL:
  Implementation Consultant submits: {
    session_id, confirmed_by: user_id,
    module_activation_plan: [{module_id, activate: bool}],
    deferred_cep_items: [{item_id, acknowledged_impact: string}],
    new_connectors_deferred: [{connector_id, planned_phase: integer}]
  }
  Orchestrator receives signal → writes to session_state → advances to Stage 7.

9.2 Memory Generalization Pipeline
The Memory Generalization Pipeline is a scheduled, human-reviewed process that promotes Tier 1 patterns to Tier 2. It is not a real-time operation — it runs after a minimum of 5 distinct customer implementations on the same connector before generalizing any pattern.
 
GENERALIZATION PIPELINE (runs nightly for eligible patterns):
  1. IDENTIFY candidate patterns from Tier 1:
     SELECT key_type, pattern_value, frequency
     FROM tier1_customer_memory
     GROUP BY key_type, connector_id, pattern_value
     HAVING count(DISTINCT customer_id) >= 5  ← minimum 5 distinct customers
  2. ANONYMIZE:
     Strip all customer_id references.
     Remove company names, email domains, and any PII from pattern values.
     Remove values that are statistically unique (appear in only 1 of N customers).
     Compute frequency: count(customers where this pattern appeared) / total_customers.
  3. GENERATE anonymization_certificate:
     {pipeline_run_id, connector_id, pattern_type, customer_count, anonymization_checks_passed: []}
     Signed by the pipeline service private key.
  4. WRITE to Tier 2 (requires anonymization_certificate):
     Implementation Memory Service verifies certificate signature before write.
     If certificate is invalid → write rejected; alert SMPL engineering.
  5. HUMAN REVIEW (weekly):
     SMPL implementation team reviews new Tier 2 patterns.
     Patterns that appear to contain customer-identifying information despite
     anonymization → removed; pipeline rule updated.
  WHAT NEVER GOES TO TIER 2:
  - Customer-specific CEP decisions (fiscal calendar, FTE methodology)
  - Stage mappings that are unique to one customer (non-generalizable)
  - Any value with frequency < 10% across the 5+ implementations
  - Compensation figures, ARR amounts, headcount numbers
