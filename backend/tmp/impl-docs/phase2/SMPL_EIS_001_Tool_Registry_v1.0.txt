Section 0 — Engineering Context and Design Decisions
EIS-001 defines the tool and interface layer that makes SMPL implementations executable by AI agents. It translates the frozen Phase 1 architecture into precise engineering contracts: tool signatures, error taxonomy, logging standards, agent invocation interfaces, and security boundaries. Three design decisions in this document go beyond the base ABS-011 scope — they address execution risks identified during playbook development that must be resolved at the engineering layer, not the architecture layer.
 
0.1 Design Decision 1 — IMS Retrieval Architecture
Problem: The IMS libraries contain ~300,000 words of connector-specific implementation logic across 21 connectors. An LLM agent cannot hold the full NetSuite IMS alongside live extraction state, CEP state, and validation logic in a single context window — and a parallel implementation running Oracle Fusion + Salesforce + Stripe + Workday simultaneously would generate irreconcilable context pressure if each agent tried to load its full IMS document.
Solution built into this document: IMS content is served to agents through a structured retrieval layer, not as full document loads. The load_ims_spec and get_connector_* tools (Category 5) implement semantic chunking — agents request specific IMS sections by section ID (e.g., IMS-001.Section_4.3) and receive only the content relevant to their current execution step. Each chunk is pre-indexed by connector ID, section number, and execution stage so the retrieval is deterministic, not semantic-search-based.
Implementation note for engineers: the IMS content store is a structured JSON document store keyed by {connector_id}.{section_id}.{subsection_id}. Each leaf node contains the executable content for that subsection — transformation rules, field maps, gate questions, validation thresholds — in a machine-readable schema alongside the human-readable text. Agents retrieve by key, not by similarity search. This produces deterministic, auditable IMS execution.
 
0.2 Design Decision 2 — Gate State Object and Pending-State UX
Problem: The Subscription Normalization Gate and Stage Normalization Gate are correct data integrity controls — but they create a period where customers see an incomplete product while they wait to answer policy questions. "ARR Reporting: PARTIAL" with no further explanation feels like a product failure rather than a deliberate data integrity protection.
Solution built into this document: a Gate State Object is introduced as a first-class data structure in the CEP and surfaced in every reporting tool output. The Gate State Object communicates three things customers need during a pending gate: (1) what capability is available right now on the data extracted so far, (2) exactly what question is pending and who needs to answer it, and (3) a real-time progress indicator showing how close the gate is to resolving. The Reporting Tools (Category 11) include mandatory pending-state output templates for every gate type.
Implementation note: the Gate State Object is not a new architecture concept — it is a formalization of information already present in the CEP resolution queue and the SOF session state. The engineering work is surfacing it consistently through all reporting paths.
 
0.3 Design Decision 3 — Cross-Domain Validation Gap Templates
Problem: The cross-domain validation matrix (SOF Table 4.2) produces flags when reconciliation thresholds are not met — but "FLAG: BOOKINGS_VALIDATION_GAP, count=47" tells an engineer what happened without telling the customer what it means or what to do about it. Without structured gap templates, every implementation consultant will frame these gaps differently.
Solution built into this document: every gap type in SOF Table 4.2 has a corresponding structured output template in the generate_gap_explanation tool (Category 11). Each template has three mandatory sections: WHAT WAS FOUND (quantified), WHY IT MATTERS (business implication in non-technical language), and WHAT TO DO NEXT (specific recommended action). These templates are part of the engineering contract — they cannot be replaced by ad hoc LLM generation for customer-facing communications about data gaps.
 
0.4 Document Scope
This document specifies 78 tools across 13 categories, the agent invocation interface, the agent response interface, the status taxonomy, the error taxonomy, the logging standard, the security model, the IMS retrieval architecture, the Gate State Object schema, and the cross-domain gap template specifications. It does not introduce new architecture — it translates the existing architecture into implementation contracts.

1.4 Security Baseline
Every tool operates under the following baseline security rules. Tool-specific additions are documented in each tool's Security Notes section.
CREDENTIAL REFERENCES ONLY. AI agents never receive raw API keys, OAuth tokens, or passwords. Agents receive a credential_reference_id which the Connector Proxy Service resolves to actual credentials at call time. Agents cannot read, log, or forward the underlying credential.
READ-ONLY AGAINST CUSTOMER SYSTEMS. No tool in Categories 1–11 and 13 may write to a customer's connected system. Only Category 7 (Canonical Data Tools) writes, and only to SMPL internal stores. Category 12 (Security Tools) manages SMPL credential store only.
ROLE-SCOPED TOOL ACCESS. Each agent's allowed_tools list is defined in its invocation context and enforced by the tool gateway. An agent may not call a tool not in its allowed_tools list regardless of how the request is constructed.
PII AND FINANCIAL DATA IN LOGS. Customer names, email addresses, compensation figures, revenue amounts, and account balances must never appear in log output_summary fields. Use counts, IDs, and confidence scores only.
TOOL VERSIONING. Every tool is versioned. Agents must specify the tool version they are calling. The tool gateway rejects calls to deprecated versions after the sunset date defined in the tool registry.

1.6 Rate Limit Budget Architecture
This section addresses the engineering implementation of connector rate limits — a requirement identified during playbook development. Every extraction tool that calls an external connector API operates within a rate limit budget managed by the Connector Proxy Service.
Budget Component
Description
Implementation
Per-connector rate limit
Each connector has a documented rate limit from its IMS Section 1 (e.g., Stripe: 100 req/min, Salesforce: governor limits by API type, SAP OData: Microsoft tier-dependent)
The Connector Proxy Service maintains a rate limit registry keyed by connector_id. Every external call is counted against the connector's budget before dispatch.
Budget allocation per session
For parallel implementations, each running agent receives a budget slice of the total connector rate limit
COORD-001 allocates budget at agent dispatch: budget_slice = connector_rate_limit / active_agent_count_for_this_connector
Budget reporting to agents
Each extraction tool response includes remaining_budget_pct and suggested_next_call_delay_ms
Agents use this to self-regulate extraction pace without polling a separate rate-limit service
Rate limit hit handling
RATE_LIMIT_ERROR triggers automatic exponential backoff: 10s, 30s, 60s, 120s, 300s
After 300s backoff: escalate to COORD-001 with recommendation to schedule extraction in off-peak window
Parallel agent coordination
Two agents extracting from the same connector share the rate limit budget
Connector Proxy Service enforces the shared budget; agents do not need to coordinate directly
Table EIS-1.5 — Rate limit budget architecture. Every extraction tool response includes remaining_budget_pct.

Category 5 — IMS Execution Tools
IMS Execution Tools implement the IMS Retrieval Architecture described in Section 0.1. They serve IMS content to agents in structured, section-sized chunks rather than as full document loads. The IMS content store is a structured JSON document store indexed by {connector_id}.{section_id}.{subsection_id}. Agents request specific sections and receive machine-readable content alongside human-readable text.
 
IMS Content Store Architecture
The IMS Content Store is a JSON document store where each document represents one subsection of one IMS specification. The key structure is:
ims_content_store["{connector_id}.{section_id}.{subsection_id}"] = {
  connector_id: "IMS-001",          // e.g., "IMS-001" for NetSuite
  section_id: "Section_4",          // e.g., "Section_4" for Transformation Rules
  subsection_id: "4.3",             // e.g., "4.3" for ARR Movement Derivation
  title: "ARR Movement Derivation", // human-readable title
  content_type: "ALGORITHM",        // enum: ALGORITHM | FIELD_MAP | TABLE |
                                    //        GATE | EXCEPTION | CONFIDENCE_RULE
  machine_readable: {               // structured data for direct agent execution
    steps: [...],                   // ordered steps for ALGORITHM type
    fields: [...],                  // field list for FIELD_MAP type
    rules: [...]                    // rule list for TABLE type
  },
  human_readable: "...",            // the full IMS prose, for context
  execution_stage: "TRANSFORM",     // which SOF stage this content applies to
  prerequisite_sections: ["4.1"],   // sections that must be loaded before this one
  cep_fields_required: [...]        // CEP fields this section reads or writes
}
