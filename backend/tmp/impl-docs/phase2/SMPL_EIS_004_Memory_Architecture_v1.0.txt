Section 0 — Engineering Context and Pre-Build Design Decisions
EIS-004 defines how SMPL captures implementation experience and converts it into reusable operational knowledge that makes future implementations faster, more accurate, and less reliant on manual CEP resolution. Three design decisions address specific failure modes that would undermine the memory system's value and safety.
 
0.1 Design Decision 1 — Taxonomy-Keyed Retrieval
Problem: "Favor structured retrieval over full-text retrieval" is the right principle, but without specifying the key structure, engineers default to vector similarity search over memory text. Vector search introduces a customer data isolation risk: if a Connector Memory record for a Workday supervisory org pattern was embedded during context that included customer-specific terminology, a similarity search from a new customer's query can surface that context. The isolation guarantee depends on the embedding being clean — and embeddings are notoriously difficult to audit.
Solution: Every memory record has a structured retrieval_key built from a controlled vocabulary. Workers retrieve by key, not by similarity. The retrieval_key is a hierarchical dot-notation path: {memory_type}.{connector_id}.{domain}.{object_type}.{task_type}. Examples: connector.IMS-001.erp.gl_account.account_type_normalization or validation.IMS-201.billing.subscription.arr_formula_mismatch. Semantic retrieval is never used for memory lookup in the MVP — it is a future roadmap item documented in Section 9. Structured key retrieval guarantees deterministic, auditable memory access.
The controlled vocabulary for each key component is defined in Section 2.3. New vocabulary terms require an engineering review before they can be used in memory records — free-form key components are rejected by the Memory Service at write time.
 
0.2 Design Decision 2 — Conflict Resolution Protocol
Problem: Two Connector Memory records for the same connector and pattern with different success rates — or one approved record that was true for an older API version but is contradicted by a new implementation — need a deterministic resolution rule. Without one, workers receive conflicting memory and either (a) pick arbitrarily, undermining the memory system's reliability, or (b) escalate every conflict to humans, negating the efficiency gain.
Solution: Memory conflicts are resolved by a three-tier precedence rule applied at retrieval time:
Tier 1 — Version-specific dominance: a memory record with a matching api_version_validated beats a record without one. Newer api_version_validated always beats older.
Tier 2 — Confidence × usage_count product score: among records with no version conflict, the record with the higher (confidence × usage_count) score wins. This rewards records that have been validated by many implementations at high confidence.
Tier 3 — Human approval recency: if scores are tied, the most recently human_approved record wins.
A conflict is only surfaced to humans when the top two conflicting records have a product score within 10% of each other AND both have api_version_validated = null — meaning neither has a clear version anchor. This is the only conflict state where the system cannot resolve deterministically.
 
0.3 Design Decision 3 — API-Version-Anchored Expiration
Problem: Time-based expiration is the wrong mechanism for connector memory. A SuiteQL optimization pattern written three years ago may still be perfectly valid — age is not the right expiration signal. Meanwhile, a Stripe livemode pattern written six months ago could be invalidated overnight by an API change. Retiring records by age discards valid knowledge; failing to retire after API changes propagates stale knowledge.
Solution: Connector Memory expiration is triggered by SCHEMA_CHANGED events from EIS-001, not by timers. Every Connector Memory record stores api_version_validated (the API version it was confirmed against) and api_version_range_valid (the version range across which it has been continuously validated without schema changes). When a SCHEMA_CHANGED event fires for a connector, the Memory Service flags all records for that connector with status = PENDING_REVALIDATION. A human reviewer determines whether each flagged record still applies to the new schema version — confirming it extends api_version_range_valid, or retiring it.
Time-based expiration applies only to Customer Memory (tied to the customer relationship lifecycle) and Organizational Memory analytics (rolling 12-month window). It never applies to Connector Memory, Transformation Memory, or Validation Memory — these expire only on schema changes or explicit human retirement.

1.2 Domain Descriptions
Customer Memory
Customer Memory is the complete set of customer-specific decisions recorded during and after an implementation. It is the operational expansion of the CEP — while the CEP holds decisions for a single active session, Customer Memory retains the history of all decisions across all sessions for a given customer, enabling implementations to build on prior work rather than starting from scratch on re-implementations or when adding a new connector.
Customer Memory never leaves the customer's scope. It is the most voluminous memory type and the safest — there is no risk of cross-customer data leakage because there is no mechanism by which Customer Memory is ever read outside of the customer's own sessions.
 
Connector Memory
Connector Memory captures reusable implementation knowledge specific to a connector — patterns that appear consistently across multiple customer implementations and are safe to reuse because they do not contain customer-specific data. Examples include: common NetSuite custom field configurations and their canonical meanings, the typical Workday Supervisory Organization depth for mid-market customers, Stripe webhook configuration patterns that resolve specific livemode detection edge cases.
Connector Memory is the primary mechanism by which the SMPL platform gets faster with scale. The tenth NetSuite implementation should generate fewer CEP questions than the first — because patterns identified in implementations 2 through 9 have been promoted to Connector Memory and are pre-applied, reducing discovery time.
 
Transformation Memory
Transformation Memory captures field-level mapping patterns — specific vendor field → canonical field transformations that have been validated across multiple implementations. A Transformation Memory record says: "In 87% of Salesforce implementations, the custom field SBQQ__Subscription__c.SBQQ__NetPrice__c maps to invoice_line.amount_local with Direct-High confidence." This pre-validates a common transformation pattern that would otherwise require per-customer CEP resolution.
 
Validation Memory
Validation Memory captures recurring validation failures and their confirmed resolutions. When the same validation issue appears across multiple implementations — SAP ACDOCA entries missing the ledger filter, Stripe subscriptions with livemode=false contaminating the extraction — and is resolved the same way each time, that resolution pattern becomes Validation Memory that future implementations can apply automatically rather than discovering through error.
 
Implementation Pattern Library
The Implementation Pattern Library captures successful end-to-end implementation strategies — the combination of connector sequencing, CEP question ordering, gate resolution approach, and capability activation sequence that produces the fastest, cleanest implementation for a given customer profile. Examples: the implementation strategy for a Series B SaaS company with NetSuite + Salesforce + Stripe is likely to be similar across customers in that segment; the Pattern Library codifies what works.
 
Organizational Memory
Organizational Memory is SMPL's platform-level operational analytics — aggregated, anonymized statistics about how implementations are progressing across the customer base. It answers operational questions: what percentage of implementations encounter a SAP ledger designation BLOCK? What is the median time-to-resolution for Salesforce stage normalization? Which connector generates the most CEP questions per implementation? This knowledge is used to improve the playbooks, the IMS documentation, and the CEP question templates — not to influence individual implementations.
 
Section 2 — Memory Record Format and Storage
Every memory record follows the standard schema defined in this section, with domain-specific extensions documented per domain. The retrieval_key is the most critical field — it is the structured access path that makes memory retrieval deterministic and auditable.

Section 3 — Memory Lifecycle
Every memory record passes through a defined lifecycle from discovery to archive. The lifecycle has two distinct tracks: the Customer Memory track (faster, no cross-customer reuse) and the Shared Memory track (slower, requires anonymization and approval before cross-customer availability).
 
3.1 Customer Memory Lifecycle
CUSTOMER MEMORY LIFECYCLE:
  DISCOVERY: A CEP decision is made during an implementation.
    Source: update_cep tool call with source=HUMAN_CONFIRMED or AUTO_DISCOVERED.
    A Customer Memory record is created automatically for each confirmed CEP field.
  ACTIVE: The record is immediately available for use in this customer's sessions.
    No approval required.
    Accessible only to sessions with this customer_id.
  UPDATED: Customer confirms a new value for a previously confirmed field.
    Old value is preserved in audit_history; new value becomes current.
    Example: FTE methodology changes from SCHEDULED_HOURS to BINARY after a policy update.
  DEPRECATED: Customer explicitly overrides a prior decision.
    Prior record marked DEPRECATED; new record becomes ACTIVE.
    Both retained in audit_history for the implementation record.
  PURGED: Customer offboards from SMPL.
    All Customer Memory for this customer_id is deleted.
    Purge event written to audit log (not to the deleted records — those are gone).
    This is the only hard deletion in the memory system.
 
3.2 Shared Memory Lifecycle (Connector, Transformation, Validation, Pattern)
SHARED MEMORY LIFECYCLE:
DISCOVERY:
  A pattern is observed during an implementation.
  Source: Connector Worker, Validation Agent, or Implementation Engineer.
  A CANDIDATE record is created by record_successful_pattern or record_failed_pattern.
  Status: DRAFT.
  customer_scope: null (no customer data in shared memory)
CANDIDATE VALIDATION:
  Memory Generalization Pipeline evaluates the candidate (see Section 4):
    - Minimum observation count check (5 distinct implementations for Connector/Transformation;
      3 for Validation; 10 for Implementation Pattern)
    - Anonymization check: no customer identifiers, financial values, or PII
    - Controlled vocabulary key check: retrieval_key must use registered terms
  If checks pass: status → REVIEW
  If any check fails: status → REJECTED; rejection reason written to audit_history
REVIEW:
  Assigned to a reviewer (different from record creator).
  Reviewer validates:
    - Technical accuracy of the pattern
    - Absence of customer-identifying information
    - Correct confidence calculation
    - Appropriate retrieval_key
  Reviewer decision: APPROVED or REJECTED.
APPROVED:
  Record is ACTIVE in the Tier 2 pattern cache.
  Available for retrieval by any worker.
  approved_by populated; approved_at set.
IN USE:
  Worker retrieves the record via search_memory tool.
  usage_count incremented on each retrieval.
  Outcome recorded by the worker after use:
    success → success_count++
    failure → failure_count++
    false_positive → false_positive_count++
  confidence updated: success_count / usage_count.
PENDING_REVALIDATION (triggered by SCHEMA_CHANGED event):
  A SCHEMA_CHANGED error from EIS-001 Section 1.2 triggers:
    Memory Service queries: all records WHERE connector_scope = {connector_id}
      AND approval_status = APPROVED
    Sets status → PENDING_REVALIDATION for all matching records.
    Sets schema_change_event_id for audit linkage.
  Records in PENDING_REVALIDATION are NOT returned by search_memory.
  A human reviewer re-validates each record against the new schema.
  Outcome: APPROVED (confirmed still valid) or DEPRECATED.
DEPRECATED:
  Pattern is no longer valid or has been superseded.
  Not returned by search_memory.
  Retained for audit and replay purposes.
ARCHIVED:
  Records older than 2 years in DEPRECATED status move to archive.
  Archive is read-only; queryable only by humans for audit.
  Not accessible to workers.

Section 4 — Memory Generalization Pipeline
The Memory Generalization Pipeline is the process that promotes customer-scoped implementation observations into approved shared memory. It runs nightly for routine promotion and on-demand for urgent patterns identified during active implementations. The pipeline is the enforcement point for customer data isolation — it is the only pathway from customer-scoped observations to shared knowledge.
 
4.1 Pipeline Architecture
MEMORY GENERALIZATION PIPELINE (nightly scheduled + on-demand trigger):
INPUTS: Implementation logs and outcome data from the past 24 hours.
  Source: implementation_logs table + canonical_objects metadata + cep_fields.
  Only metadata and pattern descriptions — no extracted customer records.
STEP 1: Candidate Pattern Identification
  Query implementation_logs for:
    - Transformation rules applied with success_result = TRUE
      WHERE connector_id = X AND transformation_rule_id = Y
      GROUP BY transformation_rule_id HAVING count(DISTINCT customer_id) >= 5
    - Validation failures with resolution_confirmed = TRUE
      WHERE resolution_type = AUTOMATIC
      GROUP BY validation_rule_id HAVING count(DISTINCT customer_id) >= 3
    - CEP questions where auto_discoverable was set to TRUE after initial CEP
      (indicates the field was auto-discovered but the pipeline did not catch it)
STEP 2: Anonymization
  FOR each candidate:
    a. Strip all customer_id, session_id, and canonical_id references.
    b. Replace company names with [COMPANY_TYPE] placeholder
       (using NER model to detect company names in text fields).
    c. Replace financial amounts with [AMOUNT] placeholder.
    d. Replace employee names with [PERSON] placeholder.
    e. Check: does the remaining content still contain enough context to be useful?
       IF remaining content < 20 tokens after anonymization: discard candidate.
STEP 3: Minimum Count Validation
  Connector Memory: min 5 distinct customers
  Transformation Memory: min 5 distinct customers + success_rate > 0.80
  Validation Memory: min 3 distinct customers + false_positive_rate < 0.10
  Implementation Pattern: min 10 distinct customers (manually triggered, not nightly)
STEP 4: Retrieval Key Assignment
  Parse the candidate's origin (connector_id, domain, object_type, task_type)
  Build retrieval_key using controlled vocabulary (Section 2.3)
  IF any key component requires a new vocabulary term: add to pending_vocabulary_review;
    create the record with status=DRAFT (not REVIEW) until vocabulary is approved.
STEP 5: Conflict Pre-Check
  Search existing APPROVED records with the same retrieval_key.
  IF existing record found:
    Compute how this candidate differs from the existing record.
    IF essentially the same (content similarity > 90%):
      Instead of creating new record: update existing record's usage_count and confidence.
    IF materially different:
      Create new DRAFT record; flag it as POTENTIALLY_CONFLICTS_WITH:{existing_id}.
      Human reviewer must resolve the conflict before APPROVED status.
STEP 6: Anonymization Certificate Generation
  Generate HMAC-signed certificate:
  {pipeline_run_id, candidate_id, connector_scope, memory_type,
   customer_count, anonymization_checks_passed: [step_2a, step_2b, step_2c, step_2d],
   timestamp, pipeline_version}
  Certificate signed with pipeline service private key.
  Memory Service verifies certificate before accepting a REVIEW-status record.
STEP 7: Submit to Review Queue
  Create memory record with status=REVIEW.
  Notify memory review team: {record_id, retrieval_key, candidate_summary}.
  Record enters human review workflow (Section 5).

  LOW sensitivity records unreviewed after 7 days: auto-escalate to team lead.
  MEDIUM sensitivity records unreviewed after 5 days: auto-escalate.
  HIGH sensitivity records unreviewed after 3 days: auto-escalate.

6.2 Retrieval Ranking
When search_memory returns multiple candidates before conflict resolution, they are ranked by the following weighted score before the conflict resolution protocol is applied:
 
RETRIEVAL RANKING SCORE (computed per candidate record):
  score = (0.40 × confidence)
         + (0.25 × normalized_usage_count)
             -- normalized_usage_count = min(usage_count / 100, 1.0)
             -- caps at 100 uses; prevents very high usage_count from dominating
         + (0.15 × key_specificity_bonus)
             -- 1.0 if retrieval_key matches all 5 levels (exact match)
             -- 0.7 if matches 4 levels (prefix match)
             -- 0.4 if matches 3 levels (partial match)
         + (0.10 × human_approval_recency)
             -- 1.0 if approved within last 30 days
             -- 0.7 if approved within 90 days
             -- 0.4 if approved within 180 days
             -- 0.1 if approved more than 180 days ago
         + (0.10 × api_version_match)
             -- 1.0 if api_version_validated matches the active connector version
             -- 0.5 if api_version is within the valid range
             -- 0.0 if api_version_validated is null
  After ranking: apply conflict resolution (Table EIS4-3.1) to the top candidates.
  Return up to top_k = 3 non-conflicting, resolved records.
  If top_k candidate set still contains a CONFLICT_REQUIRES_RESOLUTION after
  conflict resolution: include the conflict flag in the returned record.

Section 8 — Security and Customer Isolation
Memory security is enforced at multiple layers. The most critical protection is customer data isolation — ensuring that one customer's implementation knowledge never appears in another customer's implementation context. This is implemented through Postgres row-level security, strict content schema enforcement, and the anonymization pipeline's certificate requirement.
 
8.1 Customer Data Isolation Enforcement
Layer
Enforcement Mechanism
What It Prevents
Postgres Row-Level Security
Postgres RLS policy on memory_records: IF customer_scope IS NOT NULL THEN require current_customer_id = customer_scope
Any query that attempts to read Customer Memory outside the authorized customer context is silently filtered — returns zero rows, no error. Even a bug in the application layer cannot expose cross-customer memory.
Memory Service API scope enforcement
search_memory tool: does not return records with non-null customer_scope. retrieve_customer_memory tool: requires valid session_id and enforces customer_id match.
Tool-level separation ensures workers use the right retrieval path for customer-scoped vs. shared memory
Content schema enforcement at write time
Memory Service validates content JSONB against domain-specific schema before write. Schema validation fails if content contains email patterns, customer_id format, financial amount patterns (large decimals), or company name patterns (detected by NER pre-check).
Prevents customer data from entering shared memory records even if the pipeline's anonymization step had a bug
Anonymization certificate requirement
Memory Service rejects REVIEW-status writes for shared memory types (CONNECTOR, TRANSFORMATION, VALIDATION) without a valid anonymization_certificate signature.
Prevents shared memory records from being created without passing through the generalization pipeline's anonymization checks
Retrieval key taxonomy enforcement
Memory Service rejects write of any record whose retrieval_key contains a component not in the controlled vocabulary.
Prevents free-form, potentially identifying information from appearing in retrieval keys
