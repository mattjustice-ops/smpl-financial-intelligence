Library Overview — Purpose and Design Principles
The AI Agent Playbook Library (ABS-011) translates the SMPL architecture into executable agent instructions. Where the SOF defines what agents do and when, this library defines exactly how they do it — tool calls, decision logic, output formats, and behavior under every documented condition. Engineers can implement any agent from its playbook without additional architecture clarification.

Design Principles
EXECUTABLE WITHOUT CLARIFICATION. Every instruction references a specific tool, field, comparison, or threshold. No instruction says "assess" or "evaluate" without specifying the assessment criteria and the output format.
DETERMINISTIC BRANCHING. Every decision node has an exhaustive set of branches. If a condition is not explicitly handled, the agent routes to its default failure handler — it does not improvise.
READ-ONLY BY DEFAULT. No agent in this library writes to a customer system. Every tool that could be misused as a write operation is explicitly prohibited in Section 9 of the relevant playbook.
CONFIDENCE ALWAYS EXPLICIT. No agent reports a capability status, canonical object, or metric without attaching its confidence score. Omitting confidence from an output is a playbook violation.
CEP FIRST, CANONICAL SECOND. An agent that encounters a decision requiring business judgment routes to the CEP Agent (COORD-002) before attempting to infer the answer from data. The data-driven inference is documented as a lower-confidence default, never the primary path.
AUDIT TRAIL ON EVERY DECISION. Every branching decision produces an Implementation Log entry with reason, inputs, and confidence impact. Silent decisions — decisions that produce no log entry — are prohibited.

It dispatches agents, manages parallelism, routes decisions, and maintains the Implementation Log. It never executes connector logic directly.

4. Core Instruction Set
Stage 1 — Customer Discovery
1.1  READ CEP: confirm CEP is empty (new session) or partially populated (resumed session).
1.2  WRITE_LOG: session_start with session_id, customer_name, timestamp.
1.3  DISPATCH: COORD-002 (CEP Agent) with instruction: conduct_stage1_discovery.
1.4  WAIT for COORD-002 to return CEP.connector_inventory (minimum viable).
1.5  CHECK: len(CEP.connector_inventory) >= 1 AND CEP.fiscal_calendar.year_start
     AND CEP.functional_currency are all populated.
     ├─ YES → WRITE_LOG: stage1_complete; advance to Stage 2.
     └─ NO → SEND_TO_HUMAN: "Stage 1 incomplete. {missing_fields} not confirmed.
                             Cannot advance to Stage 2. Request sales team re-engage."
 
Stage 2 — Connector Discovery
2.1  FOR each connector in CEP.connector_inventory:
       DISPATCH: COORD-003 (Discovery Agent) with connector_id and credentials.
     All dispatches are parallel — do not wait for one before dispatching others.
2.2  POLL each COORD-003 instance every 30 seconds until all return status.
2.3  BUILD dispatch_list: connectors with status = AUTHENTICATED.
2.4  WRITE_LOG: stage2_complete with authenticated_count, failed_count, deferred_count.
2.5  CHECK: len(dispatch_list) >= 1.
     ├─ YES → advance to Stage 3.
     └─ NO → SEND_TO_HUMAN: "All connectors failed authentication.
                             Cannot proceed. Request credentials review."
2.6  FOR each AUTH_FAILED connector:
       SEND_TO_CEP_AGENT: {field_path: "connector_{id}.auth_status",
         question_text: "Credentials for {connector_name} failed. Please provide
         updated credentials or confirm this connector should be removed from scope.",
         reason_cannot_auto_discover: "Authentication failure is not resolvable by the
         agent — valid credentials must be supplied by a human.",
         capability_impact: "All capabilities sourced from {connector_name} unavailable",
         default_value: "DEFERRED"}
 
Stage 3 — Connector Implementation (Parallel Dispatch)
3.1  GROUP dispatch_list by domain: ERP, CRM, Billing, HRIS.
3.2  SPECIAL DISPATCH ORDER within each domain:
       ERP: dispatch ERP-005 (Oracle Fusion) and ERP-006 (SAP) first if present.
       Billing: dispatch BIL-005 (Zuora) first if present.
       HRIS: dispatch HRS-001 (Workday) first if present; flag RaaS coordination needed.
       CRM: dispatch CRM-001 (Salesforce) and CRM-002 (HubSpot) simultaneously.
3.3  SPECIAL COORDINATION: if both ERP-004 (D365 Finance) AND CRM-003 (D365 Sales)
     are in dispatch_list:
       DISPATCH both simultaneously.
       FLAG to both agents: shared_dataverse_possible = true.
       COORD-004 will coordinate identity resolution in Stage 4.
3.4  DISPATCH each Domain Agent (APB-006 through APB-009) with:
       {connector_list: [ids for this domain], cep_snapshot: current_CEP}
3.5  POLL all Domain Agents every 60 seconds.
3.6  FOR each PAUSE_FOR_CEP returned by any agent:
       IMMEDIATELY relay to COORD-002 — do not buffer.
       Log in session_state.pending_cep_items.
       DO NOT block other running agents.
3.7  FOR each BLOCKED agent after 48 hours without CEP resolution:
       SEND_TO_HUMAN with full blocking context and specific resolution question.
3.8  FOR each ERROR with retry_exhausted = true:
       SEND_TO_HUMAN with error code, agent context, and recommended action.
3.9  WAIT until all Domain Agents reach terminal status.
3.10 WRITE_LOG: stage3_complete with per-connector status summary.
 
Stages 4–7
4.x  DISPATCH COORD-004 (Canonical Integration Agent) with all Stage 3 outputs.
     WAIT for COORD-004 COMPLETE status.
5.x  DISPATCH EVAL-001 (CAL Agent), EVAL-002 (Validation Agent), EVAL-003
     (Confidence Scoring Agent) simultaneously with unified SCBM instance.
     WAIT for all three COMPLETE.
6.x  DISPATCH COORD-005 (Reporting Agent) to generate Implementation Summary.
     SEND_TO_HUMAN: schedule Stage 6 Customer Review with Implementation Consultant.
     WAIT for human Stage 6 completion signal.
7.x  DISPATCH COORD-005: activate_modules per confirmed Module Activation Plan.
     DISPATCH COORD-005: generate_final_deliverables.
     WRITE_LOG: session_complete with readiness_score and activated_modules list.
     UPDATE_SESSION_STATE: status = COMPLETE.

4. Core Instruction Set
Stage 1 — Customer Discovery Conversation
1.1  READ_CEP("connector_inventory") → if not empty, skip to 1.5.
1.2  CONDUCT discovery conversation. Ask the following, in order:
       Q1: "What ERP system does your company use for financial reporting?"
       Q2: "What CRM system does your sales team use?"
       Q3: "What platform do you use for subscription billing?"
       Q4: "What HRIS or people system do you use?"
       Q5: "What is your company's fiscal year start month?"
       Q6: "What is your reporting currency?"
       Q7 (if multi-entity suspected): "Do you have subsidiaries or multiple legal entities?"
1.3  FOR each answer:
       WRITE_CEP(field_path, value, source="HUMAN_CONFIRMED").
1.4  AUTO-POPULATE where possible:
       fiscal_calendar.year_end = year_start + 11 months.
       WRITE_CEP("fiscal_calendar.year_end", computed_value, "AUTO_DISCOVERED").
1.5  LIST all CEP fields with status PENDING.
       For each: determine if it can be auto-discovered from a connector probe.
         If YES → defer to Stage 2/3 auto-discovery.
         If NO → add to discovery_question_queue.
 
CEP Resolution Queue Management
R.1  On receipt of any PAUSE_FOR_CEP request from any agent:
       PARSE: {field_path, question_text, reason_cannot_auto_discover,
               default_value, capability_impact, source_agent}.
       CHECK: is this field already in a pending_cep_item?
         IF YES → merge; do not create duplicate item.
         IF NO → create new item with auto-assigned item_id.
R.2  CLASSIFY urgency:
       BLOCKING → field blocks extraction or canonical population of Tier 1 objects.
       NORMAL → field affects confidence or capability status but does not block.
       LOW → field improves reporting quality but has no capability impact.
R.3  CHECK: can this be auto-discovered?
       Attempt GET_AUTO_DISCOVERABLE_VALUES for the relevant connector.
       IF auto-discovered with high confidence (>= 85%):
         WRITE_CEP(field_path, auto_value, "AUTO_DISCOVERED").
         NOTIFY_WAITING_AGENT(source_agent, field_path, auto_value).
         WRITE_LOG: cep_auto_resolved.
         SKIP human question.
       IF NOT auto-discoverable:
         SEND_DISCOVERY_QUESTION to human with urgency classification.
R.4  On receipt of human answer:
       VALIDATE: answer is within expected value range for this field.
       WRITE_CEP(field_path, value, "HUMAN_CONFIRMED").
       MARK_CEP_ITEM_RESOLVED(item_id, value, "HUMAN_CONSULTANT").
       NOTIFY_WAITING_AGENT(source_agent, field_path, value).
R.5  If no human response after 48h for BLOCKING item:
       Apply default_value IF one was specified in the PAUSE_FOR_CEP request.
       WRITE_CEP(field_path, default_value, "DEFAULT_APPLIED").
       NOTIFY_WAITING_AGENT with note: "Default applied — confirm in Stage 6."
       For BLOCKING items with no default: escalate to COORD-001 for SEND_TO_HUMAN.

It resolves cross-system identity conflicts, assigns system-of-authority per canonical object type, and executes the Cross-Domain Validation Matrix. It is the most algorithmically complex coordination agent in the library.

2. System Prompt
You are the SMPL Canonical Integration Agent. You receive canonical objects from multiple Implementation Agents and merge them into a single unified SCBM instance. You resolve the same real-world entity appearing in multiple systems into a single canonical record. You assign exactly one system-of-authority for each canonical object type. You execute cross-domain validation checks to identify reconciliation gaps. You escalate every conflict you cannot deterministically resolve.
 
4. Core Instruction Set
Customer Account Identity Resolution (SOF Section 4.1)
I.1  FOR each Customer Account candidate from any Implementation Agent:
     STEP 1 — Email exact match:
       SEARCH canonical_store.customer_accounts WHERE primary_email =
       candidate.email.
       IF match found → LINK; record match_method = EMAIL; confidence = D-H.
     STEP 2 — External ID match (if Step 1 fails):
       SEARCH canonical_store.customer_accounts WHERE
       any_external_id IN candidate.external_ids.
       IF match found → LINK; confidence = D-H.
     STEP 3 — Fuzzy name match (if Steps 1-2 fail):
       COMPUTE normalized_name = candidate.name.lower().strip_punctuation()
       SEARCH canonical_store.customer_accounts WHERE
       levenshtein(normalized_name, canonical.normalized_name) <= 2.

          FOR each applicable factor F:

CS.3  COMPUTE capability-level confidence for each capability CAP:
       BASE = MIN(confidence of all REQUIRED objects for CAP)
       OPTIONAL_UPLIFT = 0.1 × AVG(confidence of all OPTIONAL objects present)

Final Determination
The SMPL AI Agent Playbook Library (ABS-011) is complete. All twelve agents — five coordination, four domain implementation, and three evaluation — are specified at the level of detail required for engineering translation into agent code, prompts, and tool configurations. SMPL implementations are now deterministic, explainable, auditable, and scalable.
 
These twelve playbooks operationalize everything built before them. The IMS libraries taught implementation agents what to do for each connector. The SOF defined when and in what order agents run. These playbooks define exactly how each agent executes — tool by tool, decision by decision, output by output. The three layers together produce the complete specification for a SMPL implementation: IMS (how to implement each connector) + SOF (how to coordinate the implementation) + Playbooks (how each agent behaves throughout).
The governing principles stated at the library's opening are visible in every playbook: Automate everything possible (COORD-003 auto-discovers environment facts before asking); ask only what cannot be discovered (COORD-002 checks auto-discoverability before routing to human); read-only by default (Section 9 of every playbook explicitly prohibits writes); confidence always explicit (COORD-005 is prohibited from omitting confidence from any output); audit trail on every decision (COORD-001 writes a log entry for every branching decision in the session).
The most consequential prohibitions in the library — the ones whose violation would most damage customer trust — are: the Closed Won ≠ Revenue principle enforced by CRM-DOMAIN (APB-007); the livemode firewall enforced by BIL-DOMAIN (APB-008); the ARR Movement population block enforced by BIL-DOMAIN before the Subscription Normalization Gate resolves; and the Department canonical object block enforced by HRS-DOMAIN before the Organizational Normalization Gate resolves. Each of these protects against a silent, systematic error that would be discovered only when a customer questions why their numbers do not match.
