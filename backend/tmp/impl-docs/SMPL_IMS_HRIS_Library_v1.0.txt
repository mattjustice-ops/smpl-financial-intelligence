The Three Universal HRIS Financial Distinctions
Three distinctions govern every HRIS implementation in this library and are stated here once rather than repeated across five connectors:
Employee ≠ Payroll Expense. An Employee record documents that a person is employed at a planned compensation. It does not confirm that payroll expense has been recognized in the GL. The ERP is the canonical owner of recognized payroll expense; HRIS contributes planned compensation only.
Salary ≠ Disbursed Compensation. A salary field in HRIS documents the planned annual rate. What was actually disbursed in a specific payroll run — including employer taxes, benefits load, deductions, bonuses, and any mid-period changes — is owned by Payroll. These two figures are related but distinct: a mid-cycle raise, a one-time bonus, or a payroll error can cause them to diverge temporarily.
Department ≠ Cost Center. An HRIS Department is an organizational unit for people management. A Cost Center is a financial reporting dimension for expense allocation. In many HRIS implementations, these two concepts are used interchangeably — but they are not the same canonical object and must not be treated as equivalent without explicit CEP confirmation of the mapping.

Every HRIS connector in this library has a mandatory Organizational Normalization Gate — the HRIS equivalent of the Billing Subscription Normalization Gate. The gate operates as a population block for specific canonical objects: organizational hierarchy objects and headcount-derived metrics cannot be correctly built until the gate questions are resolved. Cross-HRIS Implementation Principles
SMPL is always read-only. No HRIS IMS specifies write operations.
HRIS owns organizational structure and planned compensation; Payroll owns disbursed compensation; ERP owns recognized payroll expense. All three are required for trusted Labor Cost Forecasting. No HRIS connector in this library, regardless of how tightly integrated with Payroll, substitutes for ERP-confirmed GL expense.
Manager hierarchy cycles are a block condition — not a data quality issue to be ignored. A circular reporting chain (A reports to B, B reports to A) makes it impossible to compute correct org depth, span of control, or rollup headcount. Detected cycles must be resolved before the organizational hierarchy canonical object is created.
Position Planning requires a dedicated Position object. Connectors without a formal Position object (BambooHR, and Rippling with limited support) have a structural ceiling on Position Planning that cannot be overcome by SMPL implementation effort — it reflects a platform capability boundary, not an implementation maturity gap. This is analogous to QBO's multi-entity structural ceiling in the ERP library.
Headcount-derived metrics (FTE, Revenue per Employee, Labor Cost per Headcount) are always computed by SMPL from canonical Employee data — never imported from pre-computed vendor metrics. ADP's native headcount reports and Workday's native workforce analytics are cross-validation references, not canonical sources, consistent with the principle established for Maxio's native SaaS metrics in the Billing library.
IMS-301 — Workday HCM
Workday HCM is the most complex HRIS implementation in this library — the enterprise-tier equivalent of Oracle Fusion (ERP) and Zuora (Billing). Its Supervisory Organization model is flexible, powerful, and frequently misaligned with financial Cost Center structures, creating the primary implementation challenge. The implementation agent's highest-priority discovery task is not extracting employees — it's confirming whether Supervisory Organizations map to Cost Centers, and if not, how they relate.
✱ ARCHITECT NOTE: Key departure distinguishing Workday from all other HRIS connectors in this library: Workday exposes data primarily through a combination of REST API and Report-as-a-Service (RaaS) — the latter being a customer-configured report extraction mechanism unique in this library. The implementation agent cannot assume a universal standard RaaS report structure; it must coordinate with the customer's Workday administration team to confirm which reports exist and what their column structure is. This is analogous to Oracle Fusion's API version pinning requirement in the ERP library.

1.2 Supervisory Organization vs. Cost Center Gate — The Primary Discovery Step
This is the most consequential discovery question for any Workday HCM implementation. The answer determines how organizational hierarchy is constructed, how Department canonical objects are mapped, and whether ERP Cost Center reconciliation is required.
DISCOVER organizational structure mapping:
  REST API: GET /api/v1/{tenant}/organizationReferenceData
  Returns: list of Organization Types (Supervisory, Cost Center, Company, etc.)
  CHECK: Does this customer use Cost Centers as a separate dimension from
  Supervisory Organizations, or are they equivalent?
  ASK CEP:
  "In this Workday implementation, does a Supervisory Organization correspond
  1:1 to a GL Cost Center in the customer's financial reporting system?
  Options:
  A) YES: Supervisory Org = Cost Center (direct mapping possible)
  B) NO: Cost Centers are maintained separately (mapping required)
  C) UNKNOWN: Customer finance team should confirm"
  RECORD in CEP.org_policy:
    canonical_department_object = "SupervisoryOrganization" (most common)
    cost_center_equivalent = true/false
    cost_center_mapping_required = true/false
  IF cost_center_mapping_required = true:
    Department canonical objects will be created from Supervisory Organizations
    A SEPARATE CEP mapping table will reconcile them to ERP Cost Centers
    This table is required before Department Expense Forecasting can activate
  BLOCK: Department canonical object creation is blocked until
  CEP.org_policy.canonical_department_object is confirmed.

4.3 Supervisory Organization Hierarchy Construction
Workday's Supervisory Organization hierarchy is the HRIS equivalent of the GL Account hierarchy in ERP — a parent-child tree that must be constructed bottom-up before any rollup headcount calculations are possible.
CONSTRUCT Supervisory Organization hierarchy:
  STEP 1: Extract all Supervisory Organizations
  GET /api/v1/{tenant}/supervisoryOrganizations?limit=9999
  Record: orgId, name, managerReference, parentOrganization, isInactive
  STEP 2: Filter to active organizations (isInactive = false)
  Flag inactive orgs for historical record; exclude from current hierarchy
  STEP 3: Build parent-child adjacency list
  {childOrgId: parentOrgId} for all non-null parentOrganization references
  STEP 4: DETECT CYCLES (block condition)
  Traverse the adjacency list; if any cycle is detected:
  → FLAG specific org IDs forming the cycle
  → BLOCK hierarchy construction for the affected branch
  → LOG: "Circular organizational hierarchy detected: [orgIds]. Cannot
     compute rollup headcount until resolved. Customer admin must correct."
  → Continue with non-cyclic portions of the hierarchy
  STEP 5: Assign hierarchy depth (root orgs = depth 0)
  STEP 6: For each Employee, record the full path from their
  primary Supervisory Org to the root (for rollup aggregation)
4.4 FTE Computation
FTE methodology varies by customer policy and must always be confirmed via the Organizational Normalization Gate before FTE-based metrics are computed.
FTE COMPUTATION (post-gate):
  IF CEP.headcount_policy.fte_methodology = SCHEDULED_HOURS:
    fte = employee.scheduledWeeklyHours / 40
    (40 hours = 1.0 FTE standard; confirm denominator with customer)
  IF CEP.headcount_policy.fte_methodology = NATIVE_FTE_PERCENTAGE:
    fte = employee.fullTimeEquivalentPercentage / 100
    (Workday natively exposes this field where configured)
  IF CEP.headcount_policy.fte_methodology = BINARY (most conservative):
    fte = 1.0 for all active employees regardless of hours
    (Treats all employees as 1.0 FTE; simple but loses part-time distinction)
  FOR contingent workers where FTE is applicable:
    Apply CEP-designated FTE value per contractor type
    Default: 0.0 (excluded from FTE count even if included in headcount)
  VALIDATE: total FTE <= total headcount for any period
  If total FTE > headcount: FLAG — likely a data issue or FTE > 1.0 for some workers

IMS-302 — Rippling
Rippling is the fastest standard HRIS implementation in this library — Production Ready maturity, consistent REST API, and native Payroll integration that narrows the planned-vs-actual compensation gap without requiring a separate Payroll connector. The primary implementation complexity drivers are Payroll module activation (which must be confirmed, not assumed) and GL cost center mapping (which Rippling does not natively support — it requires SMPL Configuration Layer mapping).
✱ ARCHITECT NOTE: Key departure from Workday: Rippling's flat, clean Department model eliminates the Supervisory Organization vs. Cost Center disambiguation challenge entirely. Department in Rippling is a single object that directly maps to SCBM Department with high confidence. The primary gate question is not organizational disambiguation — it is Payroll module confirmation and GL cost center mapping status. The implementation agent moves from discovery to canonical population faster than for any other connector in this library.

4.2 Manager Hierarchy Construction
Rippling's managerId field builds the manager hierarchy directly — simpler than Workday's Supervisory Organization join. The same cycle detection logic applies.
BUILD manager hierarchy:
  1. Extract all active employees with non-null managerId
  2. Build adjacency list: {employee_id: manager_id}
  3. CYCLE DETECTION (block condition if cycle found)
     Traverse from each employee to root (null managerId)
     If any employee appears twice in a path → cycle detected → BLOCK
  4. Assign hierarchy depth from root (depth 0) downward
  5. Record full hierarchy path per employee for rollup aggregations
  Rippling advantage: managerId is a direct Employee field, not a
  Supervisory Organization join like Workday. Fewer null values expected.
  Cycle detection is still required — hierarchy errors can occur from
  mid-reorganization data states.

4.1 Fully-Loaded Cost Per Employee — ADP's Primary Capability Advantage
ADP's payroll-tax and benefits data enables the most complete fully-loaded cost-per-employee calculation of any connector in this library. This is the HRIS analog of Stripe's ARR formula — the core derived metric that makes ADP most valuable for Financial Intelligence.
FULLY-LOADED COST PER EMPLOYEE (per period):
  REQUIRED components from ADP:
    gross_pay = payroll_output.earningsSummary.totalGrossPay
    employer_taxes = payroll_output.taxSummary.employerTaxes (all types)
    benefits_employer_contribution = payroll_output.deductionSummary.employerDeductions
  DERIVED:
    fully_loaded_cost = gross_pay + employer_taxes + benefits_employer_contribution
  ANNUALIZED:
    annual_fully_loaded_cost = fully_loaded_cost_per_period × pay_periods_per_year
    (pay_periods_per_year from CEP.headcount_policy.pay_frequency)
  CONFIDENCE: D-H when all three components available
  DEGRADES: if benefits module inactive → D-M (gross + taxes only; no benefits)
  CROSS-VALIDATION:
    Compare ADP-derived fully_loaded_cost against ERP GL payroll expense
    Discrepancy > 3% → FLAG as COST_RECONCILIATION_ITEM for finance team review

Final Determination
The HRIS Implementation Mapping Specification Library (IMS-301 through IMS-305) is complete. Implementation agents and human consultants have sufficient implementation knowledge to begin onboarding any Tier 1 HRIS platform. The SMPL Implementation Mapping Library — ERP, CRM, Billing, and HRIS — is now complete across all four foundational business domains.
The HRIS library introduces two implementation concepts that had no precedent in the ERP, CRM, or Billing libraries: (1) the structural ceiling disclosure — BambooHR's Section 1.2 Position Planning communication is a required disclosure step that precedes technical discovery, because no amount of implementation effort can produce a capability the platform doesn't support; and (2) the role confirmation inversion — ADP's Section 1.2 role confirmation can redirect an implementation to a fundamentally different canonical scope before any extraction begins, producing a Payroll-equivalent connector rather than an HRIS connector. Both concepts extend the IMS standard's deterministic philosophy to cover situations where the implementation agent's first action is to clarify the scope of the implementation itself, not to begin extracting data.
The cross-connector pattern from building all five simultaneously: every HRIS connector's most consequential gap — the gap between what HRIS reports and what Financial Intelligence requires — is the Employee-to-Expense chain. HRIS knows who is employed, in what role, at what planned compensation. Payroll knows what was actually disbursed. ERP knows what was recognized as GL expense. None of the three substitutes for the others; all three are required for trusted Labor Cost Forecasting. The HRIS IMS library documents exactly where each connector's contribution to this chain ends and where the next system's contribution must begin — consistently, explicitly, and without ambiguity, across all five connectors.
With the completion of the HRIS IMS Library, the SMPL Implementation Mapping Library spans all four foundational business domains: ERP (financial truth), CRM (commercial intent), Billing (commercial execution), and HRIS (organizational execution). The IMS standard — established by IMS-001 (NetSuite) and validated across 20 additional connectors in four domain libraries — has proven durable, generalizable, and AI-executable. It is ready to govern future connector additions without structural modification.
