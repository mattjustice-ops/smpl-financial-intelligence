ERP Category Overview
This section establishes universal knowledge about Enterprise Resource Planning systems before any vendor-specific documentation begins. It is the Tier 1 foundation that every ERP connector specification in this registry builds upon.
✱ ARCHITECT NOTE: This registry is designed to be consumed equally well by human implementation consultants and AI implementation agents. Throughout this document, the implementation agent evaluates connector readiness, the Capability Assessment Layer determines module status, the Connector Engine validates mapping output, and the CEP requests customer confirmation for ambiguous configuration — the architecture is implementation-neutral, but SMPL's onboarding workflow is designed for automation.
What an ERP System Is
An Enterprise Resource Planning system is the system of record for an organization's core financial transactions and the master data that supports them. At minimum, every ERP maintains a General Ledger, a Chart of Accounts, and the transactional subsystems that post to it — Accounts Receivable, Accounts Payable, and Cash Management. Beyond this financial core, ERPs typically extend into adjacent operational domains: procurement, inventory, fixed assets, project accounting, and in some cases CRM and HR functionality.
For SMPL, the ERP is almost always the highest-value single connector category. It is the system from which GAAP-compliant financial statements, GL-level variance analysis, multi-entity consolidation, and budget-to-actual reporting are derived. No other connector category can substitute for the ERP in producing these outputs.
Typical Business Responsibilities
Recording every financial transaction as a double-entry journal posting against the Chart of Accounts
Maintaining the authoritative Chart of Accounts and its hierarchy
Managing Accounts Receivable: customer invoicing, collections, and aging
Managing Accounts Payable: vendor bills, payment runs, and aging
Producing the three core financial statements: Income Statement, Balance Sheet, and Cash Flow Statement
Supporting period close: accruals, reclassifications, and period lock
Maintaining fixed asset registers and depreciation schedules
Supporting multi-entity and multi-currency consolidation where applicable
Enforcing approval workflows and segregation-of-duties controls
Maintaining a complete, immutable audit trail of all financial transactions

Typical ERP Implementation Complexity
ERP implementation complexity is driven primarily by three factors that vary significantly across the five systems in this registry:
Customization depth: how much the customer has extended the system beyond its standard configuration — custom fields, custom workflows, custom dimensions.
Module breadth: how many optional modules are licensed and active — revenue recognition, multi-entity consolidation, project accounting, advanced inventory.
Data model rigidity: whether the vendor enforces a fixed schema (lower implementation complexity, lower customization risk) or allows extensive configuration (higher implementation complexity, higher customization risk).
Typical Customization Patterns
Custom GL dimensions for product line, project, or initiative tracking beyond standard Department/Location
Custom fields on Customer, Vendor, and Transaction objects to capture business-specific attributes
Custom approval workflows that vary by transaction type, amount threshold, or department
Non-standard Chart of Accounts structures — numbering conventions, account type usage, and rollup hierarchies vary significantly by customer even within the same ERP
Custom reporting dimensions layered on top of standard GL structure
Common Enterprise Modules
Across the five ERPs in this registry, the following optional modules most significantly affect canonical mapping confidence and capability unlocks:
Advanced Revenue Management / Revenue Recognition modules — unlock high-confidence Revenue Schedule population
Multi-entity / multi-subsidiary modules — unlock Legal Entity hierarchy and consolidation
Budgeting and Planning modules — unlock Budget Line population
Project Accounting modules — unlock project-level cost and revenue tracking
Fixed Asset Management modules — unlock Asset and depreciation schedule population
Multi-book Accounting — unlocks parallel GAAP/IFRS/Tax basis reporting
Typical Integration Patterns
REST API — the dominant pattern across modern cloud ERPs (NetSuite, Dynamics 365, Fusion, Intacct, QBO all expose REST endpoints)
Bulk/batch query languages — SuiteQL (NetSuite), Intacct Query API, OData (Dynamics 365, Fusion) for high-volume data extraction
Webhook/event-driven patterns — increasingly available but not yet universal across ERP vendors (less mature than CRM or Billing connector categories)
Scheduled/batch synchronization — the most common pattern for ERP connectors generally, given the batch-oriented nature of period-end financial processes

S3: Connector Strengths
Native multi-dimensional GL: every transaction line can be tagged with Account, Department, Location, and up to 8 additional custom dimensions. This produces the richest out-of-box dimensional P&L of any connector in this registry without requiring custom field mapping.
Revenue recognition depth: the native Revenue Management module supports contract-level performance obligations, multiple recognition methods, and automatic schedule generation — frequently eliminating the need for a separate billing-system-derived revenue schedule.
Multi-entity architecture: entity structure, ownership percentage, and consolidation method are all natively modeled. Intercompany transactions are flagged automatically by the platform, reducing the elimination-detection burden on the Transformation Engine.
API consistency and modernity: Intacct's REST API (v3) is well-documented, consistently versioned, and has strong sandbox/production parity — reducing implementation risk relative to older SOAP-based predecessor APIs still common elsewhere in the ERP market.

S15: Implementation Risk Register
Custom dimension proliferation: Intacct customers frequently define 4–8 custom dimensions. Without CEP-documented business meaning for each, canonical mapping of dimensional data defaults to extension fields, reducing AI reasoning depth on department/segment analysis.
Multi-book accounting complexity: customers running parallel GAAP/Tax/IFRS books must have the correct book explicitly designated in the CEP — defaulting to the wrong book silently produces incorrect canonical financials.
Session and concurrency limits: Intacct enforces per-company-file session limits that can throttle initial historical backfill for customers with several legal entities. Implementation must account for multi-session orchestration.

Cross-ERP Transformation Considerations
The following transformation challenges recur across multiple ERPs in this registry. Each is documented once here rather than repeated in every connector specification, with vendor-specific notes where materially different.
Chart of Accounts Normalization
Every ERP in this registry allows customer-defined account numbering and naming conventions. None enforces a universal account type taxonomy that maps 1:1 to the SCBM Account Type taxonomy (Asset, Liability, Equity, Revenue, Expense). All five connectors require a lookup-table-based normalization step (S10 Field Mapping Rules) from the vendor's native account type field to the SCBM taxonomy. QuickBooks Online has the most rigid native taxonomy (fewest normalization edge cases). Oracle Fusion has the most flexible, customer-defined segment structure (most normalization complexity).
Dimension Normalization
Department, Location, Class, Segment, and custom dimension fields vary enormously in both naming and business meaning across the five ERPs. Sage Intacct and Dynamics 365 both offer purpose-built multi-dimensional frameworks (8 and 10 dimensions respectively) where dimension business meaning is entirely customer-defined — this is the highest CEP-resolution burden across the registry. NetSuite's Department/Class/Location are more conventionally named but still require per-customer validation. QuickBooks Online has the simplest dimensional model (Class and Location only) and correspondingly the lowest normalization burden.
Department and Entity Hierarchy
All five ERPs support hierarchical Department structures, but hierarchy depth and rollup behavior vary. Entity (Legal Entity / Subsidiary) hierarchy is fully supported in NetSuite (OneWorld), Sage Intacct, Dynamics 365, and Oracle Fusion. QuickBooks Online has no entity hierarchy concept — it is architecturally single-entity.
Multi-Currency and Multi-Book Accounting
NetSuite, Sage Intacct, Dynamics 365, and Oracle Fusion all support multi-currency consolidation with functional and reporting currency distinction. Oracle Fusion additionally supports multi-book accounting (parallel GAAP/Tax/IFRS books) at the deepest level in this registry, followed by Sage Intacct. QuickBooks Online supports single-currency, single-book accounting only.
Custom Dimensions and Custom Fields
Custom fields and dimensions are common across NetSuite, Sage Intacct, Dynamics 365, and Oracle Fusion, and rare in QuickBooks Online. Where present, custom fields are captured as extension fields (ext_ prefix) pending CEP-level business meaning resolution — they do not participate in canonical formulas or AI reasoning until formally promoted, consistent with SKA Principle 5 (Configuration Instead of Customization).
Revenue Recognition and Deferred Revenue
This is the single largest confidence swing factor across all five connectors. Each ERP has an optional advanced revenue recognition module (NetSuite ARM, Sage Intacct Revenue Management, Dynamics 365 Revenue Recognition, Oracle Fusion Revenue Management Cloud) that, when active, raises Revenue Schedule mapping confidence from the 15–35% range (estimated from invoice service period fields) to the 80–92% range (native ASC 606 objects). QuickBooks Online has no equivalent module and is structurally capped at lower confidence regardless of configuration.
Intercompany Transactions
NetSuite, Sage Intacct, Dynamics 365, and Oracle Fusion all support intercompany transaction flagging, though the reliability of automatic flagging varies. Sage Intacct and Oracle Fusion have the most mature native intercompany elimination support. NetSuite requires OneWorld to be active for reliable intercompany flagging. Without intercompany flagging, multi-entity consolidation risks overstating consolidated revenue from unflagged related-party transactions.
Custom Approval Workflows
Approval workflows are operational/security concerns (S6 of the connector specification) rather than canonical mapping concerns. They do not affect Business Object Population Maps but are documented in each connector's Implementation Risk Register where they affect data availability timing (e.g., a transaction pending approval may not yet be queryable as a finalized Journal Entry).

Remaining ERP Knowledge Gaps
Field-level mapping rules (S10) for Dynamics 365 and Oracle Fusion remain at the pattern level — this gap, carried forward from v0.1 and v0.2, persists in v0.4. It is independent of this iteration's scope and should be prioritized as these connectors progress through the maturity model.
The SCBM Coverage and Data Confidence Profile estimates introduced in this version are planning-grade estimates derived from architectural analysis and accumulated implementation pattern knowledge — they have not yet been validated against a statistically significant sample of actual Capability Assessment Layer output per connector. This should be the first validation priority once sufficient production data accumulates.
The Financial Dimension / Segment resolution playbook recommendation, carried forward from v0.1 and reaffirmed in v0.2, remains unbuilt. Its absence is now somewhat more visible given that Data Confidence Profile explicitly quantifies Department/Segment confidence as the lowest-confidence object for Intacct, Dynamics 365, and Oracle Fusion — reinforcing this as the highest-leverage next investment.

Automated reconciliation of Data Confidence Profile estimates against live Capability Assessment Layer output, once available, to confirm the planning-grade estimates in this document remain accurate as production implementation count grows for each connector.
A formal validation exercise running an actual AI implementation agent against this registry's language and structure, to confirm the document is genuinely machine-actionable and not merely written in agent-adjacent prose.

Version 2 Considerations
Once the Financial Dimension resolution playbook is built, Department/Segment confidence estimates for Intacct, Dynamics 365, and Oracle Fusion should be revisited — the playbook is likely to materially improve these specific confidence figures by standardizing the resolution workflow.
As Dynamics 365 and Oracle Fusion progress through the Connector Maturity Model, their SCBM Coverage and Data Confidence Profile sections should be recalculated against accumulated production data rather than the architectural estimates currently documented.
Consider whether Estimated SCBM Coverage and Data Confidence Profile should eventually be computed dynamically by the Capability Assessment Layer from live customer data, with the values in this registry serving as the baseline prior used before any customer-specific data is available — this would represent the natural evolution from static planning estimates to a dynamically-updated knowledge asset, without requiring CKR architectural changes.

No new connectors were added in this iteration — scope was strictly depth enrichment of the existing five, consistent with the freeze directive.

No changes were made to the Connector Maturity Model levels themselves in this iteration — maturity level changes require an actual promotion event, not a documentation enrichment pass.
Final Determination
Does the ERP Registry now provide sufficient depth to support AI-driven implementation, automated capability assessment, and confident Sales and Solutions Engineering qualification — in addition to the human-consultant-facing guidance already established in prior versions?
Yes, with one validation step still pending before declaring full automation-readiness proven rather than architecturally designed.
Every connector in this registry now provides three layers of machine-consumable precision that did not exist before this iteration: a quantified SCBM coverage estimate by domain, an object-level confidence profile with explicit reasoning for each score, and an unambiguous Ready/Partial/Unavailable verdict per SMPL capability. Combined with the Capability Assessment Layer and Module Capability Registry definitions this data is designed to feed, an implementation agent — or a human consultant working alongside one — now has a single, consistent reference for every decision point in ERP onboarding: what to expect, how confident to be in what the system produces, and what to communicate to the customer.
The language recalibration throughout the document — implementation agent evaluates, Capability Assessment Layer determines, Connector Engine validates, CEP requests confirmation — is architecturally consistent and applied uniformly across all five connectors. This satisfies the requirement that the registry read naturally for both human and AI-agent consumption.
The one remaining gap before declaring full automation-readiness proven: this registry has not yet been tested against an actual automated POC execution. The structure, language, and data are designed for that use case, but design intent and validated operation are different claims. This should be the first priority of the next iteration — not a redesign, but a live test of whether an implementation agent operating from this document alone can execute a representative POC against each of the five connectors with results consistent with the estimates documented here.
With that single caveat, the ERP Registry is considered complete and production-ready for its intended purpose: a frozen, mature enterprise implementation knowledge asset serving human implementation consultants, Sales Engineering, Solutions Engineering, Customer Success, future connector developers, and — pending the validation step above — AI implementation agents, consistently.
