Section 1 — Performance Philosophy
Correctness before speed — the same priority FIE-BUILD-004's Release Philosophy and FIE-BUILD-002's Engineering Philosophy both already establish for their own domains
Determinism before optimization — FIE-003's Deterministic Core (FIE-BUILD-002 §1) is never traded for latency; an optimization that introduces even occasional non-determinism is rejected regardless of its speed gain
Scale through architecture — horizontal scaling and caching (Section 6) extend the platform's existing service boundaries; scaling never means bypassing Canonical, Validation, or Orchestration to go faster, per FIE-BUILD-002's Dependency Direction Rules
Predictability over peak benchmarks — a service that performs consistently at its Performance Targets is preferred over one with a higher peak but wider variance
Customer trust over throughput — Scalability Gates (below) exist specifically so a throughput improvement is never shipped at trust's expense
Trust Preservation Principle
Scalability is successful only when customers cannot detect that the platform has grown, except through improved responsiveness.
Every architectural guarantee established throughout ABS, BIS, FIE, and the BUILD series must remain unchanged regardless of scale. This is the north-star principle every performance decision in this document answers to: increasing throughput while weakening customer trust is a failed optimization, not a successful one with an acceptable tradeoff. Section 10 names the specific guarantees this principle protects; Scalability Gates and the Performance Regression Policy below are how it is enforced mechanically rather than left as an aspiration.
Performance Regression Policy
An explicit, unambiguous decision rule for engineering during optimization work — no optimization may reduce:
Determinism
Explainability
Evidence Integrity
Lineage
Confidence
Verification Quality
even if latency, throughput, or infrastructure cost improves. A performance change that weakens any guarantee above is classified as a regression, full stop — it is rejected at Scalability Gates (below) regardless of how compelling its benchmark numbers are, the same fail-closed posture this platform applies everywhere else a tradeoff between speed and correctness could otherwise tempt a shortcut.

Section 6 — Scaling Strategies
Strategy
Application
Horizontal
Stateless API layers and worker pools scale by adding instances, per FIE-BUILD-002 §9 — the default strategy wherever a service's design permits it
Vertical
Reserved for genuinely single-threaded bottlenecks that don't parallelize — the exception, not the default
Partitioning
High-volume tables partitioned by customer_id and time, per FIE-001 §25 — extended to any future table crossing comparable volume
Caching
Read-through caches only where a service's own spec explicitly permits one (e.g. FIE-002 §24's methodology resolution cache), per FIE-BUILD-002 §9's existing rule — never a generic cache-everything default
Async execution
Any operation exceeding roughly one second dispatches as a job, per FIE-BUILD-002 §9

Worker pools
Sized and scaled independently per job type, per FIE-BUILD-003 §3
Cold storage
FIE-001 §17's Hot/Warm/Cold tiering — the primary lever for controlling storage cost as historical volume grows

Cold-tier compressed detail plus reproducible Snapshot summaries, per FIE-001 §17 — never a lossy aggregation nobody can regenerate

Section 7 — Database Scalability
Partitioning — per FIE-001 §25, by customer_id and time, applied to every high-volume table as it emerges
Indexes — every foreign key and every documented Query Pattern (each service's own Query Patterns section) has a supporting index before that endpoint ships, per FIE-BUILD-002 §8
Retention — per each service's own retention policy, consistently enforced
Archive — Cold-tier movement per FIE-001 §17, extended to any comparable future store
Compression — applied at the Cold tier, never at Hot, where query latency matters most
Append-only optimization — write-heavy, append-only tables (FIE-001 temporal_records, FIE-003 financial_intelligence_objects) are indexed for write throughput first, read patterns second, since they are written far more often per row than they are individually queried
Historical storage — reproducible Snapshot summaries (FIE-001 §12) reduce the need to scan raw historical detail for common aggregate queries
Section 8 — Queue Engineering
Job prioritization — incident-severity precedence (FIE-BUILD-005 §9) takes queue priority over routine batch work, not a separate queue-priority scale of its own
Concurrency — bounded per Calculation Profile (FIE-003 §12) and per queue type
Back-pressure — a queue approaching its configured depth threshold slows acceptance of new low-priority work rather than growing unbounded
Retry strategy — exponential backoff, per every service's own Retry Strategy section
Dead-letter queues — per FIE-BUILD-002 §7, retained and alertable, never silently discarded
Worker sizing — scaled per job type independently, per Section 6
Queue monitoring — per FIE-BUILD-003 §9's Queue Health domain and FIE-BUILD-005 §4's Infrastructure Metrics
Section 9 — Connector Scalability
API rate limits — respected per external system, with backoff matching each connector's own documented limits
Polling — used only where a source system offers no event-driven alternative
Event-driven connectors — preferred where available, reducing unnecessary polling load as customer count grows
Path A (CSV/Excel) — scales by upload volume and mapping-confirmation throughput, per ABS-012 §5
Path B (Connector-native) — scales by API rate limit and per-domain connector count, per ABS-012 §1.2
Path C (Hybrid) — scales as the sum of both, per customer, per ABS-012 §1.3
Synchronization — incremental by default; a full resync is an explicit, rare operation, never the default refresh behavior
Incremental loading — only changed records since the last successful sync are processed, per each connector's own extraction logic

Section 11 — AI Scaling
LLM throughput — scaled via provider-level capacity and, where available, batching compatible providers/models
Prompt caching — cacheable only where FIE-005's own architecture permits (e.g. stable system-prompt segments); never applied to the evidence content itself, which must always reflect the actual current data
Parallel reasoning — independent Reasoning Packages (FIE-005 §10) may generate concurrently; a single Reasoning Package's internal steps (Question Understanding → Evidence Assembly → Reasoning → Verification) remain sequential, per FIE-005's own architecture
Model routing — per FIE-005's model routing and narrative provenance model (llm_version recorded on every Narrative Object), routing for cost or latency never breaks auditability, regardless of which model served a given request
Cost optimization — routing to a cheaper model is permitted only where it does not change Verification pass rate or Operational Confidence, checked empirically, not assumed
Narrative batching — multiple audience-specific Narratives for the same Reasoning Package may generate together, since the underlying reasoning is identical, per FIE-005's Narrative Policy model
Verification scaling — parallelized across independent Narratives; never relaxed or sampled to keep pace with volume, per Section 10's guarantee above

Section 13 — Scalability Certification
Before any production capacity expansion, all of the following must pass — the scaling-specific counterpart to FIE-BUILD-003 §13's Platform Certification.
Performance — meets Section 5's targets at the new expected volume
Correctness — output at scale matches output at current scale for identical inputs
Determinism — FIE-003's guarantee holds under the new load profile, verified explicitly, not assumed from lower-volume testing
Evidence — every Financial Evidence Package still fully resolves at the new volume
Confidence — FIE-005 §19's four-dimensional confidence model shows no unexplained shift under load, and confidence propagation continues to satisfy Section 10's guarantee on Operational Confidence
Lineage — full lineage resolution (FIE-BUILD-002 §17) verified at the new volume, not sampled
Verification — FIE-005's fail-closed pass rate holds steady, not merely "acceptable" under the new load
Certification is granted per capacity tier and customer cohort, the same per-cohort discipline FIE-BUILD-003 §13 already established for platform certification generally — a platform certified to scale for 100 customers is not automatically certified for 1,000.

Performance Trust
Optimization without preserving trust is a failed optimization, not a successful one with an acceptable tradeoff.
A concept unique to this platform: performance improvements must never reduce Explainability, Lineage, Evidence, or Confidence. This is not a balancing consideration weighed against speed — it is a hard gate (Scalability Gates, below). A cache that serves stale evidence faster, a batching strategy that obscures which specific inputs produced a result, or a model-routing decision that degrades Verification pass rate are all, by this document's own definition, regressions dressed as improvements.

Scalability Gates
Before any architecture change intended to improve performance is approved:
Does this scale?
Does this preserve determinism?
Does this preserve lineage?
Does this preserve evidence?
Does this preserve explainability?
Does this preserve confidence?
Only once every question above is answered yes may the optimization proceed. This is the performance-specific extension of FIE-BUILD-004's Architecture Compliance Automation — the same mechanical, non-bypassable gate discipline, applied specifically to changes whose stated purpose is speed, since that is exactly the category of change most tempted to trade away a guarantee for a benchmark win.

Principal Software Architect Review
Reviewed for whether scaling engineering preserves every trust guarantee established throughout the architecture, not only whether it improves throughput.
1. Are Any Scalability Responsibilities Still Misplaced?
No. This document extends, rather than duplicates, FIE-BUILD-003's Capacity Expansion Guidelines and FIE-BUILD-005 §14's Capacity Management — both remain correct at their own level of detail; this document is the deeper scaling methodology both explicitly deferred. Section 16's Performance KPIs are stated as complementary to, not a replacement for, FIE-BUILD-005's Operational KPIs. Performance Debt and Scalability Decision Records, added this round, mirror FIE-BUILD-005's Operational Debt and FIE-BUILD-002's Engineering Decision Records exactly, rather than inventing competing mechanisms.
2. Does Any Scalability Content Belong in BUILD-007?
Nothing in this document's core scaling methodology belongs in Security, Compliance & Governance — the two domains are genuinely independent
The boundary is now stated explicitly, not just implied: FIE-BUILD-006 defines how platform capacity scales. FIE-BUILD-007 defines how that scaling remains secure, compliant, and governed. Performance engineering must never redefine security policy; security policy must not redefine scalability architecture
Connector scaling's (Section 9) credential and rate-limit handling remains the one concrete overlap point — FIE-BUILD-007 should reference this document's connector scaling model rather than redefine it
3. Does Every Optimization Remain Subordinate to Financial Trust?
Yes, by explicit policy rather than implied priority. The Trust Preservation Principle states it as this document's north star; the Performance Regression Policy makes it an unambiguous engineering rule (no optimization may reduce determinism, explainability, evidence integrity, lineage, confidence, or verification quality, regardless of latency or cost gain); and Scalability Gates makes that rule a mandatory checklist before any performance-motivated change is approved. All three exist so this answer is enforced mechanically, not merely asserted in the document's introduction.
4. Is BUILD-006 Ready to Become the Authoritative Performance & Scalability Handbook?
Yes. Every one of the nineteen required sections, all four additional recommendations, and all eight refinements from this review round are present, every mechanism traces back to a specific guarantee already established in ABS/BIS/FIE or a prior BUILD document, and the BUILD-007 boundary is now stated as an explicit, symmetric rule rather than a one-directional note. Recommend freezing FIE-BUILD-006 and proceeding to FIE-BUILD-007 (Security, Compliance & Governance) per the authoritative roadmap.
