Section 1 — Scope Decisions
BIS-004 is the fourth Build Implementation Specification, following the discipline established in BIS-001 through BIS-003. The first six decisions were specified in the build brief; this section restates them for completeness and adds five further resolutions the validation execution model requires to be build-ready.
 
1.1 Validation Platform vs. Canonical Platform
The Canonical Platform (BIS-003) validates structural payload shape and stores canonical data — it answers "is this object structurally valid?" The Validation Platform validates business correctness, data completeness, relationships, reconciliations, and cross-domain consistency — it answers "can this object be trusted for financial intelligence?" These are sequential, not overlapping questions: an object must pass BIS-003's structural validation before it can even be written, and only written objects are eligible for this service's business-correctness validation.
 
1.2 Validation Platform vs. CAL
The Validation Platform produces validation results and readiness inputs. CAL (EVAL-001) determines module status: READY, PARTIAL, or UNAVAILABLE. This service never assigns final capability status — its output is structured evidence (Section 15) that CAL consumes as one of several inputs.
 
1.3 Validation Platform vs. Confidence Scoring
The Validation Platform generates validation findings and validation-based confidence adjustment recommendations. The Confidence Scoring Agent (EVAL-003) aggregates final confidence, applying this service's recommendations alongside other IMS Section 7 adjustment factors. This service stores adjustment recommendations, never final module or object confidence — object confidence itself is stored by the Canonical Platform (BIS-003 Section 13), which this service writes to only via the recommendation-and-apply flow specified in Section 13 of this document.
 
1.4 Validation Platform vs. Orchestration Service
The Validation Platform does not own workflow state. If validation produces a BLOCK condition, this service returns the result to the calling worker; the worker reports it to BIS-002 (Orchestration Service), which owns pause, escalation, and human task routing. This service never calls BIS-002 directly.
 
1.5 Rule Registry Ownership
Validation rules are versioned platform artifacts, originating from IMS Section 5, SCBM business constraints, SCDM field rules, CAL module requirements, and cross-domain reconciliation rules. This service stores and executes rules; rule definitions themselves are version-controlled content, authored by SMPL engineering as IMS documents evolve, not generated by this service.
 
1.6 Validation Results Are Immutable
Validation results are append-only. Rerunning validation creates a new validation_run_id; prior results are never overwritten. This enables auditability, comparison across runs, and future implementation replay.
 
1.7 New Resolution — Bulk Read Pattern from Canonical Platform
Section 22's performance target — 10,000 objects validated in under 60 seconds — is unachievable via 10,000 individual BIS-003 GET /canonical-objects/{object_id} calls. Resolution: this service reads canonical data exclusively through BIS-003's paginated list endpoint (GET /canonical-objects, BIS-003 Table BIS3-4.3), consuming pages at BIS-003's stated default page size (100) up to its max (1,000), matching the cursor-based pagination model BIS-003 Section 14 already established. A single object-level validation run for 10,000 objects issues approximately 10 paginated read calls, not 10,000 — this is the difference between meeting and missing the performance target.
 
1.8 New Resolution — Validation Trigger Model: Push, Not Poll
Validation runs are synchronous and job-triggered, never a background poller scanning for newly-written canonical objects. The Capability Worker executing an EVAL-002 (Validation Agent) job — dispatched by BIS-002 per Table BIS2-7.2 Step 14 — calls POST /validation-runs with scope={session_id} as one step in its own job execution. This mirrors the synchronous, job-triggered pattern BIS-003 Section 1.10 established for identity resolution, keeping the platform's execution model consistent: no service in the write-and-validate path runs independent background scans at MVP.
 
1.9 New Resolution — Rule Versioning Interacts with Immutable Results, Not the Other Way Around
Rules are themselves versioned (append-only, like canonical objects in BIS-003): PATCH /validation-rules/{rule_id} creates a new rule_version rather than mutating the active rule in place. Every validation_results row permanently references the rule_version that produced it (Section 6.1). A rule update never retroactively invalidates or triggers re-evaluation of prior results — the only way to get updated results against a new rule version is an explicit new validation_run. This is what makes 1.5 (rules are versioned) and 1.6 (results are immutable) consistent with each other rather than two independent claims that could otherwise conflict when a rule changes mid-implementation.
 
1.10 New Resolution — BLOCK Severity Uses the Established Signal-Not-Enforce Pattern
A validation_results row with failure_behavior=BLOCK_CAPABILITY or BLOCK_IMPLEMENTATION does not itself halt anything — per Section 1.4, this service has no mechanism to pause a session or create a human task. It surfaces the block via the validation_run's block_count and via a clearly flagged entry in the response envelope. The calling worker reads this and reports BLOCK_CONDITION to BIS-002 exactly as BIS-002 Table BIS2-15.1 already specifies. This is the third BIS document to use this exact pattern — see BIS-002 Table BIS2-15.1 (Orchestration Service's response to BLOCK_CONDITION) and BIS-003 Section 1.11 (SOA conflict routing) for the two prior instances. No new escalation mechanism is introduced here.
 
1.11 New Resolution — Reconciliation Validation Scope Boundary (FIDS)
Per the build brief's explicit instruction, this service does not build analytics-specific waterfall reconciliation logic for revenue, bookings, ARR, cash, or forecasting. MVP-buildable reconciliation rules are deterministic, single-domain, sum-matching checks already fully specified in IMS Section 5 — invoice total equals sum of invoice lines, payments tie to invoices, GL revenue agrees to recognized revenue at the account level. Waterfall-style reconciliations (beginning ARR + new + expansion − contraction − churn = ending ARR; beginning pipeline + created − closed won − closed lost = ending pipeline; beginning cash + inflows − outflows = ending cash) require calculation logic and an analytical schema that belongs to the future Financial Intelligence Data Platform (FIDS) phase. This service defines the RECONCILIATION rule_type and its interface (Section 11) so FIDS can register concrete waterfall rule instances into this registry later without a schema change here — but it implements no waterfall rule bodies at MVP.

GL Transaction REJECT rate < 1% (IMS-001 Table 5.4)

A sequence of period-based records should have no unexplained gaps
Monthly ARR Movement records should not skip a month without a documented reason

7.1 Suite Composition Rules
A rule may belong to more than one suite — e.g., a REQUIRED_FIELD rule on Customer Account.email may appear in both a CONNECTOR_IMS suite (as part of that connector's IMS Section 5) and the OBJECT suite for Customer Account.
Suite membership is explicit (rule_ids array), not computed dynamically at run time — this keeps a given validation_run's scope fully reproducible and auditable, since the suite_version at the time of the run determines exactly which rules executed.
MODULE_READINESS suites are the suite type CAL's evidence bundle (Section 15) most directly consumes — a module's blocking_rules list in the CAL evidence bundle is derived from that module's MODULE_READINESS suite's BLOCK_CAPABILITY and BLOCK_IMPLEMENTATION rules specifically.
 
7.2 Automatic Suite Resolution
When POST /validation-runs (Table BIS4-4.6) is called without an explicit suite_id, the Suite Resolver applies this precedence: if scope specifies connector_id, resolve the matching CONNECTOR_IMS suite; if scope specifies object_type, resolve the matching OBJECT suite; if run_type=CROSS_DOMAIN, resolve all active CROSS_DOMAIN suites; if run_type=RECONCILIATION, resolve all active suites containing RECONCILIATION-type rules currently implemented at MVP (Section 1.11). This resolution logic is deterministic and testable in isolation (Section 25) — it never falls back to "run everything" as a default.

Section 12 — Data Quality Scoring
 
12.1 Health Score Formula
health_score = 100
             − (flag_count / object_count) × FLAG_WEIGHT
             − (reject_count / object_count) × REJECT_WEIGHT
             − (block_count / object_count) × BLOCK_WEIGHT
Default weights (configurable per Section 24):
  FLAG_WEIGHT   = 30   (a 10% flag rate reduces score by 3 points)
  REJECT_WEIGHT = 60   (a 10% reject rate reduces score by 6 points)
  BLOCK_WEIGHT  = 100  (a 10% block rate reduces score by 10 points)
Floor: health_score is never negative; clamped at 0.
Ceiling: 100, achieved only when object_count > 0 and
         flag_count = reject_count = block_count = 0.

Implementation
No UPDATE path exists

Section 18 — Retry Strategy
Rule
Specification
Validation runs are idempotent by idempotency_key
POST /validation-runs (Table BIS4-4.6) accepts and requires idempotency_key; retry returns the existing run's current state, never starting a duplicate execution
Immutable results prevent duplicate rows on retry
Because a retried POST /validation-runs call returns the existing validation_run_id rather than re-executing, no duplicate validation_results rows are ever created by a retry — this follows directly from the idempotency guarantee above, not a separate deduplication mechanism
Failed runs can be rerun as a new validation_run_id
A run reaching status=FAILED (e.g., due to BIS-003 unreachability partway through) is not retried in place — the caller submits a new POST /validation-runs with a new idempotency_key, producing a fresh validation_run_id, consistent with Section 1.6's immutability principle applying even to failed attempts
Cancelled runs remain auditable
No retry logic applies to a CANCELLED run specifically — cancellation is a terminal, intentional caller action, not a failure state to recover from
BIS-003 (Canonical Platform Reader) unreachability
3 retries, exponential backoff (30s, 60s, 120s), matching the pattern established across BIS-001 through BIS-003 for external dependency unavailability; a run failing after exhausted retries transitions to status=FAILED, not an indefinite RUNNING state
Postgres errors
Linear backoff: 30s, 30s, 30s (3 attempts), matching the pattern established in BIS-001 through BIS-003; pages on-call after exhaustion

Section 28 — Failure Recovery
Failure
Immediate Effect
Recovery Behavior
Postgres unreachable
All reads and writes fail with INTERNAL_ERROR
Fail closed, matching BIS-001 through BIS-003. No application-layer cache exists to desync, so recovery is automatic and complete once Postgres returns.
BIS-003 (Canonical Platform) unreachable
New validation runs cannot start (Section 1.7 hard dependency); in-progress runs that have already paginated their data can complete against already-retrieved pages but cannot fetch additional pages
Retried per Section 18; if retries exhaust, the run transitions to status=FAILED with a clear error indicating the BIS-003 dependency, not a generic internal failure — this distinction matters for on-call triage, since a BIS-003 outage is a different incident than this service's own bug
This service crashes or is redeployed mid-request
In-flight requests fail; a long-running validation-run's HTTP connection is dropped
Stateless design means any replacement replica serves the next request identically. A caller whose validation-run request was interrupted retries with the same idempotency_key (Section 18); if the run had made partial progress before the crash, that progress is lost (this service does not checkpoint mid-run per-object progress at MVP) and the retry re-executes the full run — this is an accepted MVP trade-off given Section 22's targets are all under 2 minutes, making full re-execution cheap relative to building mid-run checkpointing.
A single rule's evaluation logic throws an unexpected exception
That rule's result for that specific object is recorded as VALIDATION_EXECUTION_FAILED (Section 17)
The run continues evaluating all other rules and objects — a single bad rule never aborts a run; the failure is visible in the run's summary counts and flagged for engineering investigation via Section 20's per-rule failure rate metric.
A cross-domain validation's second-domain data is unavailable (e.g., BIS-003 returns zero objects for the Billing side of a CRM↔Billing check)
The cross-domain check cannot compute a meaningful match rate
Recorded as result_status=INFO with a message indicating insufficient data, not as a FLAG or REJECT — a genuinely empty domain (e.g., a customer with no Billing connector) is a valid, expected state, not a data quality failure, distinguishing this from Table BIS4-10.1's threshold-breach FLAG behavior.

BIS-004 is complete and ready for engineering to begin implementation. Together, BIS-001 through BIS-004 specify the complete data path GPES-001 traces end to end: external systems (Connector Proxy Service) through orchestration (Orchestration Service) to durable canonical storage (Canonical Platform) to trust assessment (Validation Platform). CAL Service and Reporting Service remain as the two natural next documents — CAL as the direct consumer of this document's Section 15 evidence bundle, Reporting as the consumer of both CAL's output and this document's validation health for customer-facing communication.
 
The most consequential design decision in this document is Section 1.11 — the explicit FIDS boundary. The build brief asked for restraint here, and restraint is easy to say and hard to actually exercise in a specification document, since the natural instinct when documenting a "Reconciliation Validation" section is to solve the interesting problem in front of you. Table BIS4-11.2 exists specifically to make the boundary a designed feature rather than an omission — five reconciliation types are named, their formulas stated, and their reason for deferral given, so that when FIDS is eventually specified, this document does not need to be revisited to make room for them; it already has the room.
