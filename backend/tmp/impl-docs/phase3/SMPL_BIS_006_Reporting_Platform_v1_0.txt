Section 1 — Scope Decisions
BIS-006 is the sixth Build Implementation Specification, following the discipline established in BIS-001 through BIS-005. The first six decisions were specified in the build brief; this section restates them for completeness and adds five further resolutions the reporting execution model requires to be build-ready — including one sequencing correction the series needs made explicit before engineering starts.
1.1 Reporting Platform vs. Orchestration Service
Orchestration (BIS-002) owns workflow state — session status, current GPES state, job dispatch, gate resolution, activation status. The Reporting Platform reads that state through BIS-002's registered read endpoints and summarizes it for a human audience. This service never advances an implementation stage, pauses or resumes a session, activates a module, or resolves a gate. Every report it produces is a read-only rendering of state another service owns; if that state changes, the report does not — a new report_run is required to reflect it (Section 19).
1.2 Reporting Platform vs. Canonical Platform
The Canonical Platform (BIS-003) is the system of record for canonical business objects. This service reads canonical data through BIS-003's paginated list endpoints — following the exact bulk-read pattern BIS-004 §1.7 established against the same API — to populate report content such as connector-level object counts and canonical population summaries. It writes no canonical objects, relationships, or confidence values back to BIS-003 under any circumstance.
1.3 Reporting Platform vs. Validation Platform
Validation (BIS-004) executes rules and produces validation_results, confidence adjustment recommendations, and health scores. Reporting reads validation_results and translates them into customer-facing explanations — why a check failed, what it affects, how severe it is. This service executes no validation rule and writes no validation_results row. Where a BIS-004 finding references a rule_version, this service's rendered explanation always cites that same rule_version, never a paraphrase drawn from memory of what the rule generally does.
1.4 Reporting Platform vs. CAL / Confidence Scoring
CAL (executed as the Capability Worker, EVAL-001, per BIS-002 §1.1 — see 1.8 below) determines module status: READY, PARTIAL, or UNAVAILABLE. Confidence Scoring (EVAL-003) determines final object and module confidence. This service explains readiness and confidence using the structured outputs both already produced; it has no path in its API surface that returns a module status it computed itself. If a CAL result is missing or stale for a requested report, the correct behavior is EVIDENCE_UNAVAILABLE (Section 21), never a locally inferred substitute.
1.5 Reporting Platform vs. Knowledge Platform
The Knowledge Platform (BIS-005) stores reusable, approved implementation knowledge and patterns. This service may retrieve approved knowledge — for example, a generalized explanation pattern for a recurring validation finding — to make a narrative more specific and consistent across customers. It creates no new knowledge records and has no write path into BIS-005's tables; a narrative it generates may later become the input to a human-approved knowledge record, but that promotion happens inside BIS-005's own governance flow (BIS-005 Section 12), not here.
1.6 Reporting Platform vs. FIDS
Per the build brief, this document does not define the Financial Intelligence Data Platform's analytical schema, waterfall calculation logic, or forecasting models. Section 16 defines the narrow MVP surface this service can respons‌ibly expose today — validated, already-canonical data rendered as basic visibility, not calculation — and the interface boundary FIDS will plug into once it exists. This mirrors the discipline BIS-004 §1.11 already applied to reconciliation validation: name the boundary, build the deterministic slice available today, and leave the seam ready rather than either overbuilding or ignoring the topic.
1.7 New Resolution — Sequencing Correction: This Document Fulfills the "Reporting Service" BIS-004 Already Anticipated
BIS-004's closing assessment states explicitly: "CAL Service and Reporting Service remain as the two natural next documents — CAL as the direct consumer of this document's Section 15 evidence bundle, Reporting as the consumer of both CAL's output and this document's validation health for customer-facing communication." BIS-006 is that document. A separate interim architecture note, written between BIS-005 and this build brief, proposed that BIS-006 introduce longitudinal organizational Memory as the first service of a new Finance Intelligence layer. The build brief that actually governs this document supersedes that proposal: BIS-006 is the Reporting Service, a Stage 1 implementation-output service consistent with BIS-001 through BIS-005, not the Memory service. Memory — prior variance explanations, forecast accuracy history, recurring pattern recognition across reporting periods — remains unbuilt and unscoped. It should be numbered and specified as its own future BIS once its architecture is defined, rather than retroactively treated as delivered by this document. This resolution exists so the series' own numbering does not create a false record of what has and has not been built.
1.8 New Resolution — CAL Has No Standalone BIS
The reader may reasonably expect a BIS between Validation (004) and this document specifying "the CAL Service." None exists, and none is missing: BIS-002 §1.1 already establishes that CAL work is executed by the Capability Worker (EVAL-001/EVAL-003), a worker process governed by the Orchestration Service's job dispatch model and the ABS-011 playbook for that role — not a standalone stateful network service with its own datastore. CAL therefore had no independent build specification to write; its behavior is fully specified across BIS-002 (dispatch), BIS-003 (object confidence it reads), BIS-004 (validation evidence it reads), and the EVAL-001/EVAL-003 playbooks (its decision logic). This document is the next — and, per 1.7, correct — entry in the BIS sequence.
1.9 New Resolution — Report Generation Trigger Model: On-Demand and SOF-Stage-Triggered, Never Continuous
Following the synchronous, job-triggered pattern BIS-003 §1.10 and BIS-004 §1.8 both established, this service runs no background poller scanning for reportable state changes. Reports are generated in exactly two ways: (a) on-demand, via a direct POST /v1/reports/generate call from an authorized caller (Tool Gateway on behalf of a human, or an Implementation Consultant UI action); or (b) SOF-stage-triggered, where the Orchestration Service's stage-transition logic (BIS-002 Table BIS2-7.2) calls this service as one step of a stage-completion job — for example, generating a Customer Review Packet is the defined Stage 6 exit action. In both cases the caller supplies session_id and report_type; this service never independently decides that a report is due.
1.10 New Resolution — Narrative Non-Determinism Is Bounded by Immutable Storage, Not by Constraining the Model
LLM-generated narrative text is inherently non-deterministic even at low temperature. Rather than attempting to force determinism at the model layer, this service bounds the consequence of non-determinism at the storage layer, using the same append-only discipline BIS-003 §1.5 and BIS-004 §1.6 apply to their own domains: a generated report_run's narrative content is written once and never edited in place. Regenerating a report — whether because underlying evidence changed or because a customer wants updated wording — always produces a new report_run_id with its own report_version, never a mutation of the prior run. This guarantees that a published report a customer or board has already seen can never silently reword itself, while still allowing narrative quality to improve over time through new runs.
1.11 New Resolution — Rendering Pipeline Ownership for PDF / DOCX / PPTX
JSON and Markdown/HTML report generation complete synchronously within this service's stateless API layer. PDF, DOCX, and PPTX rendering (Section 7) are heavier, longer-running conversions unsuited to a synchronous request path. Consistent with the EIS-002 pattern of keeping the API layer stateless and delegating long-running work to an async worker, this service dispatches an Artifact Rendering Worker job for any artifact_type requiring binary document conversion. The API returns a report_run_id immediately with status=RENDERING; the caller polls GET /v1/reports/{report_id} or receives a webhook/event when status becomes COMPLETE. This keeps Section 26's p95 API latency targets meaningful — they describe the API call, not the full rendering pipeline — and avoids making the Reporting Platform's request path only as fast as its slowest export format.

Section 17 — Narrative Generation Rules
Every LLM-generated narrative is governed by the following rules, enforced by the Narrative Generator component (Section 5) before content is written to a report_section — not left to prompt instruction alone:
Every narrative claim must trace to structured evidence in the report_run's evidence bundle (Section 18)
Never fabricate a missing result — if evidence is unavailable, the section states that plainly rather than inferring a plausible value
Never state a module is READY unless CAL's current output says READY
Never suppress a validation blocker to make a summary read more favorably
Never expose raw sensitive values unless the caller's permission scope explicitly allows it (Section 25)
Use customer-appropriate language for customer-facing report types; use technical language for internal-facing report types (VALIDATION_SUMMARY, GAP_REPORT)
Always include confidence context where the underlying data has anything less than full confidence
Always include FIDS scope limitations when a customer or reviewer might otherwise expect a calculation this service does not perform
Label estimates clearly — no estimated or partial figure is presented without an explicit label
A post-generation validation pass checks every generated claim in a report_section against its declared source_evidence_refs before the section is marked COMPLETE; a claim with no resolvable reference fails generation rather than being silently dropped or published unverified.

Section 19 — Report Versioning and Auditability
Every report generation creates a new report_run_id
Generated reports are immutable once status=COMPLETE — no field of a completed report_run or its sections is ever updated in place
Regenerating a report creates a new report_version, linked to the prior version for comparison, never a mutation of the existing one
Artifacts are content-hashed at creation; the content_hash is included in the artifact response so a caller can verify integrity
Published reports (published=true) cannot be silently edited — the only permitted transitions after publish are archive and the creation of a new report_version
Archived reports remain queryable by authorized users; archiving is a visibility state, never a deletion

Section 22 — Retry Strategy
Report generation is idempotent by report_run_id or the caller-supplied idempotency_key (Section 4.1)
Artifact writes to object storage are retryable with exponential backoff
A failed report generation can be rerun, always as a new report_run_id — never retried in place against the same run
Published report artifacts are immutable and are never regenerated in place, even on a caller retry
Template updates (Section 4.4 PATCH) never mutate or trigger regeneration of prior generated reports
