Section 0 — Scope Decisions
BIS-001 is the first Build Implementation Specification in the SMPL engineering library — a level of detail below the EIS documents, specific enough that an engineer can implement the service directly from this document without re-deriving design decisions from architecture. Three scope ambiguities in the prior documents are resolved explicitly here, because silently resolving them inside the build would create drift between this document and EIS-002.
 
0.1 Scope Decision — Extraction Engine Consolidation
EIS-002 Table EIS2-2.1 lists "Connector Proxy Service" and "Extraction Engine" as separate runtime services. This BIS's section list (Section 9, Extraction Engine; Section 10, Pagination Handling) places both inside the Connector Proxy Service build. Resolution: for MVP, the Extraction Engine is implemented as a co-located internal component within the same deployable as the Connector Proxy Service — not a separate network service. This is a build-time consolidation consistent with EIS-002 Section 10.5's explicit guidance not to over-decompose before scale requires it. The two remain logically distinct components (Section 4 documents them as separate internal components with a defined interface between them) so that a future split into independent services, if load ever justifies it, requires no interface redesign — only a deployment change.
 
0.2 Scope Decision — Checkpoint Ownership Remains with the Caller
EIS-002 Section 5.2 (Checkpoint Recovery Protocol) establishes that Connector Worker crash recovery resumes from a checkpoint stored in the Job record (Postgres) and object storage, not from state held inside a runtime service. This BIS's Section 13 ("Checkpoint Creation") does not make the Connector Proxy Service stateful. Instead, Section 13 specifies the checkpoint data contract: the exact fields every extraction response returns so that the calling Connector Worker (or the Job Service on its behalf) can persist a resumable checkpoint. The Connector Proxy Service holds no extraction progress state between calls — every extract_object_batch call is a complete, independent request carrying its own page_cursor input and returning its own next_page_cursor output. This preserves the stateless-service, stateful-job recovery model established in EIS-002 without modification.
 
0.3 Scope Decision — Connector Adapter Pattern
Twenty-one connectors, each with a distinct authentication method, pagination model, rate limit structure, and schema, cannot be implemented as inline conditional logic without becoming unmaintainable and untestable in isolation. This BIS specifies a ConnectorAdapter interface (Section 4.2): one adapter implementation per IMS connector (IMS-001 through IMS-305), each independently unit-testable, independently versioned, and registered in a data-driven Connector Registry (Section 20) so that connector-specific configuration — base URLs, auth type, rate limit parameters — can be updated without a code deployment. Business logic that differs meaningfully between connectors (pagination style, auth flow) lives in code, one file per connector; configuration that is just data (rate limit numbers, base URLs, API version strings) lives in the registry.
 
Section 1 — Service Purpose
The Connector Proxy Service is the only component in the SMPL platform that sends network requests to customer-connected external systems. Every other service and every AI worker reaches external systems exclusively through this service's API — never directly.

Section 5 — Authentication Flow
Five authentication patterns cover all 21 IMS connectors. Each is implemented once, shared across every adapter that uses it — an adapter declares its auth_type and the Credential Resolver dispatches to the matching flow.

Connectors Using It
Flow Summary
OAUTH2_CLIENT_CREDENTIALS
NetSuite (TBA variant), Sage Intacct, Dynamics 365 Finance/Sales, SAP S/4HANA (BTP), Zuora, Workday, UKG Pro (where configured)

5.1 Token Caching and Refresh
FOR every OAuth2-based connector (CLIENT_CREDENTIALS or AUTH_CODE):
  ON first authenticate() call:
    Resolve base credential from Vault.
    Execute token exchange with connector token endpoint.
    CACHE: {access_token, expires_at} in Redis, keyed by
           "auth_token:{session_id}:{connector_id}"
    TTL: expires_at minus a 5-minute safety margin.
  ON every subsequent authenticated call:
    CHECK Redis cache for a non-expired token.
    IF found: use directly, skip token exchange.
    IF not found or expired:
      Re-resolve credential from Vault.
      Execute token exchange again (refresh flow for AUTH_CODE type;
      re-request for CLIENT_CREDENTIALS type).
      Update cache.
  Access tokens are NEVER returned to the calling AI worker or logged
  in any form. They exist only within the Credential Resolver's
  Redis cache and the outbound HTTP request to the external connector.
 
Section 6 — Credential Management
Lifecycle Stage
Detail
Creation
Implementation Consultant (human, via UI) creates a credential in Vault through create_connector_credential_reference (EIS-001 Category 12). The Connector Proxy Service never creates credentials — it only resolves references that already exist.
Storage
Vault stores the raw credential encrypted at rest, in a namespace isolated per customer (path pattern: secret/customers/{customer_id}/connectors/{connector_id}). No cross-customer path traversal is possible — Vault ACLs enforce this at the policy layer, not just the application layer.
Resolution
Connector Proxy Service authenticates to Vault using a service identity with read-only access scoped to the specific customer namespace needed for the current request — never a namespace-wide or global Vault token.
Scope enforcement
Every credential reference carries a scope_restrictions field (EIS-001 Table EIS-C12.1); the Connector Proxy Service validates that scope includes READ_ONLY before using the credential for any request — a credential without this restriction is rejected with INVALID_INPUT, treated as a provisioning error.
Rotation
rotate_connector_credential_reference (EIS-001 Category 12) issues a new credential_reference_id pointing to updated Vault contents; the Connector Proxy Service invalidates any cached token for the old reference immediately upon rotation, forcing re-authentication on the next call.
Revocation
revoke_connector_access removes Vault access for a credential_reference_id; any subsequent resolution attempt returns AUTH_ERROR; cached tokens for the revoked reference are proactively purged from Redis, not just left to expire.
Table BIS-6.1 — Credential lifecycle. The Connector Proxy Service participates in Resolution and the immediate cache effects of Rotation/Revocation; Creation lifecycle stages are owned by the Credential Vault Service and Implementation Consultant UI.

Section 8 — Schema Discovery
Schema discovery is where the platform detects when a connector's live API has drifted from what its IMS document expects — the origin point for every SCHEMA_CHANGED error and every PENDING_REVALIDATION memory event.
 
8.1 Schema Comparison Algorithm
ON GET /v1/connectors/{connector_id}/schema:
  1. LOAD expected_schema from IMS Content Service
     (get_ims_section for the connector's Section 3 field maps)
  2. EXECUTE a live schema probe via the connector adapter:
     - For REST APIs with metadata endpoints: call the metadata endpoint
     - For APIs without metadata endpoints: sample N recent records
       of each object type and infer field presence and type
  3. COMPARE live_schema against expected_schema:
     FOR each field in expected_schema:
       IF field missing from live_schema:
         → schema_diff.append({field, change: "MISSING", severity: HIGH})
       IF field type differs:
         → schema_diff.append({field, change: "TYPE_CHANGED", severity: HIGH})
     FOR each field in live_schema NOT in expected_schema:
       → schema_diff.append({field, change: "NEW_FIELD", severity: LOW})
       (new fields are not breaking — they become CCF candidates
        per the IMS custom field pattern, not schema drift)
  4. IF any HIGH severity diff found:
     Return status=SUCCESS with schema_diff populated (not an error —
     the schema WAS successfully discovered, it simply differs)
     Emit SCHEMA_CHANGED_DETECTED event
     → consumed by EIS-004 Section 3.4: triggers PENDING_REVALIDATION
       for all Connector Memory records scoped to this connector_id
  5. IF no HIGH severity diff: cache result for 24 hours
 
This is the single mechanism that keeps the entire platform's IMS-derived knowledge current. A schema check here is the trigger that EIS-004's Memory Generalization Pipeline listens for — nothing else in the platform independently detects connector API drift.

Section 11 — Rate Limiting
Implements the token bucket algorithm and budget allocation specified in EIS-002 Section 6.2 exactly — this section adds the concrete Redis operations and response header contract, it does not modify the algorithm.
 
11.1 Token Bucket Implementation
REDIS KEY: rate_bucket:{session_id}:{connector_id}
REDIS TYPE: Hash — {tokens: float, refill_rate: float, last_refill: timestamp}
ON every extraction or discovery call:
  1. REFILL (lazy refill on read, not a background job):
     elapsed_seconds = now() - last_refill
     new_tokens = MIN(capacity, tokens + elapsed_seconds * (refill_rate/60))
     UPDATE tokens = new_tokens, last_refill = now()
  2. CHECK:
     IF tokens >= 1:
       DECREMENT tokens by 1 (atomic Redis HINCRBYFLOAT)
       ALLOW the call
       remaining_budget_pct = (tokens / capacity) * 100
     ELSE:
       DENY the call
       retry_after_seconds = (1 - tokens) / (refill_rate/60)
       return RATE_LIMIT_ERROR
  3. RESPONSE HEADERS (in addition to the envelope body):
     X-RateLimit-Remaining-Pct: {remaining_budget_pct}
     X-RateLimit-Retry-After: {retry_after_seconds}  (only present on DENY)
 
11.2 Budget Allocation on Session Start
Reuses the EIS-002 Section 6.2 allocation formula exactly: platform_budget = connector_max_rate / active_sessions_using_connector; session_budget = platform_budget / within_session_concurrent_jobs_for_connector. The Connector Proxy Service reads connector_max_rate from the Connector Registry (Section 20), sourced from each connector's IMS Section 1 rate limit documentation.

Section 17 — Security
This section is the build-level implementation of the security enforcement already specified in EIS-002 Table EIS2-10.3 — restated here as concrete controls, not new policy.
 
Control
Implementation
Network isolation
This service is not reachable from the public internet or from any network segment outside the SMPL internal VPC. Only the Tool Gateway's service identity has network-level access (security group / firewall rule scoped to the Tool Gateway's subnet).
Method whitelist enforcement
Security / Audit Middleware (Section 4.8) maintains a hardcoded whitelist of {GET, POST} for the calls this service itself makes outward to connectors, and within POST calls, only to the specific extraction/discovery endpoints each adapter defines — never a generic "make any request" capability. Any adapter code attempting a PUT, PATCH, or DELETE against an external connector fails at the middleware layer with a SECURITY_VIOLATION, not just a code review catch.
Credential isolation
No credential value is ever present in a log line, metric label, error message returned to a caller, or stored in Redis/Postgres in plaintext. Only credential_reference_id (a Vault pointer) crosses any of these boundaries.
Vault access scope
The service identity used to reach Vault has read-only policy scoped to secret/customers/*/connectors/* — no write, no delete, no access to any non-connector-credential Vault path.
Cross-customer isolation
Every request carries session_id, which the Credential Resolver uses to derive the customer-scoped Vault path — there is no code path where a session_id from customer A can resolve a credential under customer B's namespace; this is enforced by path construction, not by a runtime check that could be bypassed.
PII/credential pattern scanning
Before any log write, output_summary is scanned against the same pattern set as EIS-002 Section 5 injection security scan (sk_live_*, Bearer *, password=, private key markers); a match blocks the log write and raises SECURITY_VIOLATION rather than silently logging redacted-but-recognizable content.
Input validation
Every endpoint validates request bodies against a JSON schema before any processing begins; malformed input is rejected with INVALID_INPUT before reaching any adapter or external call.
Rate limit fail-open exception
The one deliberate exception to "fail closed on any security-relevant failure" is the Rate Limiter's Redis-unavailable case (Table BIS-4.3) — an intentional, documented trade-off to avoid a Redis outage halting all customer implementations; this is a resource-protection control, not a data-access control, and the distinction is why it is allowed to fail open where nothing else is.

Section 24 — Failure Recovery
Runbook-level recovery guidance for the dependencies this service relies on, and for individual connector outages.
 
Failure
Immediate Effect
Recovery Behavior
Vault unreachable
All authenticate() and credential resolution calls fail with CONNECTOR_UNAVAILABLE; no new extraction can begin for any connector
Fail closed — this is a hard dependency; no workaround. Existing cached tokens in Redis continue to serve already-authenticated sessions until their TTL expires, providing a brief grace window. Recovery is automatic once Vault is reachable again — no manual intervention needed in this service.
Redis unreachable
Rate Limiter fails open (Table BIS-4.3) — calls proceed without rate-limit enforcement, logged as WARNING; token cache misses force re-authentication on every call (increased latency and load on connector auth endpoints, but not a hard failure)
Degraded but functional. Once Redis recovers, rate limit tracking resumes at full capacity (fresh token buckets) — there is no "catching up" on the gap; this is treated as an acceptable minor cost of the fail-open design.
Object storage unreachable
Extraction batch writes fail with INTERNAL_ERROR after 3 retries (Table BIS-12.1); discovery and authentication continue to function since they do not depend on the temp store
Fail closed for extraction only. Once object storage recovers, extraction resumes normally — no data was lost because failed writes never partially succeeded (all-or-nothing per page).
Single connector outage (e.g., NetSuite maintenance window)
TERMINAL_BLOCKED for jobs targeting that connector, per EIS-002 Section 0.2; all other connectors and all other customers' sessions are entirely unaffected
Automatic — the Connector Proxy Service's per-connector health tracking (Section 16) detects recovery via the next scheduled health probe or the next caller-initiated retry, whichever comes first; no cross-connector or cross-customer blast radius.
This service itself crashes or is redeployed mid-request
In-flight requests fail; the caller (Connector Worker) receives a connection error, mapped to CONNECTOR_UNAVAILABLE or a generic transport error
Stateless design means any replacement replica can serve the next request identically — no session affinity required. The caller's own retry policy (EIS-002 Table EIS2-7.1) handles the transient failure; this service holds nothing that needs recovery on its own restart.

BIS-001 is complete and ready for engineering to begin implementation. It is the first Build Implementation Specification in the SMPL engineering library and establishes the format — scope decisions stated up front, per-endpoint and per-component tables, explicit architectural traceability — that future BIS documents (Tool Gateway, Canonical Data Service, CAL Service, Reporting Service) should follow.
 
The three scope decisions in Section 0 are the most consequential contribution of this document: they resolve real ambiguities between EIS-002's service inventory and this BIS's section list rather than leaving two documents in silent disagreement. An engineer reading only EIS-002 and an engineer reading only BIS-001 should arrive at the same mental model of where the Extraction Engine lives, who owns checkpoint state, and how new connectors get added — that consistency is what makes a Build Implementation Specification trustworthy as a standalone build reference.
