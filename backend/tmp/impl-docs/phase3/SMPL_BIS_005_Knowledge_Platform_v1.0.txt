Section 1 — Scope Decisions
BIS-005 is the fifth Build Implementation Specification, following the discipline established in BIS-001 through BIS-004. The first five decisions were specified in the build brief; this section restates them for completeness and adds six further resolutions the knowledge model requires to be build-ready — several of which reconcile this brief's terminology against EIS-004's already-detailed architecture rather than leaving the two documents to quietly disagree.
 
1.1 Knowledge Platform vs. EIS-004
EIS-004 defined the architecture: the three-tier memory model, the taxonomy-keyed retrieval design, the conflict resolution protocol, the API-version-anchored expiration policy, and the Memory Generalization Pipeline. BIS-005 does not redesign any of this — it is the build specification that makes EIS-004's architecture a running service. Every design decision in this section that appears to introduce something new is, unless stated otherwise, a build-level translation of an EIS-004 decision, not a departure from it.
 
1.2 Knowledge Platform vs. Canonical Platform
The Canonical Platform (BIS-003) stores customer business data — GL Accounts, Subscriptions, Employees. The Knowledge Platform stores implementation knowledge — how those objects are typically mapped, what patterns resolve common issues, what a customer has previously decided. These are categorically different assets with different isolation rules (Section 1.9) and different lifecycles (Section 18); no canonical business data of the kind BIS-003 stores is ever written to this service's tables.
 
1.3 Knowledge Platform vs. Orchestration
The Orchestration Service (BIS-002) manages implementation workflow state — sessions, jobs, gates. The Knowledge Platform provides reusable knowledge that workers consult while executing that workflow. This service holds no session or job state of its own beyond the narrow, ephemeral Working Memory scope defined in Section 1.6.
 
1.4 Knowledge Platform vs. Validation
The Validation Platform (BIS-004) creates validation findings — the record of what was checked and what was found for one specific implementation. The Knowledge Platform stores reusable validation patterns — the generalized, anonymized knowledge of what a specific finding usually means and how it is usually resolved, once that pattern has been observed across enough implementations to be worth generalizing (Section 12).
 
1.5 Working Memory — Separate From Long-Term Knowledge
Short-lived execution context is architecturally and physically separate from long-term reusable implementation knowledge. Working Memory (Section 14) never becomes long-term knowledge automatically — promotion from ephemeral context to a durable Knowledge Record always passes through the same Discovery → Candidate → Review → Approved pipeline (Section 18) that any other knowledge candidate does, regardless of where the candidate observation originated.
 
1.6 New Resolution — Working Memory Is Not EIS-002's Worker State
EIS-002 Section 4.1 already defines a "Worker State" layer: rate limit buckets, IMS pre-fetch caches, extraction page cursors — held in Redis and in-process worker memory, owned by the Connector Proxy Service and the worker process itself, scoped to job execution mechanics. This brief's Working Memory (Section 14) is not a second implementation of that layer. It is narrower and different in kind: the cache of knowledge records retrieved from this service during a job's execution, held so that repeated retrieval calls within the same job do not re-hit the Retrieval Engine, and so that the job's end-of-execution outcome recording (Section 11.2) can reference exactly what was retrieved and whether it was used, without the calling worker needing to resubmit full context. Working Memory rows are keyed by job_id (BIS-002's implementation_jobs.job_id) and carry a TTL matching job duration, mirroring EIS-002's TTL philosophy for a different data class. No other ephemeral execution state — rate limits, extraction cursors, tool call history — lives in this service; that remains exclusively EIS-002/BIS-001 territory.
 
1.7 New Resolution — Six Knowledge Domains Reconciled Against EIS-004's Six Memory Types
EIS-004 Table EIS4-1.1 defined six memory domains: Customer, Connector, Transformation, Validation, Implementation Pattern, and Organizational. This brief's six knowledge domains are: Customer, Connector, Pattern Library, Transformation, Validation, and Decision. Five of the six map directly (Pattern Library = Implementation Pattern, renamed for this document's vocabulary). The sixth does not: Decision Knowledge is new, and Organizational Memory is absent from this brief's list.

1.8 New Resolution — retrieval_key Is Derived, Not Caller-Supplied
This brief's Knowledge Record Model lists customer_scope, connector_scope, and object_scope as discrete fields, distinct from EIS-004's single composed retrieval_key string. Resolution: both exist, and the discrete fields are primary at write time. This service computes retrieval_key from {knowledge_domain, connector_scope, object_scope, and a task-equivalent tag drawn from retrieval_tags} at write time — mirroring the pattern BIS-003 established for normalized_key (Section 1.8 of that document) — never accepting a caller-supplied retrieval_key directly. This preserves EIS-004 Section 0.1's taxonomy-keyed retrieval safety property (deterministic, auditable, no vector-search customer-isolation risk) while giving the API surface the discrete, filterable fields this brief's endpoint definitions expect.
 
1.9 New Resolution — Semantic Retrieval Remains Backlog
This brief notes "semantic retrieval may be used as a fallback" and lists a vector index as optional deployment infrastructure. EIS-004 Section 9.3 already scoped semantic retrieval as a future roadmap item with an explicit trigger condition (minimum 200 APPROVED shared knowledge records). This document does not change that decision: MVP builds structured, taxonomy-keyed retrieval only (Section 15); no vector index is deployed at MVP; the retrieval engine's internal interface is designed to accommodate a semantic fallback path later (an unused hook, not built logic) so that adding it in the future is additive, not a redesign.
 
1.10 New Resolution — Approval Governance Reuses EIS-004's Role Model
This brief's Publication endpoints (POST /publish, /approve, /archive) do not re-specify who may call them. Resolution: this service enforces the exact role and permission model EIS-004 Table EIS4-5.1 already defined (Implementation Engineer creates DRAFT only; Senior Implementation Engineer reviews and approves LOW/MEDIUM sensitivity; Engineering Team Lead approves HIGH sensitivity; the Memory Review Bot equivalent — this service's automated candidate pipeline, Section 18 — creates but never approves; Platform Admin retires only). The self-approval prohibition (approved_by must differ from created_by) is enforced at the API layer, not left as a process convention.
 
1.11 New Resolution — Working Memory Schema
This brief describes Working Memory's contents loosely (current worker, current task, checkpoint, retrieved knowledge, execution context). Section 14.1 specifies the concrete schema: a working_memory table keyed by job_id, storing retrieved_knowledge_ids (an array of knowledge_id references, not duplicated content), the retrieval_key each was retrieved for, a used boolean per entry (set by the worker's outcome-recording call), and a TTL matching the job's own timeout_policy from BIS-002's implementation_jobs record.

Section 15 — Retrieval Engine
Implements EIS-004 Section 6 exactly — structured, taxonomy-keyed retrieval as the only MVP path (Section 1.9), with the same ranking and conflict resolution algorithm already specified.
 
15.1 Retrieval Dimensions
Matching the build brief's list exactly, all nine dimensions are supported as filter parameters on POST /search (Table BIS5-4.3): connector, domain, task (via retrieval_tags), object, validation rule (via content.validation_rule_id for the VALIDATION domain), CEP item (via content.cep_field_path for CUSTOMER/DECISION domains), error (via retrieval_tags), worker type, and implementation stage (via retrieval_tags, e.g., "stage:IMS_RUNNING").
 
15.2 Ranking
Reuses EIS-004 Table EIS4-6.2's weighted ranking formula without modification: 0.40×confidence + 0.25×normalized_usage_count + 0.15×key_specificity_bonus + 0.10×human_approval_recency + 0.10×api_version_match. Customer scope is handled as a pre-filter, not a ranking weight — a CUSTOMER-domain search always scopes to the requesting customer_id before ranking begins, since cross-customer ranking comparison is never a valid operation (Section 24).
 
15.3 Conflict Resolution
Reuses EIS-004 Table EIS4-3.1's three-tier precedence exactly: API version dominance first, confidence×usage product score second, approval recency third, with the same escalate-to-human-review-queue condition (both records unversioned, scores within 10%, neither approved in the past 90 days) producing a conflict_flag=true in the search response (Table BIS5-4.3) rather than an ambiguous result set.
 
15.4 Approval Status Filtering
POST /search and POST /retrieve default to approval_status=APPROVED or PUBLISHED only. A caller may not override this to retrieve DRAFT or REVIEW-status records under any circumstance — unreviewed knowledge is never served to a production worker, full stop. The only exception is CUSTOMER and customer-scoped DECISION domain records, which per Section 8.2/13 are active immediately without passing through REVIEW at all, so this restriction does not apply to them.

18.2 Approved vs. Published Distinction
APPROVED means a human has confirmed the record is technically accurate and safe to share. PUBLISHED means the record is actually live and returned by Section 15's retrieval — for most domains these transitions are simultaneous (approval triggers immediate publication), but the two states are kept distinct in the model so a future workflow (e.g., staged rollout of a new pattern to a subset of implementations before full publication) can be added without a schema change, mirroring the extensibility principle this BIS series has applied consistently since BIS-003's Section 1.9.

Section 31 — Failure Recovery
Failure
Immediate Effect
Recovery Behavior
Postgres unreachable
All durable knowledge reads/writes fail with INTERNAL_ERROR
Fail closed, matching BIS-001 through BIS-004. No application-layer cache of durable knowledge exists, so recovery is automatic once Postgres returns.
Redis unreachable
Working Memory reads/writes fail; retrieval itself (the core function) continues to succeed via Postgres, degraded only in outcome-tracking fidelity (Table BIS5-5.1)
Degraded but functional for the primary use case. Once Redis recovers, new Working Memory rows are created normally; no reconciliation of the gap period is attempted, since Working Memory is explicitly ephemeral and not expected to be gap-free.
This service crashes or is redeployed mid-request
In-flight requests fail; callers receive a connection error
Stateless design (Section 26) means any replacement replica serves the next request identically. A worker's interrupted retrieval call simply retries (Section 21) — no partial knowledge write can occur given the atomic, single-transaction write pattern established across every prior BIS document.
Generalization Pipeline run fails partway
Some candidate records may be created, others not, for that nightly run
The pipeline is naturally re-runnable — the next scheduled run re-evaluates the same minimum-count criteria and will pick up any implementations the failed run missed; no manual intervention is required unless the failure recurs across multiple scheduled runs, which pages on-call per the general INTERNAL_ERROR escalation path (Section 21).
SCHEMA_CHANGED cascade fails to reach all matching records
A connector's Connector/Transformation Knowledge records are inconsistently left in PENDING_REVALIDATION vs. still APPROVED
This is treated as a correctness-critical failure, not a performance degradation — the cascade update runs inside a single transaction scoped to connector_scope, so a partial failure rolls back entirely rather than leaving a mixed, inconsistent state; a retry of the full cascade is safe and idempotent (Section 21).

BIS-005 is complete and ready for engineering to begin implementation. It completes the five-service foundation this BIS series set out to specify: Connector Proxy (external interface), Orchestration (workflow control), Canonical Platform (business data), Validation Platform (trust assessment), and now Knowledge Platform (institutional memory) — the complete architecture GPES-001 traces end to end, now specified at build-ready detail throughout.
 
The most consequential design decision in this document is Section 1.6 — the explicit boundary between Working Memory and EIS-002's existing Worker State. Of every resolution across all five BIS documents, this is the one most likely to have produced genuine, silent architectural drift if left unaddressed: two services independently building "temporary execution context in Redis" under different names, gradually diverging until a debugging session eventually surfaces the duplication as a production confusion rather than a design-time decision. Naming the overlap explicitly and drawing a narrow, specific boundary — Working Memory is retrieval context only, keyed by job_id, and nothing else — is what keeps this platform's ephemeral-state story singular rather than fragmented.
