Section 1 — Scope Decisions
BIS-002 is the second Build Implementation Specification, following the same discipline as BIS-001: every scope ambiguity is resolved explicitly here rather than left for individual engineers to interpret differently. The first four decisions were specified in the build brief; this section restates them for completeness and adds four further resolutions needed to make the specification build-ready.
 
1.1 Orchestration Service vs. Worker Execution
The Orchestration Service dispatches jobs and tracks state — it never executes domain work directly. Connector implementation work is executed by Connector Workers (ERP/CRM/BIL/HRS-DOMAIN). Canonical merge work is executed by the Canonical Worker (COORD-004). CAL work is executed by the Capability Worker (EVAL-001/003). Reporting work is executed by the Reporting Worker (COORD-005). The Orchestration Service owns coordination, never execution — it has no code path that calls a connector API, transforms a field, or writes a canonical object.
 
1.2 Session State Ownership
The Orchestration Service is the system of record for implementation workflow state: session status, current SOF stage, current GPES state, active/completed/blocked jobs, terminal-blocked connectors, pending CEP item references, gate state references, checkpoint references, readiness score, and activation status. Other services read this state through registered tools (read_session_state, EIS-001 Category 1) — no other service maintains a competing copy of workflow state.
 
1.3 Job Queue Ownership
The Orchestration Service creates and persists job records in Postgres first — Postgres is the durable source of truth — then publishes runnable jobs to Redis Streams for asynchronous worker consumption. Workers consume from Redis Streams and report status back through Orchestration Service endpoints (PATCH job status), never by writing to Postgres directly. This preserves exactly one durable source of truth while allowing async, at-least-once job delivery.
 
1.4 GPES State Machine as MVP Runtime Lifecycle
GPES-001's ten-state execution state machine (DISCOVERY through CONTINUOUS_MONITORING) becomes the state the Orchestration Service actually enforces at runtime. The SOF's seven stages remain the architectural reference; Section 1.5 below specifies exactly how the two relate so this decision does not create drift between BIS-002 and the frozen SOF.
 
1.5 New Resolution — GPES State Is Enforced; SOF Stage Is Derived
implementation_sessions tracks both current_gpes_state and current_sof_stage. To avoid two independently-mutable fields drifting apart, exactly one is the enforced primitive: current_gpes_state. Every state transition rule (Section 7) validates and mutates current_gpes_state only. current_sof_stage is a computed, read-only rollup field, recalculated on every GPES state transition using the exact mapping already established in GPES-001 Table 0.1 — reproduced here as Table BIS2-1.1 for this document's self-sufficiency.

1.6 New Resolution — Job Layering: implementation_jobs vs. Connector Proxy extraction_batch_id
BIS-001 defines extraction_batch_id as an identifier for one paginated extraction call inside a Connector Worker's execution. This document's implementation_jobs.job_id identifies a different, higher-level unit of work: an entire agent invocation (e.g., "run ERP-DOMAIN against IMS-001 for this session"), which may internally make dozens of Connector Proxy Service calls, each producing its own extraction_batch_id. The two identifiers are never interchangeable and never appear in the same field. A single implementation_job may reference many extraction_batch_ids in its output_artifact_refs, but an extraction_batch_id never has its own row in implementation_jobs.
 
1.7 New Resolution — Worker Dispatch Uses One Redis Stream Per Worker Type
The Worker Dispatch Coordinator (Section 5) publishes to five separate Redis Streams — stream:orchestrator (rare; used only for session-level system jobs), stream:connector_jobs, stream:canonical_jobs, stream:capability_jobs, stream:reporting_jobs — rather than one shared stream. Each worker type runs its own consumer group against its own stream. This allows independent scaling per worker type (EIS-002 Section 10.5 future scaling path: "split Connector Worker by domain") without a queue redesign — adding a domain-specific stream later is additive, not a breaking change to this architecture.
 
1.8 New Resolution — fan_in_groups.condition Enum
The condition field on fan_in_groups is data-driven per fan-in point, with three valid values: ALL_SUCCESS (every required job must reach a successful terminal status — COMPLETE or COMPLETE_WITH_GAPS; used sparingly, only where a partial result is unacceptable), ALL_TERMINAL (every required job must reach any terminal status including ERROR or CANCELLED, but not TERMINAL_BLOCKED, which does not count as terminal for this condition), and ALL_TERMINAL_ALLOW_BLOCKED (every required job must reach any terminal status, and TERMINAL_BLOCKED explicitly counts as satisfying). The Stage 3 (IMS_RUNNING) fan-in point defaults to ALL_TERMINAL_ALLOW_BLOCKED, per EIS-002 Section 0.2 and GPES-001's TERMINAL_BLOCKED handling (Table EIS2-3.3) — a blocked connector must not indefinitely hold up the other three. Other fan-in points (e.g., a future fan-in requiring confirmed financial data) may be configured to ALL_SUCCESS when partial results genuinely cannot be tolerated.
 
Section 2 — Service Purpose
The Orchestration Service is the only component in the SMPL platform that decides what happens next. Every other service either executes a specific piece of work it is dispatched, or stores data it is told to store — the Orchestration Service is where "what happens next" is decided and recorded.

A connector integration layer — it never calls an external API; that is BIS-001's Connector Proxy Service
The job graph engine — it creates jobs, tracks dependencies, and evaluates fan-in conditions
A canonical data store — it holds job and session metadata, never customer business data or canonical objects
The human-in-the-loop router — every CEP question, escalation, and customer review gate passes through this service's human task tracking
An AI reasoning engine — its own internal logic is deterministic state-machine evaluation, not LLM inference (though the jobs it dispatches may themselves invoke LLM-backed workers)

A reporting service — it triggers the Reporting Worker but does not generate customer-facing summaries itself

Section 4 — Public API Endpoints
Twenty-four endpoints across six groups, callable only by the Tool Gateway, registered workers, and approved internal platform services — never directly by an external client. Endpoints with real branching logic (session start, advance-stage, job creation, fan-in evaluation, human task resolution, activation) receive full detail tables. Simpler CRUD-style endpoints are grouped into compact summary tables.

Section 8 — Job Graph Engine
Constructs the dependency graph for every fan-out point in Table BIS2-7.2. This component never dispatches jobs itself — it creates the graph; the Worker Dispatch Coordinator (Section 9) publishes to the queue once dependencies are satisfied.
 
CREATE JOB GRAPH (called at every fan-out point in Table BIS2-7.2):
  1. VALIDATE the requesting caller is authorized for this session
     (session must be status=RUNNING, not PAUSED or CREATED)
  2. FOR a fan-out with N children:
     IF N > 1:
       CREATE fan_in_groups row: {required_job_ids: [], condition: <per Section 1.8>}
       fan_in_id = new row's ID
     ELSE:
       fan_in_id = null  (single job, no fan-in needed)
  3. FOR each child job:
     CREATE implementation_jobs row with:
       dependency_ids = [parent job_ids this child requires, if any]
       fan_in_id = the shared fan_in_id from step 2, if applicable
     APPEND this job_id to fan_in_groups.required_job_ids
  4. VALIDATE no circular dependency exists across the full graph
     (topological sort check) — REJECT the entire graph creation
     with INVALID_INPUT if a cycle is found; no partial graph is
     ever persisted
  5. RETURN all created job_ids and the fan_in_id (if created)
     to the Worker Dispatch Coordinator for immediate dispatch
     evaluation

Section 16 — Retry Strategy
Two distinct retry layers exist in this service, and they must not be confused: job-level retries (a worker's own retry of its downstream call, e.g., to Connector Proxy Service) and service-level retries (this service's own retry of its dispatch or persistence operations).

Owned entirely by BIS-001 and the calling worker

Section 19 — Security
Control
Implementation
Internal-only service
Not reachable from the public internet; callable only by the Tool Gateway and the five worker types via their internal service identities — matches BIS-001's network isolation model exactly
Role-scoped endpoint access
Each caller's service identity carries a scope; e.g., a Connector Worker's identity can PATCH job status for jobs where worker_type=CONNECTOR but cannot call POST /activate — enforced at the API layer before any business logic executes
Customer isolation
Every request is scoped by session_id, and every session_id maps to exactly one customer_id; Postgres row-level security (matching the pattern established in EIS-004 Section 8.1 for memory records) prevents any query from returning cross-customer implementation_jobs, human_tasks, or fan_in_groups rows even in the presence of an application-layer bug
No raw credentials

No direct canonical data writes
This service has no write access to the Canonical Data Service's tables — it dispatches jobs that perform canonical writes, but never performs one itself
Auditable state changes
Every session and job state mutation produces a STATE_TRANSITIONED or JOB_STATUS_UPDATED log event (Section 17) with previous_state and next_state — the full state history of any session is reconstructable from the log stream alone, independent of the current Postgres row

Section 26 — Failure Recovery
Failure
Immediate Effect
Recovery Behavior
Postgres unreachable
All endpoint calls fail with INTERNAL_ERROR — this is a hard dependency; session and job state cannot be read or written
Fail closed, no workaround. Once Postgres recovers, this service resumes normally — it holds no application-layer state that could desync from Postgres during the outage, since it never caches durable state locally.
Redis unreachable
New job dispatch fails; jobs accumulate in QUEUED status in Postgres (durable, not lost); job status updates from already-running workers still succeed since PATCH job status writes to Postgres directly, not through Redis
Degraded but data-safe. Once Redis recovers, the periodic QUEUED-job sweep (Section 16, every 60s) picks up and dispatches all accumulated jobs — no manual intervention needed.
This service crashes or is redeployed mid-request
In-flight requests fail; callers receive a connection error
Stateless design (Section 21) means any replacement replica serves the next request identically. A worker mid-execution when this service becomes briefly unavailable simply retries its next PATCH job status call per its own retry policy once the service returns — no orchestration-level state is lost because nothing was held only in this service's memory.
A worker crashes without reporting a terminal job status
Job remains RUNNING indefinitely from this service's perspective
A periodic stale-job sweep (checking timeout_at against implementation_jobs.status=RUNNING) identifies jobs that exceeded their timeout_policy.hard_timeout_seconds without a status update, and transitions them to ERROR — this is the mechanism that prevents a crashed worker from silently stalling a session forever.
Redis Streams message delivered twice (at-least-once semantics)
A worker could theoretically receive and begin processing the same job twice
Workers are required to treat execution as idempotent at the canonical-write level (Section 9); this service additionally rejects a second PATCH job status call attempting to move an already-terminal job to RUNNING, preventing the second delivery from corrupting job state even if the worker itself did not fully protect against it.

BIS-002 is complete and ready for engineering to begin implementation. Together, BIS-001 and BIS-002 specify the two services an engineering team needs to build first: the interface to the outside world (Connector Proxy Service) and the control plane that decides what happens next (Orchestration Service). Every other runtime service named in EIS-002 Table EIS2-2.1 — Canonical Data Service, CAL Service, Reporting Service, IMS Content Service — is a natural next BIS, each following the same scope-decisions-first discipline established across these two documents.
 
The most consequential design decision in this document is Section 1.5 — making GPES state the enforced primitive and SOF stage a derived rollup. Without that explicit resolution, an engineer could reasonably have built either field as authoritative, and a future bug where the two fields disagree would have been genuinely difficult to diagnose, since both EIS-002 and GPES-001 reference "the current stage" without specifying which representation is the source of truth. That ambiguity is now closed.
