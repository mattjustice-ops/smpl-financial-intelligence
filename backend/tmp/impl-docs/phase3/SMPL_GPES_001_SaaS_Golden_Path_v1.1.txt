Section 0 — Document Purpose and SOF Stage Mapping
GPES-001 is the first execution specification produced from the frozen SMPL architecture. It does not introduce new architecture, new agents, or new tools. It documents, at execution granularity, exactly what happens when the platform runs a real customer through onboarding — every tool call, every state transition, every checkpoint, every point where a human is asked something and why.
This document exists because architecture specifications answer "what is possible" and execution specifications answer "what actually happens, in what order, and how long does it take." Engineering teams building the MVP runtime (EIS-002) should be able to read this document and know exactly what integration test to write for each stage.
GPES-001 is the reference implementation for SMPL's Golden Path execution model — the benchmark execution pattern, the baseline for runtime performance, and the baseline for implementation metrics. It is also the first candidate entry for the Implementation Pattern Library defined in EIS-004 Section 1.2. Every future GPES document, whether documenting a different connector combination or a more complex customer profile, should be structured and measured against this document's format: the same nine-stage structure, the same execution state machine, the same deviation-pattern catalog, and the same metrics scorecard.

0.2 Design Principles Applied in This Execution
Minimal customer effort: this reference implementation requires 4 discrete customer confirmations totaling approximately 12 minutes of customer time, plus one 45-minute Stage 6 review meeting.
AI discovery over questionnaires: of the 40+ CEP fields populated during this implementation, 33 are AUTO_DISCOVERED and 7 require HUMAN_CONFIRMED input — an 82% auto-discovery rate for this connector combination.
Parallel connector execution: all four connectors authenticate, discover, and implement simultaneously — see Section 5 (Parallel Execution Map) for the full concurrency model.
Non-blocking waits: every PAUSE_FOR_CEP condition in this implementation is resolved without halting any other connector's progress — demonstrated stage-by-stage below.

1.1 Why This Profile and Connector Combination
This combination is deliberately chosen as SMPL's cleanest reference path — not because it hides complexity, but because it isolates the platform's core execution model from the connector-specific complexity documented extensively in the IMS libraries (SAP's ACDOCA filter, Oracle Fusion's ledger designation, Workday's Supervisory Org disambiguation, Zuora's Rate Plan enumeration). Every one of those complexities is real and is documented in its respective IMS — this document demonstrates the platform's behavior when none of them are present, which is the majority case for SMPL's primary target segment: Series B–D SaaS companies on modern, API-first systems.
The four connectors in this combination are Production Ready or fast-resolving across the CKR and IMS libraries: NetSuite (Production Ready ERP, standard configuration with no OneWorld or ARM), HubSpot (fast Stage Normalization Gate resolution due to single default pipeline), Stripe (Production Ready Billing, the IMS-001 reference-quality connector), and Rippling (fastest HRIS in the library, no Position Planning ambiguity, native Payroll narrowing the compensation gap).

This section does not attempt to document every possible failure; it shows the ten most common deviation patterns and demonstrates that the runtime's response to each is deterministic, not improvised. Every deviation pattern below traces back to a specific rule already defined in EIS-002 (Section 7, Retry and Failure Recovery) or the SOF Decision Framework — this section shows those rules in the context of this reference implementation, it does not define new ones.

Field

Rate limit budget exhausted mid-extraction (e.g., HubSpot Property History API rate limit hit during Deal stage-event extraction for a customer with an unusually large deal history)
Runtime Behavior
RATE_LIMIT_ERROR triggers automatic backoff per EIS-002 Table EIS2-7.1: 10s, 30s, 60s, 120s, 300s. The extraction tool's response includes remaining_budget_pct and suggested_next_call_delay_ms, allowing the worker to self-regulate before hitting the limit again.
Worker Actions
CRM-DOMAIN reduces its call frequency proactively when remaining_budget_pct drops below 20% (per the EIS-003 Table EIS3-6.1 Rate Limit Self-Regulation test); if the limit is still hit, applies the backoff schedule
Checkpoint
page_cursor preserved; no data loss; extraction resumes from the exact point it paused
Customer Experience
Typically invisible — extraction simply takes longer for that connector. If the 300s backoff is reached: "This connector has a large amount of history to process; extraction may take longer than usual for this step." No action required.
Recovery Path
Automatic — no human intervention needed. If retry_after_seconds exceeds 300s repeatedly, COORD-001 may re-queue the remaining extraction for an off-peak window (LOW priority) per EIS-002 Table EIS2-7.1, without blocking the rest of the implementation.
Table GPES-6.3 — API rate limiting.

No customer-facing question — this is an engineering issue, not a business decision. Customer sees: "One data type from Stripe requires a brief technical review before it's included — the rest of your implementation continues normally."

SMPL engineering reviews the schema change, updates the affected IMS section, and (per EIS-004 Section 3.2) the connector's memory records affecting the changed object type move to PENDING_REVALIDATION. 6.9 Capability Assessment Blocked
Field
Detail
Trigger
A required canonical object for a capability has zero populated records — for example, if Stripe had zero active Subscriptions at the time of extraction (not the case for Meridian Analytics, which has 812)
Runtime Behavior
EVAL-001 does not treat this as an error — a capability with a genuinely empty required object correctly assesses as UNAVAILABLE or PARTIAL depending on whether the emptiness is expected (e.g., a brand-new Stripe account) or unexpected (e.g., an established account that should have subscriptions)
Worker Actions

Customer Experience
If anomalous: "ARR Reporting couldn't be assessed — we found zero active subscriptions in Stripe, which is unusual for an account of this size. If anomalous and confirmed to be an extraction issue: re-run extraction for the affected connector. If confirmed as expected (e.g., pre-revenue company): capability remains UNAVAILABLE with no further action needed — this is a correct assessment, not a failure state.

Field
Detail
Trigger

7.2 Memory System Contribution
This implementation drew on Connector Memory (EIS-004 Tier 2) at several points, each reducing what would otherwise have been a CEP question:
HubSpot: 5 of 6 stages auto-resolved from Connector Memory pattern matches — without memory, this would have been 6 CEP questions instead of 1.
Rippling: FTE methodology auto-discovered (no memory needed — Rippling exposes this natively); canonical department object auto-resolved (structural, not memory-dependent for this connector).
NetSuite: zero CEP questions — a combination of Rippling-style structural simplicity (single entity, no OneWorld) and Connector Memory confirming this is the expected profile for a company at this ARR/employee scale.
Net effect: this implementation generated 6 CEP questions instead of an estimated 11–13 that a first-ever implementation of this connector combination (with no Tier 2 pattern cache) would have generated — consistent with the CEP question reduction rate target in EIS-004 Table EIS4-9.2.
