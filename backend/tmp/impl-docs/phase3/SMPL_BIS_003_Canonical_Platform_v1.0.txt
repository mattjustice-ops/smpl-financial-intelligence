Section 1 — Scope Decisions
BIS-003 is the third Build Implementation Specification, following the discipline established in BIS-001 and BIS-002. The first six decisions were specified in the build brief; this section restates them for completeness and adds five further resolutions the canonical storage and identity resolution model requires to be build-ready.
 
1.1 Canonical Platform vs. Connector Workers
Connector Workers transform vendor data into canonical object payloads — that transformation logic lives entirely in the IMS libraries and the Connector Worker playbooks. The Canonical Platform validates structural requirements, stores canonical objects, links source references, applies identity rules, and persists canonical relationships. It performs no connector-specific extraction or transformation of its own — if a payload arrives structurally invalid, this service rejects it; it does not attempt to fix it.
 
1.2 Canonical Platform vs. CAL
The Canonical Platform stores objects and object-level confidence. The CAL Service (EVAL-001/EVAL-003, per BIS-002's Capability Worker) evaluates module readiness and capability-level confidence, reading object-level confidence from this service as an input. This service never computes or returns a module status of READY, PARTIAL, or UNAVAILABLE — that vocabulary does not exist in this service's API surface.
 
1.3 Canonical Platform vs. Orchestration Service
The Canonical Platform does not own session state or workflow state. It stores created_from_session_id and created_from_job_id on every canonical object and version for lineage, but the Orchestration Service (BIS-002) remains the exclusive system of record for implementation progress. This service never calls BIS-002's endpoints to check or influence session state — the reference is one-directional, for audit trail only.
 
1.4 Canonical Store Granularity
MVP uses a flexible canonical object store: a generic canonical_objects table (Postgres JSONB payload plus typed indexes on customer_id, object_type, normalized_key, and source reference lookups), not a separate physical table per SCBM object type. Typed projection tables are backlog (Section 29), added only when a specific high-volume analytics or reporting need justifies the schema-migration cost.
 
1.5 Immutable Source References
Raw source references are immutable. If a source object's mapping changes, the service creates a new canonical object version or updates the canonical link — it never mutates a source_references row in place. The full history of which source objects fed which canonical objects, and when, is always reconstructable.
 
1.6 Merge Decisions Require Auditability
All identity merge decisions are logged and reversible. No merge destroys source object identity. A merged object retains all source references and relationship history from every constituent object — merge is a status change and a survivorship decision, never a deletion.
 
1.7 New Resolution — Canonical Object Schema Registry
Section 1.1's "validates structural requirements" needs a concrete source of truth for what structurally valid means per object_type. Resolution: a Canonical Object Schema Registry, one JSON Schema document per SCBM object type (GL Account, Subscription, Opportunity, Employee, etc.), derived from and versioned alongside the SCDM. The registry is loaded at service startup from a versioned configuration store — the same architectural pattern as BIS-001's IMS Content Service (EIS-001 Category 5), not a new mechanism. Every POST or PATCH to a canonical object validates canonical_payload against the registry entry for that object_type before any write occurs; a payload missing a required field or containing a field of the wrong type is rejected with VALIDATION_FAILED, never silently accepted with nulls filled in.
 
1.8 New Resolution — normalized_key Computation
normalized_key is computed by the Canonical Platform itself at write time, never accepted as caller input. Each object_type has a registered normalization function (part of the same Schema Registry entry from 1.7): for Customer Account, normalized_key is derived from lowercased, trimmed email if present, else lowercased, punctuation-stripped company name; for Employee, from lowercased work email; for GL Account, from account_code within the customer's chart of accounts. This is what makes identity resolution (Section 10) and source-reference-based lookup (Section 8) deterministic — two source records that should resolve to the same canonical object produce the same normalized_key independent of which connector or which order they were written in.
 
1.9 New Resolution — Bulk vs. Single-Object Write Boundary
POST /v1/canonical-objects/bulk-upsert is the primary write path for Connector Worker extraction output — batch size matches BIS-001's extraction page_size (default 1,000, max 5,000, per BIS-001 Table BIS-3.6) so the two services' batching boundaries align and a single extraction batch maps to a single canonical write call. POST /v1/canonical-objects (single) is reserved for individually-triggered writes: a Canonical Integration Agent's identity-resolution-driven update to one object, or a human-initiated correction. Connector Workers never call the single-object endpoint in a loop — that pattern is explicitly disallowed and is not a supported integration pattern for this service.
 
1.10 New Resolution — Identity Candidate Generation Timing
For MVP, identity candidate generation runs synchronously as part of the Canonical Integration job (BIS-002 Table BIS2-7.2, Step 13) — the Canonical Worker calls POST /v1/identity-resolution/candidates as one step in its Stage 4 (CANONICAL_POPULATION) execution, not as a separately scheduled background process. The brief's mention of an "optional background job" describes a backlog capability (Section 29) — a periodic re-scan across a customer's full canonical store to catch merge opportunities that were not detected at initial write time (e.g., a new connector added months later introduces a match to an existing object). That capability is out of scope for MVP.
 
1.11 New Resolution — SOA Conflict Routing
When SOA_CONFLICT is detected (Section 17), this service does not create a human task itself — it has no such endpoint and, per Section 1.3, stays out of workflow-state territory. Instead, it returns SOA_CONFLICT to the calling Canonical Worker job via the standard error envelope; the Canonical Worker reports this through its normal PATCH job status call to BIS-002, which routes it exactly as BIS-002 Table BIS2-11.1 already specifies: a SYSTEM_OF_AUTHORITY_DISPUTE human task, routed to the Implementation Consultant only, urgency BLOCKING. No new escalation path is introduced — this service produces the signal, BIS-002 owns the human routing, consistent with the boundary established in Section 1.3.
 
Section 2 — Service Purpose
The Canonical Platform is the only component in the SMPL platform authorized to write a canonical business object. Every capability assessment, every confidence score, every customer-facing report ultimately reads from what this service stores.

8.1 Source Reference Rules
Source references are immutable (Section 1.5) — a row, once written, is never updated. A change in mapping is recorded by inserting a new source_references row and setting mapping_status=HISTORICAL on the prior one, never by mutating the prior row.
Source references are customer-scoped — the UNIQUE constraint (Table BIS3-4 schema) includes customer_id explicitly, so the same vendor object_id from two different SMPL customers who happen to use the same connector never collides.
Source references preserve vendor object identity permanently — even after a canonical object is merged away (status=MERGED) or archived, its source_references rows remain queryable, satisfying Section 1.6's auditability requirement.
Source references do not store raw payloads — only source_payload_hash (SHA-256), enabling change detection (has this vendor record changed since we last saw it) without duplicating potentially sensitive customer data into this service's storage.
Source references support lineage and replay — first_seen_at and last_seen_at bound exactly when this service has observed this source record, which is the foundation for the Section 29 backlog replay capability.

9.1 Rules
SOA can be assigned at object-type level (field_path=null) or field-path level — a field-path assignment always takes precedence over an object-type assignment for that specific field, per the precedence_order column.
SOA assignments are customer-specific — no default assignment is shared across customers, even though the SOF Table 4.1 rules that generate SOF_RULE_AUTOMATIC assignments are the same rules for every customer; the resulting assignment row is still customer_id-scoped, never global.
SOA decisions are auditable — every assignment records its source (Section 1.11 enum) and reason; PATCH is restricted to ESCALATION_RESOLVED corrections only, so the history of how an assignment came to be is never lost to an edit.

10.3 Candidate Generation Algorithm
ON POST /identity-resolution/candidates (scope=SESSION, per Section 1.10):
  1. LOAD all canonical objects created_from_session_id = {this session}
     for the requested object_type.
  2. FOR each newly-created object O:
     SEARCH existing canonical_objects for the same customer_id + object_type
     WHERE status IN (ACTIVE, TENTATIVE, PARTIAL)
     STEP A — EXACT: compare normalized_key directly.
       IF match found → match_type=EXACT, score=1.00
     STEP B — EXTERNAL_ID (if Step A found nothing):
       CHECK canonical_payload for connector-documented cross-reference
       fields (e.g., IMS-201 Section 4.6 pattern: metadata.opportunity_id)
       IF match found → match_type=EXTERNAL_ID, score=0.98
     STEP C — NORMALIZED_EMAIL (if Steps A-B found nothing):
       Compare normalized email fields if present on both sides
       IF match found → match_type=NORMALIZED_EMAIL, score=0.95
     STEP D — FUZZY_NAME + supporting signals (if Steps A-C found nothing):
       Compute edit-distance-based name similarity
       Compute NORMALIZED_DOMAIN if email present but full match failed
       COMBINE per Table BIS3-10.1's COMPOSITE_KEY formula if both present
       IF combined score >= 0.40 → create candidate at that score
  3. FOR each candidate found: WRITE identity_resolution_candidates row
     with the confidence band from Table BIS3-10.2 applied to match_score.
  4. IF confidence band = AUTO_CONFIRM: immediately invoke the confirm
     logic internally (no separate API round-trip) and proceed to merge
     if applicable.
  5. RETURN candidates_generated count and the full candidate list to caller.
 
Section 11 — Merge Engine
Executes reversible survivorship decisions. Every rule here traces back to the Section 1.6 auditability requirement: nothing a merge does is destructive.
 
11.1 Survivorship Rules
ON merge request (from identity confirmation or explicit POST /merge):
  1. IF surviving_object_id explicitly provided: use it.
     ELSE compute survivor by priority:
       a. Highest object-level confidence wins
       b. Tie-break: object with the most source_references wins
          (more corroborating sources = more likely correct/complete)
       c. Tie-break: earliest created_at wins (stability preference)
  2. FOR each non-surviving object O in the merge set:
     CAPTURE a canonical_object_versions snapshot of O's current state
     (change_reason="PRE_MERGE_SNAPSHOT") — this is what makes unmerge exact.
  3. FOR each non-surviving object O:
     SET O.status = "MERGED"
     RECORD merge_operation_id and surviving_object_id on O
     (stored in O's confidence_breakdown.merge_context for query convenience,
      full detail in the merge history table)
  4. REPOINT all source_references from non-surviving objects to the
     surviving object_id — WITHOUT deleting or mutating the original
     source_ref_id rows (Section 1.5); a new field on source_references,
     current_object_id, is updated while object_id (the original link)
     remains as historical record. Downstream consumers always read
     current_object_id for active lookups.
  5. REPOINT all canonical_relationships where from_object_id or
     to_object_id references a non-surviving object, to reference the
     surviving object_id instead — original relationship rows are
     versioned via their own audit trail (Section 12), not silently edited.
  6. MERGE confidence_breakdown: the surviving object's confidence is
     recalculated using the UNION of all source_system_refs from every
     merged object — a merge can increase confidence (more corroborating
     sources) even though no new data was extracted.
  7. WRITE merge_history record: {merge_operation_id, surviving_object_id,
     merged_object_ids, reason, executed_at, executed_by}
 
11.2 Unmerge
ON POST /canonical-objects/{surviving_object_id}/unmerge:
  1. LOOKUP the merge_history record for this surviving object's
     most recent merge operation.
  2. FOR each merged_object_id in that operation:
     RESTORE canonical_objects row from its PRE_MERGE_SNAPSHOT version
     (Section 11.1 Step 2) — status back to its pre-merge value
     (typically ACTIVE or TENTATIVE).
  3. RESTORE source_references.current_object_id to each object's own
     object_id for references that were repointed during this merge.
  4. RESTORE canonical_relationships that were repointed during this merge.
  5. RECALCULATE the surviving object's confidence_breakdown, removing
     the contribution of the now-restored objects' source references.
  6. WRITE a new merge_history entry documenting the unmerge, referencing
     the original merge_operation_id — the original merge record is never
     deleted, only superseded by the unmerge record, preserving full
     history of the merge-then-unmerge sequence.
 
Customer-facing identity always shows the current surviving canonical object — any downstream service reading through GET /canonical-objects/{object_id} for a merged object_id is redirected (HTTP 301-equivalent in the response envelope: {status: "SUCCESS", data: {redirected_to: surviving_object_id}}) rather than returning stale data. Internal audit — merge-history, source_references with mapping_status=HISTORICAL — preserves every prior identity permanently, satisfying Section 1.6 without compromising the clean single-object view every other service expects.

12.2 Lineage Queries
Every canonical_object_versions row carries session_id and job_id, directly answering "what implementation session and what specific job produced this exact version of this object" — this is the mechanism BIS-002's created_from_session_id / created_from_job_id references on implementation_jobs connect to. A full lineage trace for any canonical object is: current canonical_objects row → canonical_object_versions history ordered by version → for each version, the session_id/job_id that produced it → cross-reference to BIS-002's implementation_jobs for what IMS section and connector that job executed → cross-reference to source_references for the exact vendor record(s) involved.
 
12.3 Replay (Backlog Reference)
Full replay — reconstructing what canonical state existed at any historical point in time by walking version history backward — is architecturally supported by this data model (nothing is destructively overwritten) but the replay execution engine itself is Section 29 backlog, not MVP. The MVP guarantee is that the data required for replay is captured correctly from day one; building the replay query engine is deferred.

Section 15 — Write APIs
Every write endpoint (single create, bulk-upsert, merge, SOA assign, relationship create) passes through the same five-stage pipeline before touching Postgres.
 
WRITE PIPELINE (applies to every write endpoint):
  STAGE 1 — Input validation:
    Request envelope shape check (required fields present, types correct)
    → INVALID_INPUT if malformed
  STAGE 2 — Schema Registry validation (canonical object writes only):
    canonical_payload validated against the object_type's registered schema
    → VALIDATION_FAILED with specific field errors if non-conforming
  STAGE 3 — Identity/uniqueness check:
    normalized_key computed (Section 1.8); UNIQUE constraint evaluated
    → DUPLICATE_OBJECT if an ACTIVE object already claims this key and no
      merge intent is signaled (this is a create-vs-update disambiguation,
      not necessarily an error — the caller typically retries as an update)
  STAGE 4 — Authorization check:
    Caller's service identity scope validated against the requested
    operation (Section 21) — e.g., only the Canonical Worker's identity
    may call the merge endpoint in the identity-confirmation-triggered path
  STAGE 5 — Persist:
    Postgres write, wrapped in a transaction that includes the
    corresponding canonical_object_versions insert when a version
    trigger (Table BIS3-12.1) applies — both writes succeed or both fail,
    never a partial state where a payload changes without a version record

Every create/update endpoint (Table BIS3-4.1, 4.2) accepts and requires an idempotency_key; retry with the same key is always safe and returns the original result, never a duplicate
Bulk upserts are safely retryable
Per-object rejection (Table BIS3-4.2) means a partially-failed batch can be corrected and resubmitted for only the failing entries — the caller never needs to re-derive which subset succeeded, since rejected[] names them explicitly by index
Merge/unmerge is idempotent with merge_operation_id
Retry of the same merge_operation_id returns the original outcome without re-executing survivorship logic a second time — critical since re-running survivorship computation on an already-merged state would be nonsensical
Source reference creation rejects duplicates deterministically
No retry logic is needed here because the operation is not meant to be retried on conflict — a duplicate source reference attempt (Section 4.2) signals a caller-side logic error (attempting to re-link an already-linked record) more often than a transient condition
Internal Postgres errors retry internally then escalate
Linear backoff: 30s, 30s, 30s (3 attempts), matching the pattern established in BIS-001 and BIS-002 for consistency; pages on-call after exhaustion

Section 28 — Failure Recovery
Failure
Immediate Effect
Recovery Behavior
Postgres unreachable
All reads and writes fail with INTERNAL_ERROR — hard dependency, matching BIS-001/BIS-002
Fail closed, no workaround. This service holds no application-layer cache of durable state, so recovery is automatic and complete once Postgres returns — no reconciliation step is needed.
This service crashes or is redeployed mid-request
In-flight requests fail; callers receive a connection error
Stateless design (Section 23) means any replacement replica serves the next request identically. A bulk-upsert interrupted mid-batch is safely retried in full by the caller using the same idempotency_key (Section 18) — the caller does not need to know which subset of the batch was persisted before the crash, since a full retry correctly no-ops the already-persisted entries.
Concurrent write race on the same normalized_key
Two callers simultaneously attempt to create an object for the same identity
Resolved by the Postgres UNIQUE constraint (Table BIS3-4.8 schema note) — one write succeeds, the other receives DUPLICATE_OBJECT and is expected to retry as an update or investigate; this is a correctness guarantee at the database layer, not application-layer locking, so it holds even under this service's horizontally-scaled multi-replica deployment.
Merge operation fails partway through the pipeline (Section 11.1)
Partial repointing could theoretically leave relationships or source references in an inconsistent state
The full merge pipeline (Steps 2–7) executes inside a single Postgres transaction — any failure at any step rolls back the entire operation, leaving all objects in their pre-merge state exactly as if the merge had never been attempted; there is no partial-merge state that can persist.
Schema Registry fails to load at startup
Service fails readiness checks and does not receive traffic
This is treated as a deployment-blocking condition, not a runtime failure to recover from — the CI/CD pipeline's readiness gate (Section 23) prevents a replica with a broken Schema Registry from ever serving requests.

BIS-003 is complete and ready for engineering to begin implementation. Together, BIS-001, BIS-002, and BIS-003 specify the three services that carry an implementation from external data through orchestration to durable canonical storage — the complete write path GPES-001 traces end to end. CAL Service and Reporting Service remain as natural next BIS documents, each reading from what BIS-003 stores rather than introducing new storage of their own.
 
The most consequential design decision in this document is Section 1.8 — normalized_key computed by this service, never accepted from the caller. Without that resolution, two Connector Workers writing what should be the same canonical Customer Account from different connectors could easily compute their own, inconsistent keys, silently defeating identity resolution before it ever runs. Making key computation this service's exclusive responsibility, driven by a per-object_type registered function rather than caller-supplied logic, is what makes the 86.3% match rate in GPES-001 a property of the platform's design rather than a coincidence of how one implementation happened to be extracted.
