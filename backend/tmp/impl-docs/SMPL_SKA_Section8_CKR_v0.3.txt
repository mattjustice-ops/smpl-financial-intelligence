Section 8.2  —  Module Capability Registry (MCR)
The Module Capability Registry is a new formal SKA component introduced in CKR v0.3. It resolves a responsibility overlap identified during final architectural review: in v0.2, the Capability Assessment Layer was simultaneously defining what financial intelligence modules require AND evaluating whether a specific customer had met those requirements. These are two distinct responsibilities with fundamentally different stability levels.
8.2.1  Why the MCR Is a Separate Component
Module definitions are stable. They change when the SCBM changes — when new canonical Business Objects are defined, when new Relationships are registered, or when new Business Concepts are added to the registry. Module definitions do not change when a customer connects a new system.
Customer readiness assessments are dynamic. They change every time a connector is added, every time a CEP field is updated, and every time a canonical object's population completeness improves. Customer readiness assessments are computed at runtime.
If these two responsibilities share one component, a change to a module definition (stable, rare) requires touching the same component as a customer readiness calculation (dynamic, frequent). This creates false coupling and increases the risk that a module definition change inadvertently affects a running customer assessment, or vice versa.
◉ DESIGN DECISION: The MCR owns all module definitions — what a module is, what it requires, and what it produces. The Capability Assessment Layer consumes MCR definitions as authoritative inputs and evaluates whether a specific customer's canonical data satisfies those requirements. The CAL never defines module requirements. The MCR never performs customer-specific assessment.

8.2.4  MCR Architecture — How It Integrates with the SKA

The MCR resolves a previously implicit architectural pattern. In v0.2, the Capability Registry lived in SKA Section 10 (Capability Assessment Layer) without a formal name or governance process. Module definitions were effectively embedded in the CAL's module readiness scoring logic. This worked for a small number of modules but would have become unmanageable at scale — adding a new module would have required modifying the CAL's assessment logic rather than simply adding an MCR entry.
With the MCR formally introduced: adding a new SMPL module requires creating one MCR entry. The CAL reads that entry automatically and begins assessing customer readiness against it. No CAL code changes required. The CAL is a generic assessment engine that evaluates any module defined in the MCR.
✱ ARCHITECT'S NOTE: The MCR is one of the most important architectural components introduced in the entire SKA design process. It draws the line between "what SMPL offers" (MCR) and "what a customer can access today" (CAL). This distinction enables SMPL to grow its module library without requiring implementation or CAL modifications for each new module — the addition of an MCR entry is sufficient.
Section 8.3  —  Confidence Architecture — Three-Way Separation
Version 0.2 defined Mapping Confidence in the CKR but did not formally separate it from the completeness of customer data or the certainty of AI reasoning outputs. These three concepts are distinct. They have different owners, different measurement methods, different customer-facing implications, and different governance requirements. Conflating them produces misleading confidence scores that erode enterprise trust.
8.3.1  The Three Confidence Dimensions
Dimension
Definition
Architectural Owner
What It Measures
How It Is Measured
Customer-Facing Implication
Mapping Confidence
How accurately vendor objects and fields were translated into canonical objects and fields by the Transformation Engine. This is a property of the mapping specification, not of any specific customer's data.
Connector Knowledge Registry (CKR) — defined per field mapping rule in Section S10 of the connector specification.
Reliability of the transformation rule across all instances. Direct-High: the rule is correct for ≥95% of implementations. Inferred-Low: the rule is a best estimate correct for 50–69%.
Categorical classification set by CKR engineering team during connector specification authoring. Validated by pattern observation across implementations.
Displayed in provenance chain: "This ARR value was computed using a Derived-High confidence mapping rule (CKR Stripe Rule R-047 v1.2)." Users understand the formula is reliable, not estimated.
Data Confidence
How complete, fresh, and internally consistent the canonical data is for this specific customer. This is a property of a customer's connected systems and data, not of the mapping specification.
Capability Assessment Layer (CAL) — computed per customer per module at runtime.
Completeness: what percentage of required canonical fields are populated? Freshness: how recently was the data refreshed? Consistency: do values that should agree (e.g., ARR chain integrity) agree?
Computed continuously from canonical object population maps (from CKR) + CEP refresh configuration + SCDM validation rule results.
Displayed as module readiness score: "ARR Analytics: 94% — Partial due to missing movement reason fields." Users understand what data would improve it.
Reasoning Confidence
How confidently the AI Reasoning Engine can produce accurate Financial Intelligence from the available canonical data and business relationships.
AI Reasoning Engine — generated per output at reasoning time.
Traversal completeness: were all required Knowledge Graph relationships traversable? Pattern strength: does the reasoning pattern match established causal patterns? Inference vs fact ratio: how much of the output is deterministic vs probabilistic?
Generated by the AI Reasoning Engine during traversal. Based on relationship confidence levels (from Relationship Registry), data confidence (from CAL), and comparison to established reasoning patterns.
Displayed on every AI-generated output with epistemic label: "VERIFIED FACT," "COMPUTED METRIC," "AI EXPLANATION (72% confidence)," or "AI PREDICTION (65% confidence, see supporting evidence)."

8.3.2  Why the Separation Matters for Enterprise Trust
Without this separation, a single "confidence score" can mean at least three different things simultaneously — and users cannot distinguish which aspect of the system they should be concerned about:
A low confidence score from a bad mapping rule (Mapping Confidence) means the CKR specification needs updating — a SMPL engineering problem.
A low confidence score from incomplete customer data (Data Confidence) means the customer needs to connect additional systems — a customer action item.
A low confidence score from sparse Knowledge Graph traversal (Reasoning Confidence) means the AI could not find sufficient connected evidence — an output quality signal for the specific answer, not a platform problem.
Each of these has a different resolution path, a different owner, and a different customer communication. Conflating them into one score creates three failure modes:
Customers blame their data when the problem is the mapping rule.
Customers trust AI outputs that carry low reasoning confidence because the mapping confidence is high.
Engineering teams optimize for the wrong dimension because they cannot isolate which confidence type is degraded.
⬡ TRUST IMPLICATION: Separating confidence into three dimensions is a trust architecture decision. When a CFO sees a recommendation marked "AI PREDICTION (65% confidence)" — and the provenance chain shows that Mapping Confidence is High, Data Confidence is 94%, and Reasoning Confidence is 65% based on sparse renewal history — they can make an informed decision about whether to act on that recommendation. A single undifferentiated score would leave them unable to calibrate their judgment.

8.3.4  Phased Implementation
The three-way confidence model is architecturally correct from the beginning, but implementation complexity differs by dimension:
Phase 1 (current): Mapping Confidence is already fully specified in the CKR (seven categorical levels). Data Confidence is partially implemented via module readiness scoring in the CAL. Reasoning Confidence is implicit in AI output labels — it is not yet formally computed and stored.
Phase 2: Data Confidence formalized with freshness and consistency factors added to the module readiness formula. Reasoning Confidence computed and stored per output, enabling comparison across time periods and customers (using SMPL engineering knowledge, never customer data).
Phase 3: All three confidence dimensions visible in the Provenance Chain with distinct provenance layers. Platform Confidence Score — a customer-facing aggregate — computable from all three dimensions with appropriate weighting.
◉ DESIGN DECISION: The three-way separation is adopted now. Terminology is standardized in this document and must be used consistently across all SKA components going forward. No implementation is blocked by the Phase 2 and 3 items — those are enhancements to an architecturally correct foundation.

8.5.2  Data Warehouse Connector — Special Case Assessment
The Data Warehouse connector category (Snowflake, BigQuery, Databricks, Redshift) warrants specific attention because it differs from all other connector categories in one fundamental way: the schema is customer-defined, not vendor-defined. There are no universal vendor objects to map — only customer-authored tables and views.
The template handles this correctly through the existing sections:
S3 (Strengths): documents warehouse-universal strengths — SQL access to any schema, bulk query performance, historical data depth, multi-source consolidation.
S8 (Vendor Object Inventory): documents that objects are customer-defined. CKR captures common patterns (e.g., "most Snowflake implementations have a subscription table with columns matching...") as Tier 2 patterns, not Tier 1 universals.
S9 (Population Map): documents expected completeness ranges from typical warehouse schemas, not guaranteed mappings.
S12 (Identity Resolution): documents that identity resolution in warehouse connectors relies on customer-authored join keys documented in the CEP.
No template modification is required for data warehouse connectors. The existing sections accommodate them with higher Tier 2 content and lower Tier 1 confidence.
✱ ARCHITECT'S NOTE: Data warehouse connectors are inherently lower-confidence than SaaS API connectors because the schema is customer-defined. A Snowflake connector specification will have more Tier 2 (pattern) content and fewer Tier 1 (universal) mapping rules. This is correct — the template's three-tier knowledge structure handles this gracefully without modification.

8.6.4  The Definitive Answer
Yes. If every future connector were built using this specification, SMPL could scale to hundreds of supported systems without redesigning the CKR.
This conclusion is based on five properties that the CKR has demonstrated across three design iterations:
Universal template applicability: the 18-section template was tested against 10 connector categories — ERP, CRM, Billing, HRIS, Payroll, Marketing, Customer Success, Product Analytics, Identity, and Data Warehouse. Every section applies to every category. No category required a structural change to the template.
Clean component separation: CKR owns universal vendor knowledge (15 confirmed responsibilities). CEP owns customer-specific decisions (14 confirmed responsibilities). MCR owns module definitions (introduced v0.3). CAL owns customer readiness assessment. These responsibilities do not overlap. Adding new connectors or modules does not require modifying any other component.
Automatic downstream integration: any connector built to the 18-section template is automatically consumable by the Transformation Engine (reads Section S10 field mapping rules) and the Capability Assessment Layer (reads Section S9 object population maps). No CAL or Transformation Engine modifications are required when new connectors are added.
Independent scalability: connector specifications are fully independent of each other. A change to the NetSuite connector specification does not affect the Salesforce connector specification. A new connector does not require updating any existing connector. The registry scales additively.
Knowledge compounding without customer data: every connector added to the CKR increases the platform's capability for all future customers without using any existing customer's data. The CKR grows through engineering work — accumulated connector knowledge compiled by SMPL's implementation team — and that growth benefits every future implementation at no marginal cost.
8.6.5  Architecture Freeze — Formal Recommendation
ARCHITECTURE REVIEW BOARD RECOMMENDATION: The Connector Knowledge Registry is hereby declared architecturally frozen. The template is complete. Future work transitions from architectural design to execution.
The freeze applies to:
The 18-section Standard Connector Specification template. No structural changes permitted without Architecture Review Board approval.
The 15 confirmed CKR responsibilities. No responsibility may be added or removed without ARB decision.
The 14 confirmed CEP responsibilities. Same governance applies.
The MCR structure and Tier 1 module list. New modules are added by populating the MCR template, not by modifying its structure.
The three-way confidence model (Mapping / Data / Reasoning). Ownership assignments are frozen.
The freeze does not apply to:
Individual connector specifications — these are populated, refined, and versioned continuously as connectors are implemented and improved.
MCR module entries — new modules are added as SMPL's product grows.
Tier 2 pattern library entries — these are updated as implementation patterns are observed and promoted.
Additive template sections (S19+) — these may be added after individual ARB review without modifying existing sections.

Architectural Risks
◆ ARCHITECTURAL RISK: The three-way confidence model introduces three independently measurable confidence dimensions, but the customer experience of "confidence" remains a single score in most UI surfaces. The design of confidence aggregation — how Mapping Confidence, Data Confidence, and Reasoning Confidence combine into a user-facing label — must be resolved before Phase 2 confidence instrumentation is built. The wrong aggregation formula could mislead users in the same way that a single undifferentiated score would.
Future Enhancements
⟶ FUTURE ENHANCEMENT: Public SMPL Connector Standard: the 18-section CKR template, published as an open specification. Vendors who implement this standard produce data that SMPL can ingest without custom transformation work. This is the long-term ecosystem leverage strategy and the CKR's most significant potential compounding asset beyond the registry itself.
⟶ FUTURE ENHANCEMENT: Automated connector certification testing: a test suite that validates connector specification compliance and production correctness. Level 1 certification becomes a passing test run, not a human review decision. Deferred to Phase 2 but architecturally enabled by the structured template.
⟶ FUTURE ENHANCEMENT: Platform Confidence Score: a customer-facing single number that aggregates all three confidence dimensions, weighted by module importance. "Your SMPL confidence score is 94%." Deferred to Phase 2 product development.
Decisions Deferred
⊡ DECISION DEFERRED: Machine-readable CKR schema: deferred to Phase 2 pending SCDM formalization. All template sections are structured for clean migration to JSON Schema without architectural redesign.
⊡ DECISION DEFERRED: Reasoning Confidence formal computation and storage: deferred to Phase 2 AI Reasoning Engine maturation. Architecture is correctly specified; implementation follows.
