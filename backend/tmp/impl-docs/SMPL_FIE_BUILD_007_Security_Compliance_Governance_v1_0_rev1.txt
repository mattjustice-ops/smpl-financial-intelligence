Operational Philosophy
Security is not merely about preventing unauthorized access. Security preserves customer trust by ensuring:
Every financial conclusion remains authentic
Every calculation remains reproducible
Every methodology remains governed
Every evidence chain remains intact
Every customer action remains attributable
Every administrative action remains auditable
The platform must never sacrifice transparency in pursuit of security. Likewise, security must never weaken evidence, lineage, or explainability — the same Trust Preservation discipline FIE-BUILD-006 established for performance, applied here to protection.
Section 1 — Security Philosophy
Zero Trust — no request is trusted by network location or prior authentication alone; every call is verified, per FIE-BUILD-002 §6's authentication standard
Least Privilege — a service's credentials grant only what that service needs, per FIE-BUILD-002 §10
Defense in Depth — no single control is the only thing standing between an attacker and customer data
Evidence Before Trust — the platform's own defining principle (FIE-005), applied to security: a security claim is only as good as the evidence backing it
Fail Closed — an ambiguous authorization or verification signal defaults to denial, per the fail-closed posture this platform applies everywhere else a tradeoff could tempt a shortcut
Secure by Default — a new service or feature ships with the strictest applicable security posture; loosening it requires an explicit decision, never the reverse
Immutable Auditability — the audit trail itself follows the platform's universal append-only discipline (FIE-BUILD-002 §8); no audit record is ever editable or deletable
Governance over Convenience — a security exception is possible, but always through Section 9's governance process, never as a quiet workaround
Trust Integrity Principle
Security exists to preserve the authenticity, governance, and trustworthiness of every financial conclusion the platform produces — not merely to prevent unauthorized access.
The security counterpart to FIE-BUILD-005 §6's Operational Confidence. Trust Integrity is maintained when:
Evidence remains authentic
Lineage remains complete
Methodologies remain governed
Calculations remain deterministic
Narratives remain attributable
Audit history remains immutable
Security controls should strengthen customer trust, never obscure platform behavior. This is this document's north-star principle, the same role FIE-BUILD-006's Trust Preservation Principle plays for performance — every section that follows answers to it.
Security Regression Policy
An explicit, unambiguous rule: security improvements may never reduce
Explainability
Evidence Integrity
Financial Lineage
Deterministic Calculations
Operational Confidence
Customer Transparency
even where the change genuinely improves security. A security improvement that weakens customer trust is classified as a regression, not an acceptable tradeoff — the same fail-closed, no-exceptions posture FIE-BUILD-006's Performance Regression Policy applies to speed, applied here to protection. This prevents a well-intentioned security decision from unintentionally violating the platform's own philosophy.

Section 3 — Identity and Authentication
Users — human operators, authenticated via SSO where the customer's organization supports it
Service Accounts — one identity per service, scoped per FIE-BUILD-002 §10's least-privilege standard
API Keys — for programmatic access, rotated per Section 5's key rotation policy

MFA — required for any elevated-permission human account (Section 4's approval workflows, FIE-002 Addendum A's restatement approvers, BIS-005 promotion reviewers)

Section 4 — Authorization
Role-Based Access Control (RBAC) — the primary model, matching the discipline-based roles already named throughout FIE-BUILD-001's Engineering Ownership Matrix and FIE-BUILD-003's Platform Ownership Matrix
Attribute-Based Access Control (ABAC) — named as a future capability, not built at MVP; RBAC is sufficient for the customer and role granularity this platform currently requires
Tenant Isolation — per FIE-BUILD-002 §10, enforced by customer_id on every table and every query, with no code path capable of a cross-tenant read
Administrative Permissions — elevated roles (restatement approval, knowledge promotion, security configuration) require a permission scope distinct from ordinary operational access, per FIE-002 Addendum A §1.4 and BIS-005 §15's existing precedent
Approval Workflows — multi-party approval for the platform's highest-stakes actions, extending the pattern FIE-002 Addendum A already established for restatement approval
Delegated Administration — a customer's own administrator may manage their organization's user access without platform engineering involvement, scoped strictly to their own tenant
Emergency Access — a documented break-glass procedure for incident response (Section 13), itself logged and reviewed after every use, never a standing bypass
Section 5 — Data Protection
Encryption at Rest — every service's storage, per the posture already stated in each owning spec's own Security section
Encryption in Transit — TLS for every request, internal and external
Field-Level Encryption — applied where a specific field's sensitivity warrants it beyond table-level encryption (e.g. compensation fields flagged in ABS-012's HRIS CSV Mapping Profile)
Customer Isolation — per FIE-BUILD-002 §10, the same tenant isolation guarantee restated at the data-protection layer
Key Rotation — scheduled rotation for encryption keys, independent of and in addition to Section 3's credential rotation
Secrets Management — no secret committed to a repository, ever, per FIE-BUILD-002 §10; all secrets injected at deploy time through the platform's secret manager
Secure Backups — per FIE-BUILD-005 §13, encrypted at rest identically to primary storage, never a lower-security copy of the same data
Section 6 — Financial Integrity Protection
Unique to this platform. Security controls exist to protect these specific financial artifacts — and must never alter their financial meaning in the process of protecting them.

What Security Must Never Do

Obscure which version was active for a given calculation, even from a security control's own audit perspective
Calculation Runs (FIE-003)

Section 7 — Audit and Lineage Protection
Protects: lineage, evidence, version history, methodology changes, administrative actions, calculation history, narrative history.
Audit history is immutable. Never editable. Never deleted. This is not a new rule — it is the platform's universal append-only discipline (FIE-BUILD-002 §8), restated here as a security guarantee rather than only an engineering one: an attacker or a careless administrator with elevated access still cannot rewrite what actually happened, because no code path anywhere in the platform has an UPDATE or DELETE grant on these records, enforced at the schema layer, not only by policy.

Section 11a — Data Privacy
The operational program behind Section 8's GDPR/CCPA compliance entries — those name the frameworks; this is what actually runs day to day.
Data Subject Access Requests (DSAR) — a defined, time-bound process for a customer's end user to request what data is held about them
Retention — per each service's own retention policy, consistent with the platform's append-only discipline (Section 7)
Subprocessors — every third party touching customer data (including LLM providers, Section 11b) is tracked, disclosed, and contractually bound
Data Processing Agreements (DPA) — executed with every customer and every subprocessor, per applicable jurisdiction
Immutability vs. erasure — the platform's core guarantee is that financial history is never deleted (Section 7); a privacy erasure request is satisfied by anonymization or scoped field-level removal of personal data, never by deleting the financial record itself. This is a real, structural tension worth stating plainly rather than glossing over: a GDPR erasure request and an immutable audit trail are reconciled by separating personal identifiers from financial fact, not by exempting financial records from privacy law or by breaking immutability to satisfy it
Section 11b — AI/LLM Vendor Security
FIE-005 sends financial context to LLM providers to generate reasoning and narratives. This is a distinct data-handling surface from FIE-BUILD-006 §11's AI scaling concerns (throughput, cost, routing) — this section governs what leaves the platform and under what terms, not how fast it happens.
LLM provider DPAs — executed with every model provider FIE-005 calls, per Section 11a
Zero-retention where required — configured with providers that support it, for customers whose contractual or regulatory posture requires it
Prompt content rules — what may and may not enter a prompt is explicitly scoped; raw sensitive fields (e.g. compensation data flagged per ABS-012's HRIS CSV Mapping Profile) are excluded or masked before reaching a model call, never passed through by default
llm_version audit tie-in — every Narrative Object already records llm_version (FIE-005 §17); this section makes that field a security and privacy audit artifact as well as an engineering one, since it is what lets a future data-handling question be answered against a specific model version and provider agreement, not a vague "the AI"

Explainability Protection
Security controls must never make customer outputs less explainable. Encryption, masking, and access controls may hide sensitive information, but they must preserve the ability to demonstrate, to an authorized viewer:
Where data came from
Which methodology produced it
Why a conclusion was reached
Which evidence supports it
How confidence was established
A security control that protects a value by making it unexplainable to the people who are supposed to be able to explain it has failed at its actual job, even if it succeeded at hiding data from an unauthorized viewer.
Governance Gates
Before approving any security-related architecture change:
Does it improve security?
Does it preserve determinism?
Does it preserve lineage?
Does it preserve explainability?
Does it preserve evidence?
Does it preserve Operational Confidence?
Only if every answer is yes should the change proceed — the security-specific instance of the same Scalability Gates pattern FIE-BUILD-006 established, applied to a different category of change with the same non-negotiable trust guarantees underneath it.

Principal Software Architect Review
Reviewed for whether security and governance preserve every trust guarantee established throughout the architecture, not only whether they satisfy compliance checklists.
1. Are Any Security Responsibilities Misplaced?
No. This document extends, rather than duplicates, FIE-BUILD-002 §10, FIE-BUILD-003 §13, FIE-BUILD-004 §11, FIE-BUILD-005 §19, and FIE-BUILD-006 §9 — each remains correct at its own level of detail; this document is the dedicated security depth all five deferred. Section 9's governance table is explicitly subordinate to the four prior ownership/governance tables, per this series' established reconciliation rule. Section 10 states its boundary against FIE-BUILD-006 §9 explicitly and symmetrically, matching the exact language FIE-BUILD-006's own Final Review used to describe that boundary.
2. Does Any Content Belong in BUILD-008?
Customer-facing security documentation and customer security questionnaire responses belong in the future FIE-BUILD-008 Customer Implementation & Success, not as an expansion of this internal-facing handbook
Nothing else in this document's core security methodology is misplaced — security, compliance, and governance are a cohesive enough domain to hold together as one document, the same judgment FIE-BUILD-003 and FIE-BUILD-006 each made for their own domains
The boundary is now stated explicitly, matching this series' established pattern: FIE-BUILD-007 establishes enterprise security, governance, and compliance. FIE-BUILD-008 establishes secure customer implementation, onboarding, activation, and operational adoption. Security policy remains governed here; customer execution belongs to FIE-BUILD-008.
3. Does the Document Preserve Every Trust Guarantee Established Throughout the Architecture?
Yes, by explicit, checkable mechanism rather than by assertion. Section 6 names the specific financial artifacts security must protect without altering their meaning. Explainability Protection states plainly that a security control hiding data from an unauthorized viewer must not also hide it from an authorized one. Governance Gates makes determinism, lineage, explainability, evidence, and Operational Confidence a mandatory checklist before any security-motivated architecture change — the same enforcement pattern as FIE-BUILD-006's Scalability Gates, applied to a different category of change against the identical set of non-negotiable guarantees.
4. Is BUILD-007 Ready to Become the Authoritative Security, Compliance & Governance Handbook?
Yes. Every one of the nineteen required sections plus all five additional recommendations (Financial Security, Explainability Protection, Governance Gates, Compliance Mapping, Security Decision Records) are present, every mechanism traces back to a specific guarantee already established in ABS/BIS/FIE or a prior BUILD document, and the one naming collision this document surfaced against FIE-BUILD-006 ("SDR") is resolved explicitly rather than left for a future reader to discover as an ambiguous cross-reference. Recommend freezing FIE-BUILD-007 and proceeding to FIE-BUILD-008 (Customer Implementation & Success) per the authoritative roadmap.
