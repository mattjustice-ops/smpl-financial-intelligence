ERP Implementation Library — Scope and Organization
This document contains the complete ERP Implementation Mapping Specification library: six IMS specifications covering every Tier 1 ERP platform in the SMPL connector catalog. Each specification follows the identical ten-section structure established by IMS-001 (NetSuite), the permanent reference implementation.
IMS-001 (NetSuite) precedes this library as the standalone reference document. It is summarized here for completeness but the authoritative version is the standalone IMS-001 document. IMS-002 through IMS-006 are the new specifications introduced in this build.

Cross-ERP Implementation Principles
These principles apply to every ERP IMS in this library and are stated once here rather than repeated across six specifications.
SMPL is always read-only. No ERP IMS specifies write operations. Every extraction is governed by D-019 (read-only connectors) across the SKA.
CEP governs all customer-specific decisions. Every IMS defers to the CEP for fiscal calendar, account type edge cases, consolidation policy, dimensional business meaning, and system-of-record disambiguation. The IMS provides the question; the CEP provides the customer-specific answer.
Confidence scores are per-customer floors, not universal ceilings. The CKR provides the architectural planning ceiling; the IMS Section 7 computes the customer-specific floor based on actual data quality, module availability, and CEP resolution status.
Revenue Recognition modules follow the same activation pattern across every ERP: high-confidence Revenue Schedule when the module is active; Derived-Low fallback from invoice service period fields when inactive. The ERP changes; the pattern does not.
Multi-entity support follows the same canonical pattern: Legal Entity hierarchy, intercompany elimination, currency translation. The specific API surface differs by ERP; the canonical model does not.
IMS-002 — Sage Intacct
Sage Intacct is the most architecturally distinct ERP connector in this library — a cloud-native multi-dimensional GL with no Transaction polymorphism, native multi-entity structure, and a Revenue Management module that competes with NetSuite ARM for mid-market revenue recognition depth. Its implementation profile is simpler than NetSuite in most respects, while matching or exceeding it on multi-entity and dimensional confidence.
✱ ARCHITECT NOTE: Key departure from NetSuite IMS: Intacct uses the REST API v3 with distinct, non-polymorphic object types (GLBATCH, ARINVOICE, APBILL, GLPAYMENT). There is no Transaction-type discrimination step analogous to NetSuite's Table 4.5 — each object type is unambiguously a specific canonical target. This simplifies Section 4 Transformation Rules and reduces the primary exception handling burden.

4.2 Date Normalization
Intacct REST API returns dates as structured objects with year, month, and day sub-fields rather than as ISO strings. The implementation agent must reconstruct the ISO 8601 date from components.
Intacct date format: {year: "2024", month: "03", day: "15"}
NORMALIZE Intacct date:
  date_string = year + "-" + month.zfill(2) + "-" + day.zfill(2)
  Validate: date_string parses to a valid calendar date
  ├─ Valid → accept as ISO 8601 date
  └─ Invalid → FLAG_FOR_CEP with specific field and record identifier
4.3 Multi-Book Accounting — Book Designation Enforcement
This transformation rule is unique to Intacct in this library and is the highest-severity implementation risk for multi-book customers. A customer running parallel GAAP/Tax/IFRS books will have transaction entries for each period across multiple books. Extracting without book filtering silently produces blended, incorrect canonical financials.
IF CEP.multi_book = true:
  REQUIRE: CEP.canonical_book is populated
  ├─ canonical_book confirmed → filter all GLBATCH queries:
  │   WHERE journal IN (CEP.canonical_book)
  └─ canonical_book NOT confirmed → BLOCK extraction
      LOG: "Multi-book accounting active. CEP must designate canonical
      book before GL extraction can proceed."
      DO NOT proceed with unfiltered extraction
IF CEP.multi_book = false:
  Extract all GLBATCH records without book filtering
4.4 Custom Dimension Value Extraction
When custom dimensions are present and have been CEP-resolved, their values are extracted from the dimensions sub-object on every GLENTRY and mapped to the corresponding canonical extension field.
FOR each GLENTRY where custom dimensions are active:
  entry.dimensions = {DIM1: "value_a", DIM2: "value_b", ...}
  FOR each dimension in CEP.resolved_dimensions:
    IF CEP.dimension_mapping[DIM_N].canonical_field EXISTS:
      Map entry.dimensions[DIM_N] → canonical_field
    ELSE:
      Map to extension field: ext.dim_{DIM_N} = value
      Mark as PENDING_CEP_RESOLUTION if not yet resolved
4.5 Intercompany Transaction Flagging
Intacct natively flags intercompany transactions on GLBATCH entries with the INTERCOMPANY field. This is structurally superior to NetSuite, which requires the implementation agent to infer intercompany status from subsidiary attribution. The flag is used directly for intercompany elimination logic in multi-entity consolidation.
IF GLBATCH.intercompany = true:
  Tag canonical GL Transaction: gl_transaction.is_intercompany = true
  Add to intercompany elimination queue for consolidation processing
  Flag will be used in Period Aggregate derivation to prevent double-counting
IF GLBATCH.intercompany = false or null:
  gl_transaction.is_intercompany = false
  Include normally in all period aggregates

Section 10 — AI Implementation Workflow
The Intacct workflow follows the same DISCOVER→ANALYZE→NORMALIZE→TRANSFORM→VALIDATE→POPULATE→SCORE→CAPABILITY ASSESSMENT→MODULE ACTIVATION→FINANCIAL INTELLIGENCE READY sequence established in IMS-001. Intacct-specific branch points:
BRANCH 1 — Multi-book active?
  YES → BLOCK extraction; require CEP.canonical_book before proceeding
         (Highest-severity Intacct-specific branch — do not proceed without resolution)
  NO → Continue normally
BRANCH 2 — Custom dimensions present?
  YES → Initiate CEP custom dimension resolution workflow (Section 1.3)
         Proceed with extraction; mark unresolved dimensions PENDING
  NO → Continue normally
BRANCH 3 — Revenue Management module active?
  YES → Extract Revenue Schedule from /v3/revreccustomer; confidence = D-H
  NO → Fall back to ARINVOICE service period derivation; confidence = DR-M
BRANCH 4 — Multi-entity active?
  YES → Apply intercompany flag from GLBATCH for elimination logic
         (simpler than NetSuite — flag is direct, no inference required)
  NO → Single entity; skip consolidation logic
IMPLEMENTATION SPEED ADVANTAGE vs NetSuite:
  The absence of Transaction polymorphism eliminates the type discrimination
  step and its associated exception handling. For standard configurations
  (no multi-book, standard dimensions), Intacct typically reaches
  canonical population faster than NetSuite with equivalent data volume.
IMS-003 — QuickBooks Online
QuickBooks Online is the simplest ERP implementation in this library — the least schema variability, the lowest CEP discovery burden, and the fastest path to Financial Statements readiness. Its implementation profile is bounded by two structural ceilings that no implementation effort can overcome: it is single-entity only, and it has no revenue recognition module. Both must be set as explicit customer expectations before implementation begins.
✱ ARCHITECT NOTE: Key departure from NetSuite IMS: QBO's schema is largely rigid. The implementation agent's primary discovery tasks are confirming accounting basis (cash vs. accrual) and Class/Location dimension conventions — a fraction of the CEP burden required for NetSuite, Intacct, or Dynamics 365. The speed advantage is real; the ceilings are equally real.

1.2 Accounting Basis Detection
QBO supports cash-basis and accrual-basis accounting. The API returns data in either basis depending on query parameters. This is the most consequential single CEP decision for a QBO implementation and must be resolved before any GL extraction begins.
DETECT accounting basis:
  Query Preferences API: GET /v3/company/{realmId}/preferences
  response.AccountingInfoPrefs.BookCloseDate → indicator of active use
  ASK CEP: "Does this company report on a cash basis or accrual basis?
  This determines how all revenue and expense timing will be presented."
  Record in CEP.accounting_basis (CASH or ACCRUAL)
  IF ACCRUAL:
    All API queries: accounting_method=Accrual parameter on relevant endpoints
    Revenue and expense timing reflects service delivery, not payment receipt
  IF CASH:
    All API queries: accounting_method=Cash parameter
    Revenue recognized when payment received; expense when payment made
    NOTE: Cash basis canonical financials are explicitly labeled in SMPL output
    to prevent interpretation as GAAP accrual-basis financials

Unlike every other ERP in this library, QBO requires no multi-entity detection step — the question is always answered before implementation begins. This simplifies discovery significantly.

4.2 Accounting Basis Enforcement
Every QBO query that returns financial data must include the accounting_method parameter matching CEP.accounting_basis. This is enforced at the query construction step, not post-extraction.
FOR every QBO financial object query (Invoice, Bill, JournalEntry, etc.):
  query_params.minorversion = 65  (current API version)
  IF CEP.accounting_basis = ACCRUAL:
    query_params.accounting_method = Accrual
  IF CEP.accounting_basis = CASH:
    query_params.accounting_method = Cash
    TAG all canonical objects: gl_transaction.accounting_basis = CASH
    These objects will be labeled in SMPL output as cash-basis
4.3 QBO Change Data Capture (CDC) — Deleted Record Detection
QBO's standard object endpoints do not return deleted records. Deleted records are only surfaced through the Change Data Capture endpoint. CDC must be queried on every incremental sync to detect logical deletions.
INCREMENTAL SYNC deleted record detection:
  GET /v3/company/{realmId}/cdc?entities=Invoice,Payment,JournalEntry,...
       &changedSince={last_sync_timestamp}
  FOR each deleted record in CDC response:
    Locate canonical object with matching source_id
    Update canonical: status = DELETED, deleted_at = CDC timestamp
    Exclude from all active-state calculations
    Preserve in historical record

IMS-004 — Microsoft Dynamics 365 Finance
Dynamics 365 Finance is the highest CEP-resolution-burden ERP in this library. Its Financial Dimensions framework — fully customer-defined, up to 10 dimensions per transaction — means the implementation agent cannot complete meaningful dimensional canonical mapping without customer input. Financial Statements reach READY status despite this; dimensional P&L remains PARTIAL until dimension resolution is complete.
✱ ARCHITECT NOTE: Key departure from NetSuite IMS: OData v4 is the API standard (instead of SuiteQL), enabling strongly-typed, standards-compliant query construction. GeneralJournalEntry is the core object, but posting source variety in enterprise implementations requires transaction-source discrimination analogous to (but structurally different from) NetSuite's Transaction type discrimination. Financial Dimension resolution is the primary implementation complexity driver — it has no equivalent in any other ERP in this library.

4.2 Financial Dimension Expansion — The Core Transformation Challenge
Dynamics 365 stores dimension values as a DefaultDimension reference key on each transaction line, not as inline field values. Resolving this reference to actual dimension values requires a separate API call per unique DefaultDimension key. This is the primary performance bottleneck in Dynamics 365 extraction.
FINANCIAL DIMENSION EXPANSION:
  1. During GeneralJournalAccountEntry extraction, collect all unique
     DefaultDimension keys across all lines
  2. BATCH resolve: GET /data/DimensionAttributeValueSets
     WHERE RecId IN ({unique_dimension_keys})
     Use $batch OData requests to minimize API round trips
     Cache resolved dimension sets in memory during extraction session
  3. FOR each resolved dimension set:
     FOR each dimension in CEP.financial_dimensions:
       Extract dimension value for dim_id from the resolved set
       Map to CEP.financial_dimensions[dim_id].canonical_target
         ├─ canonical_target = "Department"
         │   → gl_transaction_line.department_id
         ├─ canonical_target = extension field
         │   → gl_transaction_line.ext.{dim_label} = value
         └─ canonical_target = PENDING_CEP_RESOLUTION
             → do not map; tag line as DIMENSION_PENDING
  4. Cache hit ratio optimization:
     Maintain dimension set cache for full extraction session.
     In typical enterprise implementations, unique dimension set count
     is much smaller than total transaction line count.
     Cache hit rate > 80% expected for most enterprise configurations.
4.3 Signed Amount Convention
Dynamics 365 stores transaction amounts with a signed convention (positive = debit, negative = credit) rather than separate debit/credit fields as in NetSuite or Intacct's alternative convention. This normalization step is mandatory.
FOR each GeneralJournalAccountEntry.AmountMST:
  IF AmountMST >= 0:
    gl_transaction_line.debit_amount = AmountMST
    gl_transaction_line.credit_amount = 0
  IF AmountMST < 0:
    gl_transaction_line.debit_amount = 0
    gl_transaction_line.credit_amount = ABS(AmountMST)
  Validate: for each GeneralJournalEntry,
    sum(debit_amounts) = sum(credit_amounts) within 0.01 tolerance
4.4 Account String Parsing — Dimension Value Extraction
Dynamics 365 frequently returns combined account strings that include the main account AND dimension values concatenated with a separator (e.g., "110100-001-002" where 110100 is the main account and 001, 002 are dimension values). The main account must be extracted cleanly without the dimension portion.
FOR each AccountDisplayValue:
  separator = CEP.account_dimension_separator (typically "-" or "|")
  main_account = AccountDisplayValue.split(separator)[0]
  Validate: main_account matches a MainAccountId in the mapped GL Account set
  ├─ Match found → use main_account as gl_transaction_line.account_id
  └─ No match → FLAG_FOR_CEP — separator assumption may be wrong

Section 4 — Transformation Rules
4.1 CoA String Parsing — Multi-Segment Extraction
This transformation is unique to Oracle Fusion in this library. The AccountCombination field contains ALL segment values for a transaction line, concatenated with a customer-configured separator (typically "." or "-"). Parsing must use CEP.coa_segments to know which position maps to which canonical field.
FOR each journal line AccountCombination string:
  separator = CEP.coa_segment_separator (e.g., ".")
  segments = AccountCombination.split(separator)
  FOR each segment_definition in CEP.coa_segments:
    value = segments[segment_definition.position - 1]
    
    IF segment_definition.is_natural_account:
      → gl_transaction_line.account_id = value
    ELIF segment_definition.canonical_target == "Department":
      → gl_transaction_line.department_id = value
    ELIF segment_definition.canonical_target is an extension field:
      → gl_transaction_line.ext.{segment_definition.label} = value
    ELIF segment_definition.canonical_target == PENDING:
      → tag line as SEGMENT_PENDING; do not map this segment
  VALIDATE: len(segments) == len(CEP.coa_segments)
  └─ Mismatch → FLAG_FOR_CEP: CoA string format may have changed

Section 4 — Transformation Rules
4.1 ACDOCA Ledger Filtering — Mandatory First Step
This transformation has no equivalent in any other ERP in this library. SAP's Universal Journal stores all ledger variants (GAAP, tax, group reporting) in a single table, distinguished only by the RLDNR field. Extracting without this filter produces canonical financials that blend multiple accounting bases — the highest-severity data integrity risk in this library.
EVERY JournalEntryItem query MUST include:
  $filter=Ledger eq '{CEP.canonical_ledger}'
  CEP.canonical_ledger default: "0L" (SAP Leading Ledger)
  Confirm with customer's SAP Finance team before assuming 0L.
  Some implementations use a custom leading ledger identifier.
  DO NOT proceed without this filter.
  Unfilterd ACDOCA extractions include all parallel ledger postings,
  which produces understated or overstated canonical financials
  depending on intercompany and parallel accounting configuration.
4.2 SAP Date Format Normalization
SAP returns dates in YYYYMMDD format from some API responses. Convert to ISO 8601 (YYYY-MM-DD) before canonical storage.
IF date_string matches /^[0-9]{8}$/ (YYYYMMDD):
  iso_date = date_string[0:4] + "-" + date_string[4:6] + "-" + date_string[6:8]
ELIF date_string matches ISO 8601 already:
  Accept as-is
ELSE:
  FLAG_FOR_CEP — unexpected date format
4.3 Composite Natural Key Construction
SAP document numbers (BELNR) are only unique within a combination of Company Code (BUKRS) + Fiscal Year (GJAHR). The canonical source_id must be a composite key.
gl_transaction.source_id = BUKRS + "_" + GJAHR + "_" + BELNR
Example: "1000_2024_0100012345"
  Company Code: 1000
  Fiscal Year: 2024
  Document Number: 0100012345
This composite key is stable and globally unique within a SAP system.
Use it consistently across all GL Transaction and GL Transaction Line objects.

Final Determination
The ERP Implementation Mapping Specification library (IMS-001 through IMS-006) is complete. Implementation agents and human consultants have sufficient implementation knowledge to begin onboarding any Tier 1 ERP platform with minimal manual intervention. CRM IMS development may begin.
The six specifications in this library demonstrate that the IMS standard established by NetSuite generalizes across ERP connectors with fundamentally different architectures: Intacct's multi-dimensional GL with no polymorphism; QBO's rigid single-entity schema; Dynamics 365's Financial Dimensions framework; Fusion's multi-ledger architecture; SAP's Universal Journal. Each required genuinely different implementation logic — the standard accommodated all five without structural modification.
The cross-connector pattern that emerges from building five IMS specifications simultaneously, which would not have been visible from a single specification, is that every ERP in this library has exactly one pre-extraction gate that — if bypassed — produces silent, incorrect canonical financials rather than a detectable error. NetSuite: environment type. Intacct: multi-book canon. QBO: accounting basis. Dynamics 365: dimension resolution (partial block). Fusion: canonical ledger per entity. SAP: ACDOCA ledger filter. This pattern should become the first checkpoint in every future ERP implementation audit: "What is the mandatory pre-extraction gate for this connector, and has the CEP confirmed it?"
