Document Purpose and Scope
The SMPL Orchestration Framework (SOF) is the operational backbone of the SMPL platform. Where the architecture documents (SKA, SCBM, SCDM) define what SMPL produces, the registry documents (CKR, IMS Libraries) define how individual connectors are implemented, and the CEP, CAL, and MCR define how customer-specific decisions are stored and evaluated, the SOF defines how all of these systems collaborate in real time to onboard a customer from first engagement to Financial Intelligence Ready status.
The SOF is not a connector specification. It does not replace or modify any IMS document. It is the coordination layer that determines which IMS agents run, in what order, with what inputs, producing what outputs, and subject to what decision criteria at every stage. If the IMS libraries are the playbooks for individual connectors, the SOF is the coaching staff that assembles them into a team for a specific customer engagement.

The Single Governing Principle
Automate everything possible. Ask only what cannot be discovered.
Every decision the SOF makes must be traceable to this principle. When a node routes to PAUSE_FOR_CEP, it is because the required information cannot be reliably inferred from available data — not because it is easier to ask than to discover. When a node routes to CONTINUE, it is because the decision is deterministic from available inputs. This principle is enforced throughout the Decision Framework in Section 4.
Relationship to Prior Architecture Assets
The SOF is the fourth and final layer of the SMPL implementation stack, sitting above the three prior layers:
Layer 1 — Architecture (SKA, SCBM, SCDM): Defines the canonical model that implementations populate.
Layer 2 — Registries (CKR, MCR): Defines what each connector can produce and at what confidence.
Layer 3 — Execution (IMS Libraries, CEP, CAL): Defines how each connector is implemented and assessed.
Layer 4 — Orchestration (SOF): Defines how all of the above collaborate to onboard a specific customer.
The SOF never modifies or redesigns any asset from Layers 1–3. It coordinates them. A change to the IMS for Salesforce updates the Salesforce implementation agent's behavior; the SOF's coordination logic for that agent does not change unless the agent's inputs, outputs, or decision branch points change.
Section 1 — SOF Agent Registry
Every participant in a SMPL implementation is registered here with its responsibilities, inputs, outputs, and relationship to other agents. The SOF's coordination logic references agent IDs rather than agent names, ensuring that future agent additions or modifications require only Agent Registry updates rather than SOF logic rewrites.
1.1 Agent Taxonomy
SMPL implementation participants fall into three categories: Coordination Agents (manage orchestration flow, not implementation content), Implementation Agents (execute connector-specific IMS logic), and Evaluation Agents (assess outputs and activate capabilities). Human implementation consultants are registered as a fourth participant type — not agents, but with defined intervention points and communication protocols.

Section 2 — Core Orchestration Workflow
The SOF orchestration workflow is a seven-stage process from Customer Engagement to Financial Intelligence Ready. Each stage has explicit inputs, outputs, responsible agents, decision criteria, and success conditions. Stages 3 and 4 are the most parallelizable; Stages 1, 6, and 7 always require human involvement.

Stage 3 — Connector Implementation
Field
Content
Purpose
Execute the full IMS workflow (Sections 1–10) for each authenticated connector. This is the most time-intensive stage and the one with the most parallelism.
Responsible Agent
One Implementation Agent per connector (Table SOF-1.2), coordinated by COORD-001 (Implementation Coordinator).
Human Involvement
CEP Agent (COORD-002) surfaces PAUSE_FOR_CEP requests to the human consultant as they arise. Other than CEP resolution, Stage 3 is fully automated.
Inputs
Authentication credentials and CEP state for each connector.
Outputs
Per connector: populated canonical objects, per-object confidence scores, validation report, pending CEP items, and an Implementation Agent completion status (COMPLETE, COMPLETE_WITH_GAPS, PARTIAL, or BLOCKED).

All Implementation Agents can run simultaneously. The only coordination constraint is the Dataverse shared-tenant note for ERP-004 and CRM-003 (see Table SOF-1.2). Time-intensive agents (ERP-005, ERP-006, BIL-005, HRS-001) should be dispatched first within their domain group.
Dependency management
If an agent is BLOCKED (an IMS Section 9 block condition that cannot be auto-resolved), COORD-001 suspends that agent and dispatches a PAUSE_FOR_CEP or ESCALATE request. Other agents continue uninterrupted.
Success Condition
All dispatched Implementation Agents reach COMPLETE, COMPLETE_WITH_GAPS, or PARTIAL status. A BLOCKED agent with no pending resolution after 2 business days triggers an ESCALATE to the human consultant.

Section 3 — Decision Framework
Every decision node in the SOF produces exactly one of four outcomes: CONTINUE (automated execution resumes), PAUSE_FOR_CEP (human input required for a specific business decision), ESCALATE (human consultant must assess and resolve a complex condition), or ERROR (technical failure requiring investigation). No decision produces an ambiguous output — the SOF's determinism is its operational integrity.

3.5 Human Intervention Mandatory Conditions
The following conditions always require human intervention — they cannot be automated regardless of available data:
Business definition interpretations where multiple valid canonical mappings exist (e.g., a Billing status that could be ACTIVE or PAST_DUE depending on business policy)
System-of-authority conflicts between two systems with equal or similar confidence for the same canonical object type
Cross-domain conflicts where a customer's existing business logic produces outcomes that contradict SCBM canonical ownership (e.g., a customer who uses their ERP as their system of record for ARR, not their Billing platform)
Structural ceiling disclosures (e.g., Position Planning unavailable from BambooHR) that require customer acknowledgment before implementation proceeds
Any BLOCK condition that persists beyond 2 business days
Stage 6 Customer Review — always human-mediated
Section 4 — Canonical Integration Detail
The Canonical Integration Agent (COORD-004) executes the most complex coordination in the SOF — merging outputs from up to 21 Implementation Agents into a single coherent SCBM instance. This section documents the integration logic for the canonical objects most likely to appear in multiple connectors simultaneously.
4.1 Customer Account Identity Resolution
Customer Account (Legal Entity) records are the canonical object most likely to appear in multiple connectors. The same customer may be an Account in Salesforce, a Customer in Stripe, and a Customer in NetSuite — all representing the same business entity and needing a single canonical Customer Account record.
CUSTOMER ACCOUNT IDENTITY RESOLUTION ALGORITHM:
FOR each new Customer Account candidate from any Implementation Agent:
STEP 1 — Exact match (highest confidence):
  IF email matches an existing canonical Customer Account.primary_email:
    → MATCH (D-H confidence)
    → Link to existing canonical record; record source connector as contributor
STEP 2 — External ID match (high confidence):
  IF connector provides an external_id field that matches another
  connector's external_id for the same canonical record (e.g., Salesforce
  Account ID stored in NetSuite Customer.externalId):
    → MATCH (D-H confidence)
    → Record bidirectional ID link in canonical Customer Account
STEP 3 — Name-based fuzzy match (medium confidence):
  IF normalized company name (lowercase, stripped punctuation) has
  edit distance <= 2 from an existing canonical Customer Account.name:
    → TENTATIVE MATCH (D-M confidence)
    → FLAG for CEP confirmation before treating as confirmed match
    → Record as MATCH_PENDING in canonical Customer Account
STEP 4 — No match:
  → Create new canonical Customer Account record
  → Tag as source connector only
  → Log as UNMATCHED for Stage 6 review
POST-RESOLUTION:
  Compute match rate = confirmed_matches / total_candidates
  IF rate < 80% → PAUSE_FOR_CEP (Table SOF-3.4)
  IF rate >= 80% → CONTINUE with matched set

7.2 Readiness Score Calculation
READINESS SCORE = weighted average of all assessed capabilities:
  FOR each capability c in CAL_output:
    IF c.status = READY:
      contribution = c.confidence × c.importance_weight × 1.0
    ELIF c.status = PARTIAL:
      contribution = c.confidence × c.importance_weight × 0.5
    ELIF c.status = UNAVAILABLE:
      contribution = 0
  READINESS_SCORE = SUM(contributions) / SUM(importance_weights)
  EXPRESSED AS: percentage (0–100%)
  Importance weights are defined in the MCR for each capability.
  Core Financial Reporting and ARR Reporting receive the highest weights.
  Niche capabilities (e.g., specific territory reporting) receive lower weights.
  COMMUNICATE alongside the score:
  "Your SMPL Readiness Score is {N}%. This reflects the completeness and
  confidence of your current connected systems. Connecting {Recommended
  Connector} would improve this score by an estimated {delta}%."

8.2 Scheduled Reporting Orchestration
Board packages, executive dashboards, and periodic financial reports can be orchestrated by the SOF on customer-defined schedules. The Reporting Agent (COORD-005) assembles reports from the canonical store using the following workflow:
SCHEDULED REPORT ORCHESTRATION:
  TRIGGER: Scheduled date/time OR manual request
  1. COORD-005 queries canonical store for the requested report period
  2. COORD-005 validates that all required canonical objects for the report
     are current (modified within the report's recency threshold)
  3. IF any required canonical object is stale:
     → Trigger incremental sync for affected connector(s)
     → Wait for sync completion before proceeding
  4. COORD-005 assembles report from canonical objects
  5. EVAL-003 appends per-metric confidence scores to the report
  6. Report delivered via configured channel (email, dashboard, PDF)
  CONFIDENCE DISPLAY RULE:
  Every metric in every scheduled report displays its confidence score.
  No metric is presented without its confidence context.
  This is a non-negotiable SOF reporting standard.
8.3 AI Narration and Commentary
Future AI narration — the generation of natural-language commentary explaining financial results, workforce trends, and commercial pipeline movements — is a COORD-005 extension that operates on the canonical store after canonical objects are populated and validated. The narration agent is outside the scope of this v1.0 SOF but is architecturally positioned here to confirm that the canonical store structure and confidence scoring framework it requires are already in place.
Narration will always be confidence-gated: the narration agent does not provide commentary on metrics below a configurable confidence threshold, and any commentary generated below the full-confidence ceiling is labeled with its confidence level. This prevents the generation of confident-sounding narrative from low-confidence data — consistent with the SOF's core transparency principle.
8.4 Architecture Extensibility — New Connector Addition
Adding a new connector to the SMPL platform requires the following SOF changes, and only these changes — the core workflow, decision framework, and logging structure require no modification:
Register a new Implementation Agent in Table SOF-1.2 with its IMS reference, agent ID, and parallelism notes.
Add any connector-specific dispatch conditions (time-sensitive agents, shared-platform coordination) to Stage 3 notes.
Update Table SOF-4.2 (Cross-Domain Validation Matrix) if the new connector introduces new cross-domain validation relationships.
No other changes are required. The SOF's design ensures that connector additions are additive, not structural.

Final Determination
The SMPL Orchestration Framework v1.0 is complete. It defines how every major SMPL architecture asset — SKA, SCBM, SCDM, CKR, IMS Libraries, CEP, CAL, and MCR — collaborates during customer implementation. It is ready to serve as the foundation for all future AI Agent Playbooks.
The SOF closes a gap that existed across the entire prior body of architecture: the individual IMS documents define how each connector is implemented in isolation; the SOF defines how they coordinate in combination. The Customer Account identity resolution algorithm (Section 4.1), the Cross-Domain Validation Matrix (Table SOF-4.2), and the System-of-Authority Assignment rules (Table SOF-4.1) are the three pieces of coordination logic that no individual IMS document could specify — they required a view across all four domains simultaneously.
The Readiness Score formula (Section 7.2) is the SOF's most consequential customer-facing contribution: a single number that summarizes the implementation quality of a multi-connector, multi-domain SMPL deployment, with a clear explanation of what would improve it. Combined with the confidence-labeled capability explanations (Table SOF-6.2), the SOF ensures that the first thing a customer sees is not a list of technical statuses but a clear, honest picture of what SMPL can deliver today and what additional steps would expand that picture.
The governing principle — Automate everything possible. Ask only what cannot be discovered — has been operationalized throughout. Every PAUSE_FOR_CEP node in the Decision Framework is accompanied by the explicit reason the information cannot be auto-discovered. Every CONTINUE decision documents why human input is not required. The SOF never asks a question it could answer itself, and it never answers a question that requires human business judgment.
