## Scheduled context blob — future architecture

What you described fits well. Today everything is **on-demand**: every Copilot question and every AI commentary call rebuilds the blob from live DB queries. That is always fresh but slow and repetitive.

A **materialized context blob** would sit between the warehouse and Claude:

```mermaid
flowchart LR
    subgraph sources [Data sources]
        Cash[Cash / bridges]
        GL[GL / P&L]
        Opp[Opportunities / CRM]
        Mkt[Marketing / funnel]
    end

    subgraph refresh [Refresh triggers]
        ETL[ETL / table update webhook]
        Cron[Scheduled jobs]
        ME[Month-end close flag]
    end

    subgraph store [Blob store]
        Live[Live blob - current month]
        Snap[Weekly snapshots]
        Close[Month-end frozen blob]
    end

    sources --> refresh
    refresh --> store
    store --> Copilot
    store --> Commentary
    store --> Prompt5
```

### Suggested tiers (matches your intent)

| Tier | Data domain | Refresh cadence | Use |
|------|-------------|-----------------|-----|
| **Live** | Opportunity / pipeline drilldown | On query or short TTL (minutes) | Current deal-level context |
| **Weekly snapshot** | Same opportunity set | Saved each week | “What changed since last week” deltas in commentary |
| **Weekly** | Cash bridges, collections | After cash table updates | Copilot cash questions without full rebuild |
| **Monthly** | GL, income statement, headcount | After GL close load | P&L / opex drivers |
| **On update** | Any table in `data_sources` registry | Webhook or post-load hook | Partial blob refresh, not full recompute |
| **Month-end freeze** | Full composite blob | Once close is certified | Board export, Prompt 5 deck, archived Copilot context |

### What gets stored

Per org + close period, something like:

- `context_blob_live` — current composite text (or structured JSON sections)
- `context_blob_sections` — keyed slices (`cash`, `gtm_funnel`, `ytd_cfs`, `pipeline_drilldown`, …) so you only rebuild what changed
- `context_blob_snapshots` — `(org_id, period, snapshot_at, section, content_hash, blob_text)` for weekly opportunity (and optionally cash) diffs

Refresh logic: compare `content_hash` or `max(updated_at)` per source table → rebuild only stale sections → merge into composite → optionally append “since last snapshot” diff block for opportunities.

### What triggers refresh

1. **Data load completes** (your existing warehouse/ETL path) — emit `blob.refresh` with `{org_id, period, sections: ["gl", "cash"]}`
2. **Cron** — weekly opportunity snapshot; nightly validation that live blob isn’t older than source data
3. **Month-end** — freeze `context_blob_close_{period}` immutable; Prompt 5 and board exports read frozen blob for reproducibility

### Speed wins

- Copilot: read prebuilt blob (~50ms) instead of 10–30s of bundle collection + assembly
- `enrich_slide_with_ai` / Prompt 5: same blob or section-specific slices
- Prompt 5 deck: attach `copilot_context_blob` from store instead of rebuilding payload from scratch each export

```

         ↘ errors at any step
```

### Event types (shared)

| Event | CSV example | API example |
|-------|-------------|-------------|
| `batch_received` | File uploaded | `POST /ingest/batch` accepted |
| `rows_staged` | 12,400 parsed | 12,400 in request body |
| `rows_rejected` | 37 bad headers/types | 37 failed schema validation |
| `rows_imported` | 12,363 → warehouse | 12,363 → warehouse |
| `validation_run` | Close checks | Same checks |
| `rows_exported` | MD&A / board export | Same exports |
| `row_error` | Line 482: bad date | Record `ext_id=…`: missing period |

```
June 2026 close

```

## API-specific pieces (same ledger, extra metadata)

For API customers you’ll want on each batch:

- `idempotency_key` / `external_batch_id` (their system’s reference)
- `api_version` + endpoint
- Per-record `external_id` so errors map back to **their** CRM/ERP row
- Async pattern: `202 Accepted` → poll `GET /ingest/batches/{id}` (same status shape as CSV upload job)

Row-level errors return in a consistent shape for both paths:

```json
{
  "batch_id": "…",
  "source": "api",
  "summary": { "staged": 500, "imported": 497, "rejected": 3 },
  "errors": [
    { "row": 482, "external_id": "opp-9912", "field": "close_date", "code": "invalid_period", "message": "…" }
  ]
}
```

CSV uses `row` (line #); API uses `external_id` when present — same error table in the UI.
