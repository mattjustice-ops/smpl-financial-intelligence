## 1. Purpose

Define how SMPL handles customer data so Confidentiality commitments are operable for a small B2B SaaS FP&A platform — including ingest paths, tenant isolation, privileged support, and exports.

## 2. Scope

Applies to customer data in the SOC 2 system boundary ([../01_system_boundary.md](../01_system_boundary.md)):

- Financial warehouse facts (GL-derived, ARR, pipeline, headcount, close packs, etc.)
- Auth / org membership identifiers (email, sessions, invites)
- Export artifacts (Excel, board decks) generated by the product
- Prompt context sent to Anthropic (derived from engine outputs)
- Privileged ops / white-glove load paths that can touch tenant data

Customer source systems (NetSuite, Salesforce, QuickBooks, etc.) remain **customer-controlled**. SMPL does not operate those systems.

## 4. Classification default

Treat customer financial facts, org membership, support tickets with metrics, and production secrets per [P06](./P06_data_classification_and_handling.md). When unsure, treat as **Confidential**.

## 5. Ingest paths (honest state)

| Path | Status | Confidentiality rules |
|------|--------|------------------------|
| Self-serve CSV / upload | Product path | Store only in tenant-scoped warehouse; no shared staging dumps in git |
| White-glove / Path A (ops load) | Live for POC / early customers | Named operator only (Matt); minimize copies; delete staging files after load; document ticket/POC justification |
| Native ERP/CRM/billing connectors | Roadmap / sandbox prototypes | **Read-only** when implemented; never GL/ERP write-back; secrets in env stores only |

Do not claim native connectors are generally available until product and sales KB say so. Prototype/sandbox scripts must not use production customer credentials.

## 6. Hard product constraints

1. **No GL / ERP write-back** — SMPL reads and reconciles; personnel must not attempt workarounds that post journals, invoices, or payroll to customer systems.
2. **Multi-tenant isolation** — data is scoped by `organization_id`. Org A must not read Org B. Engineering must maintain isolation tests before Type I fieldwork ([../PROGRESS.md](../PROGRESS.md)).
3. **AI is not system of record** — Anthropic commentary is narrative; warehouse/engine outputs are authoritative for numbers. Keys stay on Railway (API) only.
4. **Card data** — Stripe handles PAN; SMPL does not store full card numbers.

## 7. Privileged / white-glove access

1. Only named operators in the access inventory may load or inspect tenant warehouse data outside the normal product UI.
2. Prefer customer-controlled exports or read-only shares over standing admin credentials.
3. After POC or ticket close: revoke temporary credentials, delete local staging copies, note completion date.
4. Break-glass DB access uses MFA’d Neon/Railway consoles (solo founder today — no separate break-glass login). Log purpose in ticket or IR notes if used for incident/support.

Detail for a dedicated privileged-access policy lives in future **P16**; until then, this section + [P03](./P03_access_control_policy.md) apply.

## 8. Storage & processing locations

| Store | Typical data |
|-------|----------------|
| Neon (Postgres) | Warehouse + auth/org tables |
| Vercel / Railway | App runtime; env-held secrets; logs (avoid dumping Confidential payloads) |
| Resend | Magic-link and transactional email |
| Anthropic | Prompt context for commentary |
| Stripe | Billing contacts / payment metadata |
| Sanity | Marketing CMS — confirm before storing customer-named Confidential content |

## 9. Sharing & exports

- Product exports remain **Confidential**; the customer controls downstream distribution (board, auditors, etc.).
- Do not email customer dumps to personal accounts or unsanctioned tools.
- External sharing of Confidential data requires NDA/contract or customer direction ([P02](./P02_acceptable_use_policy.md)).
- Sales/security questionnaires use approved “pursuing SOC 2” language only ([../SECURITY_ONE_PAGER.md](../SECURITY_ONE_PAGER.md)).
